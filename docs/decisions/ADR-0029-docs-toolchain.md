# ADR-0029: Documentation toolchain: doc comments as the single source of descriptions, generated OpenAPI and JSDoc pages, JSDoc as a lint gate

Date: 2026-10-14. Status: accepted (user, 2026-10-14, feature `docs-toolchain`).
<!-- On acceptance replace the whole Status sentence with the accepted form; never append to the proposed one. -->

## Context
Issue #27 asks that the documentation already written in the sources reaches its consumers: the 16 CDS doc comments (9 `db/` entities, the service, the `importProducts` action, the `ProductsImportFile` type, 4 service entities) reach nothing today, because the Node.js compiler drops doc comments unless `cdsc.docs` is on; the `$metadata` of `CatalogService` carries 4 `Core.Description` annotations, all inherited from `@sap/cds/common`; no OpenAPI document exists; JSDoc is required by CONVENTIONS section 4 but checked by nobody (`cds lint` lints CDS files only, CI runs no JavaScript ESLint at the root, the PostToolUse hook runs ui5lint only for the app); the registry keeps one JSDoc line per `srv/lib` export. `PATTERNS.md` has no row for where a description is written, for a generated API document, for a JSDoc page or for a documentation gate, so invariant 4 requires this ADR. Issue #28 (business-rules wiki) will consume the OpenAPI document and the JSDoc page and is blocked by this decision.

Facts measured on 2026-10-14 (`docs/features/docs-toolchain/research/docs-facts.md`): a doc comment on a `db/` entity or element is not propagated to the projection (capire "Doc Comments", confirmed on the project model and on a scratch model); a doc comment above an `annotate` statement and above the elements inside its block lands in CSN `doc`, in EDMX `Core.Description` and in the OpenAPI schema title and property description; when a doc comment and `@description` meet on one target the annotation wins; `cdsc.docs` raises the `Core.Description` count of the contract from 4 to 11 (+13 lines) and `cds.load('*')` honours the `package.json` setting, so the snapshot test, the registry and `cds watch` agree; `cds compile srv --to openapi -l en` resolves every `{i18n>}` placeholder (7 to 0) and `-l ru` would put Cyrillic into a committed file; the converter defaults to the `rest` protocol path (`/rest/catalog`) when the service has no `@protocol`; `--openapi:diagram false` is parsed as truthy; `jsdoc-to-markdown` aborts on the project's TypeScript-flavoured JSDoc types and renders nothing for functions inside `sap.ui.define`; `eslint-plugin-jsdoc` 65.3.2 supports ESLint 10 and its recommended set would need a backfill of 4 blocks in `srv/catalog-service.js` and 4 in `DetailsForm.js` under the rule set below.

## Decision
1. **One switch.** `package.json` gets `"cds": { "cdsc": { "docs": true } }`. No command, test or script passes `--docs`; `cds watch`, `cds compile`, `cds.test()`, `cds.load('*')` in the generators and the snapshot test read the same setting.
2. **One mechanism: the CDS doc comment.** A description is a `/** ... */` doc comment, never `@description`, `@Core.Description` or `@Core.LongDescription` in project CDS (the compiler prefers the annotation when both are present; two mechanisms would be two ways). Placement per artefact kind: (a) a `db/` entity may carry a doc comment as a developer note about the table (it reaches CSN, the registry and a future HANA `COMMENT`, never the contract); elements in `db/` carry none; (b) a service projection and its own elements are described in `srv/annotations/<Entity>.cds`: one doc comment above `annotate <Service>.<Entity> with {` and one above each element next to its `@title`; (c) the service, a bound or unbound action and its parameters, a service-level type and its elements, and a singleton are described at their definition in `srv/<name>-service.cds`; (d) a developer note in `srv/*.cds` that is not an API description is a `//` comment. A description is one sentence in English, written for the API consumer: the OpenAPI converter uses it as the schema `title` and the tag `description`, and Swagger UI shows it as the first line.
3. **Service header and language.** The service carries `@protocol: 'odata-v4'` (explicit; the OpenAPI server URL becomes `/odata/v4/catalog`, the EDMX is unchanged), `@title: 'Product Catalog API'` (`Common.Label` on the entity container, `info.title`) and `@Core.SchemaVersion: '1.0.0'` (`info.version`, mirrors `package.json` `version`, bumped together). Descriptions are English literals: `Core.Description` is API documentation read by developers and tools, Fiori Elements renders labels from `Common.Label` and nothing from `Core.Description`, invariant 10 requires English in sources and `-l en` keeps the committed document free of Cyrillic. This is the recorded exception to invariant 7 ("texts through i18n") for descriptions; elements inherited from `@sap/cds/common` keep SAP's localized `@description`.
4. **Generated OpenAPI document.** `npm run docs:registry` (`scripts/gen-registry.mjs`) writes, besides the registry, `docs/api/CatalogService.openapi3.json` through the new `scripts/gen-api-docs.mjs`: `npx cds compile srv --to openapi -l en -s all -o docs/api` (no `--docs`, no `--openapi:diagram`), then `info['x-sources'] = <sources hash>` of `scripts/lib/registry-sources.mjs`. `npm run docs:api` runs `scripts/gen-api-docs.mjs` alone (the command the issue asks for). `scripts/check-docs-fresh.mjs` adds the stamp check (`apiDocsStatus`) and `docs/registry/JSDOC.md` to its file list; `--fix`, the Stop gate and the CI step "Registry freshness" cover both without a change. `test/api-docs.test.js` pins the content and byte-compares the committed document with a fresh compile. JSON, English, one file per service.
5. **JSDoc page.** `gen-registry.mjs` writes `docs/registry/JSDOC.md`: every `/** ... */` block followed by a declaration (`export [default] [async] function|class|const`, `function name(`, a method or `sap.ui.define` member `name(args) {`, `const name = (...) =>`) in `srv/**/*.js` and `app/*/webapp/ext/**/*.js` (and `webapp/model/**/*.js` when it exists), one `##` per file, one `###` per symbol with the signature, the description and the `@param`, `@returns`, `@throws` rows; generator header, protected as generated output (ADR-0017), freshness by the registry hash. `REUSE-CATALOG.md` keeps its one-line purpose column and points to the page. No third-party JSDoc renderer.
6. **Swagger UI in development.** `cds-swagger-ui-express` is a root `devDependency`; it registers itself on `cds.on('bootstrap')` and serves `/$api-docs/odata/v4/catalog` and `/$api-docs/odata/v4/catalog/openapi.json` under `cds watch`; default `cds.swagger` options; `CDS_SWAGGER=false` in the `test` script only if the measured `npm test` cost is 2 seconds or more. Never a runtime dependency.
7. **JSDoc as a gate.** `eslint-plugin-jsdoc` in the root `eslint.config.mjs` (files `srv/**/*.js`) and in `app/products/eslint.config.mjs` (files `webapp/ext/**/*.js`): `flat/recommended` as warnings; errors for `jsdoc/require-jsdoc` (srv: `publicOnly: true` with `ClassDeclaration` and `MethodDefinition`; ext: `FunctionDeclaration`, `FunctionExpression`, `MethodDefinition`), `require-param`, `require-param-description`, `require-returns`, `require-returns-description`, `check-param-names`; `tag-lines` with `startLines: null`; `no-undefined-types` off under `webapp/`. Gates: the PostToolUse hook (root ESLint for `srv/`; `checkUi5` in `scripts/lib/file-checks.mjs` runs the app ESLint for `webapp/**/*.js` outside `test/` and `localService/`), SubagentStop (errors block), the new root script `lint:js` (`eslint .`) in the CI backend job and in `/test-all`, the existing app `lint:js` in the CI UI job and in `/test-all`. `Component.js`, tests and `scripts/` are out of the jsdoc scope.
8. **Registry shows descriptions.** `DOMAIN-MODEL.md` prints the `db/` note and the projection's description under each entity heading and a Description column per element from the projection's element `doc`.

First application: feature `docs-toolchain` (#27).

## Amendment: pinned OpenAPI converter, pretty-printed document, no install analytics (user decisions 2026-10-25, phase 3)
Phase 3 (PLAN step 3) installed `cds-swagger-ui-express` and found that decision 4 rests on a wrong assumption: the export does not run the converter bundled with `@sap/cds-dk`. Measured by `cap-backend-dev` on 2026-10-25 and re-checked by the orchestrator with `npm ls @cap-js/openapi`:
- **The plugin's converter breaks Swagger UI.** `cds-swagger-ui-express` 0.11.0 (latest) depends on `@cap-js/openapi ^1.0.4`, which resolved at the project root to 1.7.0 (published 2026-10-06, latest). With it, `GET /$api-docs/odata/v4/catalog/openapi.json` answers 500: `CDS compilation failed (@sap/cds-compiler v7.0.3) Error: Unexpected 'virtual': an element can't be virtual and an association/composition (in entity:"CatalogService.Products"/element:"DraftAdministrativeData")`. The cause is a line 1.7.0 adds to `lib/compile/index.js`, `csn = cds.clone(csn)`: the clone fails on the served model (`compile.for.nodejs`) of a draft-enabled service and works on the parsed model (`cds.load('*')`). 1.7.0 also changes the default protocol from `rest` to `odata`.
- **The CLI export uses the project copy.** `cds compile --to openapi` prefers a project-local converter (`cds._local`) over the copy bundled in `@sap/cds-dk` 10.1.0 (1.6.0, which works on both model forms). With the plugin installed, the export of decision 4 ran the plugin's transitive 1.7.0 and wrote 73 paths and 30 schemas instead of the 69 and 44 measured at the spec.
- **An install script reports analytics.** `swagger-ui-dist`, which the plugin brings through `swagger-ui-express`, depends on `@scarf/scarf`, whose install script sends installation analytics unless the consuming project opts out. CI installs with `npm ci --ignore-scripts`; a local `npm install` runs the script.

Decisions 1-8 stay as written; A and B replace the converter and serialization assumptions of decision 4.

A. **One declared converter.** The root `package.json` gets the devDependency `"@cap-js/openapi": "1.6.0"`, exact. npm dedupes the plugin's `^1.0.4` to it, so the CLI export of decision 4 and the Swagger UI of decision 6 run one declared converter, the version the spec measured. In decision 4, "the bundled converter of `@sap/cds-dk`" reads "the project's pinned converter".
- The pin is removed when a release serves a draft-enabled service without the error, in the change that also regenerates the document.
- A Dependabot bump to 1.7.x turns `test/api-docs.test.js` "serves the Swagger UI and its OpenAPI document in development" red. That red test is the intended guard.

B. **Pretty-printed document.** `docs/api/CatalogService.openapi3.json` is committed as two-space JSON with a trailing newline (`stampOpenApi` in `scripts/gen-api-docs.mjs`), not as the converter's minified single line, so a model change shows as a reviewable diff. Criterion 16 compares the committed bytes with the stamped serialization, `stampOpenApi(<fresh compile>, sourcesHash(root))`, not with the raw converter output. Phase 3 figures with the pinned 1.6.0 (scratch probe on the working tree, 2026-10-25): 69 paths, 44 schemas, 11 tags; 157,341 bytes minified, 283,160 bytes pretty-printed before the stamp. The spec's "about 156 KB" was the minified size; the 280,020 bytes of the 1.7.0 document describe no phase.

C. **No install analytics.** The root `package.json` gets `"scarfSettings": { "enabled": false }`, the opt-out that `@scarf/scarf` documents for the consuming project; it disables the install-time report for every package in the tree. CI keeps `--ignore-scripts`; the setting covers local installs.

Not decided here: a report of the 1.7.0 defect to `cap-js/openapi` is the user's call.

## Amendment: hook gates do what decision 7 says, converter outside the CAP group (user decisions 2026-10-25, phase 3 gate, PLAN step 4 part 2)
Step 4 part 1 (`cap-backend-dev`, `test-backend`, 2026-10-25) found that the hook paths of decision 7 do less than decision 7 says. The first fact was re-checked by the orchestrator, and by the architect on the source on the same day:
- **The glob matcher never expands braces.** `globToRegExp` in `scripts/lib/hook-utils.mjs` escapes `{` and `}` in its escape branch. That branch comes before the `{` branch, so `isUnder()` reads `{a,b}` as literal text although its JSDoc promises alternatives. Example: `isUnder('app/products/webapp/ext/fragment/DetailsForm.js', 'app/**/webapp/**/*.{js,xml,html}')` is false. Inventory of brace globs in `scripts/**` on 2026-10-25: exactly one, the ui5lint filter of `scripts/hooks/subagent-stop.mjs` (line 172). There are none in `MCP_RULES`, `PROTECTED`, `PROTECTED_EXCEPTIONS`, `GENERATED`, `REUSE_WATCH`, `STALE_SCOPE`/`STALE_EXCLUDE` or `CYRILLIC_SCOPE`/`CYRILLIC_EXCLUDE`. So SubagentStop ran ui5lint only for a changed `manifest.json`, never for webapp JavaScript, XML or HTML. Part 1 worked around the matcher in `file-checks.mjs` with one glob per extension (`UI5_SCOPE`).
- **SubagentStop runs no app ESLint.** Decision 7 names SubagentStop ("errors block") as a gate of the `webapp/ext` JSDoc rules, but `ui5Errors` runs only ui5lint. A missing JSDoc block in `ext/` is therefore reported at the edit (PostToolUse), in CI and in `/test-all`, but never blocks a hand-over.
- **npx may fetch a linter.** Both hook paths call `npx ui5lint` without checking that the app has it installed. When no `node_modules/.bin/ui5lint` exists anywhere from the app up to `/`, npx asks the registry for a package named `ui5lint`. That is a 404 today, but a package published under that name would be installed and run without a prompt. Part 1 already guards the app ESLint with `<app>/node_modules/.bin/eslint`.
- **A failed run reads as clean.** All four readers (`eslintNote`, `ui5lintNote`, `eslintErrors`, `ui5Errors`) parse `stdout || '[]'`. ui5lint and ESLint write a crash to stderr and exit 2 (`@ui5/linter` `lib/cli/base.js`; ESLint CLI exit codes, not verified by MCP), so a crash with an empty stdout reads as "no findings". Only a non-empty, non-JSON stdout is reported.
- **The pinned converter rides in the CAP group.** The `sap-cap` group of `.github/dependabot.yml` matches `@cap-js/*`. A bump of the pinned `@cap-js/openapi` (amendment A) would therefore arrive in the group PR, and the red Swagger test, which is the intended guard, would hold back every CAP patch in that PR.

Decisions 1-8 and A-C stay as written. D-G make the gates of decision 7 do what it says, and G scopes the guard of amendment A to the converter.

D. **Brace alternatives expand (user decision D1).** `globToRegExp` takes the `{` branch before the escape branch, so `{a,b}` becomes `(?:a|b)`. The alternatives are literal text: no wildcard and no nesting inside braces. An unclosed `{` and a lone `}` match themselves. Part 1's workaround is folded back: `file-checks.mjs` exports one `UI5_SCOPE`, and `subagent-stop.mjs` imports it instead of keeping its own literal. The scope follows the resources ui5lint lints: `['app/**/webapp/**/*.{js,html}', 'app/**/webapp/**/*.{view,fragment}.xml', 'app/**/webapp/manifest.json']`, one list with no exclusion list (orchestrator decision, 2026-10-25, after the implementer stopped on the first form).
- ui5lint lints XML only as views and fragments: `@ui5/linter` `lib/linter/xmlTemplate/linter.js` line 9 reads `altGlob ?? "**/{*.view.xml,*.fragment.xml}"`. Any other XML path on its command line fails the whole run. `npx ui5lint --format json webapp/localService/metadata.xml` in `app/products` exits 2 with "Specified file pattern ... did not match any resource" and writes no report.
- Under F, the first form (`*.{js,xml,html}`) would therefore have blocked SubagentStop after every `metadata.xml` regeneration, and the failed run would have hidden the other files' findings. Part 1 already sent `.xml` to ui5lint at the edit, and the `'[]'` fallback hid the failure.
- Verified on the source and by command (re-run 2026-10-26). `npx ui5lint --format json webapp/localService/metadata.xml` in `app/products` exits 2, writes nothing to stdout, and stderr reads "Specified file pattern 'webapp/localService/metadata.xml' did not match any resource". The exit 0 side is pinned by `test/hooks-file-checks.test.js` "sends only the resources ui5lint lints to ui5lint": a fragment reaches ui5lint, `metadata.xml` makes no npx call.

Effect: SubagentStop now runs ui5lint on every changed webapp `.js` and `.html` file, `test/` and `localService/` included as at the edit, and on view and fragment XML, and blocks on its errors. `metadata.xml` and any other non-view XML go to neither hook. ui5lint reports no findings on the 42 `.js`, `.html` and `.xml` files of `app/products/webapp` other than `localService/metadata.xml` (orchestrator, 2026-10-25), and `npm run lint`, which covers `manifest.json`, reports none either (2026-10-25). Existing code therefore blocks no agent. At the gate the implementer repeats the inventory grep and reports what each brace glob now matches.
E. **SubagentStop runs the app ESLint (user decision D2).** The scope is every changed `.js` file whose app-relative path is in `APP_ESLINT_SCOPE` and outside `APP_ESLINT_EXCLUDE`, that is `webapp/**/*.js` minus `webapp/test/**` and `webapp/localService/**`. These are the constants of part 1, now exported from `file-checks.mjs`. For these files SubagentStop runs `eslint --format json` once per app, in the app directory. Errors (severity 2) block, in the line format of the root ESLint errors; warnings pass. Decision 7's "SubagentStop (errors block)" now holds for `ext/`.
F. **Only installed linters run, and a failed run is a failure (user decision D3).** This applies to both hook paths: the PostToolUse checks of `file-checks.mjs` (which SubagentStop also runs for files written outside Edit/Write) and the SubagentStop lint gate.
- ui5lint and the app ESLint run only when `<app>/node_modules/.bin/<tool>` exists. An install in an ancestor directory does not count.
- A missing tool is a note naming the tool and the app, with the advice to run `npm install` in the app. At SubagentStop it is an advisory in `systemMessage`, never a block, because an agent may not install dependencies.
- One reader in `file-checks.mjs` parses a linter's JSON report for both paths. A run is clean only when its stdout parses as a report without messages. A non-zero exit without a parsable report, an empty stdout included, is a failure. It is a note at the edit and a blocking line at SubagentStop, naming the tool, the exit code and the end of stderr.
- The root ESLint (`checkJs` and the root pass of SubagentStop) goes through the same reader, so it inherits the failure rule. It keeps no install check: the root install (`npm ci`) is the precondition of every hook, and a missing root bin would make npx resolve the real `eslint` package, not an unknown name.
G. **The converter gets its own Dependabot PR (user decision D4).** The `sap-cap` group gains `exclude-patterns: ["@cap-js/openapi"]`. A bump of the pinned converter then arrives as a separate PR, and its red Swagger test (the guard of amendment A) blocks only that PR. The rest of the CAP group updates as before. This settles the last Consequences line of amendment A ("how such a PR is handled is open to the user").

Upstream report (user decision D5): the user posts an issue on the 1.7.0 defect to `cap-js/openapi`, and the orchestrator drafts its text. This replaces the "Not decided here" line of amendment A. No repository file changes.

## Alternatives
| Option | Why rejected |
|---|---|
| `@description` in `srv/annotations/<Entity>.cds` next to `@title` | works the same in CSN, EDMX and OpenAPI and is localizable, but it is a second mechanism next to the 16 doc comments the project already has, and the compiler silently prefers it over a doc comment on the same target; kept as the fallback if the user wants localized descriptions (then it replaces doc comments on projections and elements) |
| Doc comments on the projections inside `srv/<name>-service.cds` | 4 exist, but element descriptions cannot live there (projection elements are not listed) and invariant 5 keeps entity semantics in `srv/annotations/`; the entity sentence and its element sentences belong in one file |
| `--docs` on each command | `cds watch`, the snapshot test, the registry generator, the OpenAPI export and MCP would each need the flag; one `package.json` setting is read by all of them |
| i18n keys for descriptions (`en` and `ru` bundles) | about 60 keys per bundle for text no UI renders; the OpenAPI document is English by `-l en` anyway; offered as Open question 1b |
| `--openapi:url /odata/v4/catalog` in the export command | imperative repetition of a fact the model can state; `@protocol: 'odata-v4'` is declarative, changes no EDMX and makes a second service self-describing |
| Byte comparison with a fresh compile in `check-docs-fresh.mjs` | one `cds compile` per Stop gate and per CI run for the check alone; the stamp is a 1 ms read, the byte comparison lives in `npm test` where a compile already runs |
| OpenAPI document under `docs/registry/` as JSON | the generated-file gate reads a header hash from the first line (`recordedHash`); a JSON file has none and would block every hand-over as a "hand write" |
| OpenAPI as YAML under `docs/registry/` (comment header possible) | needs a YAML emitter the project does not have; #28 parses JSON with `JSON.parse` |
| `jsdoc-to-markdown` / `jsdoc` for the JSDoc page | measured: aborts on `{{ ID?: string }}` and `Array<{ ID: string, ... }>` (jsdoc's type parser is not TypeScript-flavoured) and renders nothing for the 56 documented functions inside `sap.ui.define` factories, with or without `@module` |
| TypeDoc | `typescript` peer dependency (ADR-0005 keeps TypeScript out), and the same blindness to `sap.ui.define` members |
| `flat/recommended-error` wholesale | 120 findings in `ext/` today, 49 of them UI5 namespace types the plugin cannot resolve and 55 a blank-line style; the chosen set blocks on what the convention asks for and warns on the rest |
| `require-jsdoc` on every function kind in `srv/` | would require a block on every arrow callback inside handlers; the convention asks for exported functions and the handler class methods |
| `ext/` gate through CI and `/test-all` only (option B) | the issue asks for the PostToolUse lint; an agent would learn of a missing block at the commit or the PR instead of at the edit; offered as the cheaper option in Open question 4 |
| `cds-swagger-ui-express` as a runtime dependency | the service already serves `$metadata`; the UI is a development aid, and a production install must not ship it |
| Extending `HANDLERS.md` and `REUSE-CATALOG.md` with full JSDoc instead of a page | the registry tables answer "what exists"; a page per file with parameters answers "how to call it" and is what #28 links |
| Amendment A: `overrides` for `@cap-js/openapi` in `package.json` | invisible to Dependabot: no PR would ever announce a fixed release, so the pin would outlive the defect unnoticed; rejected by the user, 2026-10-25 |
| Amendment A: live with the 500 | Swagger UI of decision 6 broken in development, criterion 21 red, and the CLI export on a converter the spec never measured; rejected by the user, 2026-10-25 |
| Amendment A: withdraw decision 6 (no Swagger UI) | drops the live page the issue asks for; only the committed document would remain; rejected by the user, 2026-10-25 |
| Amendment B: commit the converter's minified output | one line of about 157 KB: every model change is a whole-file diff that no reviewer can read |
| Amendment C: rely on `npm ci --ignore-scripts` | covers CI only; a local `npm install` still runs the install script |
| Amendment C: `SCARF_ANALYTICS=false` or `DO_NOT_TRACK=1` in the environment | per machine and per shell, not committed; the `package.json` setting holds for everyone who installs the project |
| Amendment D: keep one glob per extension and correct the JSDoc of `isUnder()` | the matcher would keep a syntax that every reader of a glob assumes works, and the dead SubagentStop filter shows the trap is real; rejected by the user, 2026-10-25 |
| Amendment D: the scope `app/**/webapp/**/*.{js,xml,html}` as first written | ui5lint fails the whole run on any XML that is not a view or a fragment, so every `metadata.xml` regeneration would block SubagentStop under F and hide the findings of the other files; rejected by the orchestrator, 2026-10-25 |
| Amendment D: that scope plus an exclusion list with `app/**/webapp/localService/**` | a second list next to the scope, and any other non-view XML outside `localService/` still fails the run; rejected by the orchestrator, 2026-10-25 |
| Amendment E: drop SubagentStop from the gates of decision 7 | an `ext/` function without JSDoc would reach the phase commit and fail only in CI or `/test-all`; rejected by the user, 2026-10-25 |
| Amendment F: skip a missing tool silently (part 1 behaviour for the app ESLint) | the gate looks green while it checked nothing; the note tells the agent and the user that the app needs `npm install` (architect) |

## Consequences
- `PATTERNS.md`: new rows "Description of an entity, element, action or type" (Service and logic: decision 2 and 3 forms, example `srv/annotations/Products.cds`), "Generated API documentation" (Infrastructure: `npm run docs:registry` writes `docs/api/CatalogService.openapi3.json` and `docs/registry/JSDOC.md`; `npm run docs:api` alone; Swagger UI at `/$api-docs/odata/v4/catalog` in development), "JSDoc requirement and gate" (Infrastructure: the rule set, the scopes, `npm run lint:js` at the root and in the app); "Shared function for several handlers" points to the rule set.
- `CONVENTIONS.md`: section 2 adds `docs/api/` (generated OpenAPI); section 3 adds "a description is a doc comment: `db/` entity note, projection and elements in `srv/annotations/<Entity>.cds`, service artefacts at their definition; no `@description`"; section 4 names the jsdoc rule set as the definition of "JSDoc on every exported function"; section 5 adds "JSDoc on every function of `webapp/ext/**`"; section 8 lists `docs/api/CatalogService.openapi3.json` and `docs/registry/JSDOC.md` as generated by `npm run docs:registry`.
- Rules (protected, `PIPELINE_ALLOW_PROTECTED=1`): `srv-services.md` (doc comments in the annotations file, `@Core.Description` removed from the allowed list, the service header), `db-model.md` (developer-note doc comment), `srv-handlers.md` (the jsdoc rules are the gate), `ui5-webapp.md` (JSDoc for `ext/`, `npm run lint:js`); skills `test-all` (two `lint:js` steps) and `gen-docs` (names the new files); `test/prompt-budget.json` re-recorded.
- Templates: `annotations-semantic.cds` (doc comments on the `annotate` statement and the elements; `@Core.Description` dropped from the header comment), `service.cds` (`@protocol`, `@title`, `@Core.SchemaVersion`, doc comments on the service, an action and a type), `entity.cds` (a developer-note doc comment).
- `TESTING.md`: the Static row gains "ESLint for JavaScript at the root (`npm run lint:js`, incl. JSDoc)"; a new row "Generated docs freshness: `node scripts/check-docs-fresh.mjs` (registry hash, OpenAPI stamp), `test/api-docs.test.js` (byte comparison)". `STACK.md`: `cds-swagger-ui-express`, `eslint-plugin-jsdoc` (root and app), `@cap-js/openapi` bundled with cds-dk.
