The review step always runs before `docs-keeper` (step numbers differ per plan: 16/17 in `categories-code-list`, 10/11 in `products-draft-edit`, 8/9 in `products-draft-marker`). At review time these are expected, not findings: missing `SUMMARY.md`, unrefreshed or uncommitted `docs/registry/*`, PATTERNS/TESTING/templates not yet updated, unticked PLAN and ADR consequence checkboxes, missing LESSONS entries, stale "Next steps" wording in STATE. `ui-verifier` may run in parallel (runs 1-2, so `VERIFICATION.md` can be absent while `screenshots/` exists) or as its own phase before the reviewer (run 3: `VERIFICATION.md` present with a verdict, still uncommitted). UI runner output (`ui5-test-runner`) is gitignored (`app/products/report/`), so the OPA "passed" claim rests on agent reports plus `VERIFICATION.md`.

Since the second run the PLAN carries an explicit reviewer checklist in the "Review" step row; the orchestrator's task message repeats it with numbered items and asks for evidence per item (command output quoted). Work through that list first, then the generic protocol.

Since the third run the review phase is split into several `reviewer` invocations, one per lens (e.g. "plan conformance, patterns and layers", "documentation truth and language discipline"); each lens gets the same diff but a different numbered work list. Consequence for severity: a defect whose fixer is `docs-keeper` in the next phase must be `non-blocking`, because marking it blocking would stop the review phase from closing and `docs-keeper` cannot run before it closes. Reserve `blocking` for defects in the committed code/annotations or a language-rule violation, and put every phase-6 item in the findings list anyway so nothing is lost.

Since the third run the orchestrator also spawns a `reviewer` to *refute* one other reviewer's finding ("default to refuted unless you can positively establish it must block"). The decisive check in this project is the PLAN's split between its prose acceptance criterion and its normative code block: `PLAN.md` "Acceptance criteria" describes what the artifact should contain, while "Details for the developers" pastes the exact code the developer must write. When those two disagree (2026-09-09: criterion asked for an *ordered* `Term="Common.SemanticKey"` … `<PropertyPath>name</PropertyPath>` assertion, the code block gave two independent `toContain` calls, and the implemented test was byte-identical to the code block), the implementer who followed the code block is not at fault - deviating from an approved plan silently is the forbidden move (protocol section 9). Diff the plan block against the implementation (`sed -n` both ranges into the scratchpad, `diff`) before accepting such a finding, and check whether a behavioral test elsewhere in the same feature already covers the gap the finding claims is unguarded.

**Why:** First run (2026-09-07): the orchestrator said not to flag registry drift; VERIFICATION.md was absent at review time. Second run (same day): same hand-off shape, plus explicit "do not start or stop dev servers" because ui-verifier owns :4004. Third run (2026-09-09, `products-draft-marker`): the hand-off lists the deliberately uncommitted phase-6 files by name, pre-supplies the measured gate numbers ("do not re-derive"), assigns a lens ("plan conformance, patterns and layers"), and requires the answer through the StructuredOutput tool instead of prose.

**How to apply:** Report registry/STATE/PATTERNS gaps as "for docs-keeper", not blocking. Re-run yourself: `npm run lint`, `npm test`, `node scripts/check-docs-fresh.mjs`, `npx prettier --check` on changed test files, `diff <(cds compile '*' --to edmx-v4 -s CatalogService -l en) app/products/webapp/localService/metadata.xml`, and `ui5lint` in `app/products` (cheap, ~10 s). In zsh quote grep globs (`--include='*.cds'`, `ls srv/*.js` fails with "no matches found" when empty, which is the wanted evidence). Do not write a REVIEW.md unless the plan lists it as a step artifact; return findings in the message.
