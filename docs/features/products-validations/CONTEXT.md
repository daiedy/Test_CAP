# products-validations: context

Date: 2026-10-13, amended and approved 2026-10-14 (plan gate: every open item accepted as recommended). Author: `architect`. Branch: `spec/products-validations` (feature branch `feature/products-validations` at implementation). Issue #10.

This file is the brief for the implementers: every agent of the feature reads it whole (protocol step 1), so it holds only the sections below (ADR-0018). Screens go to `SCREENS.md` (`ux-designer`). Experiments, measurements, rejected mechanisms and framework facts are in `research/validation-facts.md`, read by `architect` and `reviewer` unless a plan step names it.

## Request
Issue #10: Object Page validations, through annotations where possible. The user's addition at `/spec` start: come up with logical constraints for all fields, including the typed details of feature #9; not every field needs one; the point is a set of not-so-ordinary validations that show what the project can do. At the plan gate (2026-10-14) the user asked for more rules on the details and set the principle that shapes the whole catalogue: wherever possible look for validations and controls that leave the user no way to make the mistake; then there is nothing to check. So the deliverable is a showcase: every rule has a domain reason in a product catalog, names the control that prevents the error before the request where the framework offers one, and keeps a server constraint as the guard on every path (API, import, draft, Save); the feature has no handler except the import pre-checks; messages explain the reason, in `en` and `ru`.

## User decisions
Plan approved on 2026-10-14 ("accept the recommendations" for every open item):
- Principle "prevent before validate": prefer controls that make the mistake impossible over validating after the fact; every rule in the catalogue names its preventing control ("Preventing controls" table below) and keeps the server constraint as the API guard.
- D1 rule set: R1-R6, R8, R10-R13. R7 (description equals name) is not included. R9 and R14 are rejected (below).
- D2 custom texts per rule through `@assert.format.message` / `@assert.range.message` and constraint keys; cds defaults stay for `@mandatory`, `@assert.target` and the existing stock and rating ranges.
- D3 framework timing (format and range in the `PATCH` response, constraints on the next `DraftMessages` read, `@mandatory` at Save); no typing handlers.
- D4 R6 condition `stock > 0`; the writers that omit a description change (`newProduct`, `generatedRow`, README).
- D5 = A: the required flag is read from the assignment by the constraints and the form; no copied column.
- D6 the seven required assignments: `LAPTOPS/SCREEN_SIZE`, `MICE/DPI`, `SEATING/MAX_LOAD`, `APPLIANCES/POWER`, `APPLIANCES/CAPACITY`, `DRINKWARE/CAPACITY`, `FITNESS/THICKNESS`.
- D7 per-row import pre-checks for R4 and R6 as pure functions in `srv/lib/products-import.js`.
- D8 `error()` with two targets (R4, R6) and with path arguments (R11), pinned by backend tests.
- R10 "bounds per assignment": `SubcategoryAttributes.minValue` and `maxValue` narrow the attribute's global bounds for one subcategory; seed values in the "Seed" list below; the global bounds stay the first guard.
- R11 "Storage not below Memory (laptops)": a showcase of a rule between two detail rows of one product ("I would not add such items myself, but as an example of what we can do it is good"); D11: data-driven through `DetailAttributes.atLeast`, no mirror branch (one defect, one message at Save when only Memory changed); D12: the LAPTOPS `STORAGE` bound is 32-8192 so the rule is reachable inside the bounds.
- R13 "Memory is a power of two (laptops)": accepted on the same showcase grounds; D13 b: no suggestion list, no `DetailAttributes.suggestions` column; the constraint, the LAPTOPS bounds and the message suffice.
- R12 "battery life only for wireless connectivity": not a validation but a control: the Battery Life row is disabled (and its value cleared) while the Connectivity row of the same product has no wireless value or no value at all, enabled as soon as a wireless value is selected; data-driven through `DetailListValues.enables`; the server keeps one `@assert` branch as the API guard only (invariant 6, ADR-0027 split), marked "guard, not user-facing".
- D13 a: the currency code list (`@CodeList.CurrencyCodes` on the service, `Common.UnitSpecificScale: minorUnit` on `Currencies/code`) is a regular step of the UI phase with its browser proof: the Price field refuses `10.50` with `JPY` on the client; the text that appears is recorded.
- R9 "text pattern": dropped entirely. The user replaces the free-text `DIMENSIONS` attribute by three numeric attributes (length, width, height) and a free-text `MODEL` attribute in a separate backlog issue (the dimensions remodel, A+), blocked by #10 because it reuses R10's bounds per assignment; a format rule on free text is then not needed. `DIMENSIONS` keeps its current seed in #10; `DetailAttributes.pattern`, the handler and every R9 artefact are out. The `matchespattern` measurement stays a fact (research section 10.5, ADR-0028 alternatives).
- R14 "at most N selections in a MULTI_LIST": rejected (an aggregate or a subquery is not allowed in `@assert`, `exists` cannot count, a handler would be the only way, no domain reason).
- SCREENS: Q1 the two-target live message for R6; Q2 the framework's client texts for R3 and R10 on the screen (the project texts reach the API and the import); Q3 no MULTI_LIST required assignment (the API-only branch stays); Q4 the texts of SCREENS "Texts" (the action-first rewrites, the dependency hint data-driven "Depends on {0}"); Q5 the range hint as the placeholder of the empty input (`10–18`, the unit in `description`); Q6 a 3-second toast when a dependent value is cleared on disable; Q7 a disabled row is outside the counter "Filled N of M".
- Standing decisions that shape the design: semantics in `srv/annotations/`, presentation in `app/products/annotations/` (ADR-0004); `@assert: (case ...)` constraints before handlers (ADR-0024 decision 2); persistence `@assert.unique` only in `db/` and never for a user-facing rule on a draft entity (ADR-0026 decision 1, TESTING); the Details section is the generated typed form of ADR-0027, whose rows come from the subcategory's assignments.

## Applicable patterns
Rows from `docs/architecture/PATTERNS.md`:
- "Format or range check": `@assert.format`, `@assert.range` in `srv/annotations/` (R1, R3, R5). The row does not mention `@<anno>.message` and open bounds: ADR-0028 decision 1.
- "Cross-field consistency check": `@assert: (case ...)` with null guards, `exists` set membership, no `@assert.unique` inside a draft tree (R2, R4, R6, R8, R10-R13). Uniqueness across the whole entity through a self-association, the two-target `error()` form, a `$self` value compared inside the infix filter and a rule between two child rows have no row: ADR-0028 decisions 2, 3, 8, 9.
- "Field editable only when another field is filled" (ADR-0025): the dynamic `Common.FieldControl` shape, integer codes, association paths; a conditionally required field that stays editable (`7 : 3`) is a variant with no row: ADR-0028 decision 4.
- "Rows generated from an assignment on a draft" (ADR-0027 decision 3): unchanged under D5 = A.
- "Typed attribute values" (ADR-0027 decision 4): R8, R10, R11, R13 add branches to the same `numberValue` constraint; a value-driven dependency between attributes as a control plus guard (R12) has no row: ADR-0028 decision 10.
- "Reference to another entity": `atLeast` and `enables` are managed associations in `db/schema.cds` (the +28 EDMX each is measured and accepted, research section 10.7).
- "Monetary amount" (`Decimal(15, 2)` + `Currency` + `@Measures.ISOCurrency`): the R4 control adds the code-list customizing the Fiori currency type reads; no row names it: ADR-0028 decision 11 (a control offered by the framework).
- "Bulk create from a file" (ADR-0021): a root constraint is checked at commit and names no row, so every new root constraint gets a per-row pre-check (R4, R6); the row says it for one rule, the ADR generalises it (decision 6); the detail rules need none.
- "Custom section or column" (ADR-0027): the required marker, the range placeholder, the disabled dependent row, the toast and the counter rule in `DetailsForm.js`.
- "Prevent before validate" (the user's principle): ADR-0028 decision 11 adds it to PATTERNS as the rule of every validation task.
- "OData contract": `npx vitest -u` and `metadata.xml` in the same phase as each model change (phases 2 and 3).
- "Texts": message keys in `_i18n/messages*.properties`, labels in `_i18n/i18n*.properties`, app texts in `webapp/i18n/`.

## Relevant lessons
From `docs/LESSONS.md`:
- 2026-10-10: making a field mandatory breaks every writer that omits it: R6's writers are listed in research section 8 and in the plan (tests, fixtures, README); R10's bounds are checked against every seeded value and the journeys' inputs (Battery Life 12 on the mouse, inside MICE 1-2000).
- 2026-10-10: an `@assert` constraint is checked at commit, not per row, so the import maps it only through a per-row pre-check: R4 and R6 get one; the detail rules need none because the import creates no detail rows.
- 2026-10-10: a missing `@mandatory` value hides another field's rule; at activation the input validation hides the constraints (research section 1): the tests assert one kind per request.
- 2026-10-12: decide the mechanisms of a custom fragment at plan time and prove them in a skeleton: the required marker is a `setRequired` on the existing label, the bounds go through the existing `Decimal` type, the disabled row is `setEnabled` plus the proven `setProperty(null)` write; the activation-error mapping onto a custom control is the one unproven piece and has a fallback (plan risks).
- 2026-10-12: a criterion that names a verb is measured for every verb: the plan names active `POST`, active `PATCH`, draft `PATCH`, `draftActivate` and the import per rule.
- 2026-10-09: measure a UI claim before the plan gate: the `additionalTargets` rendering, the client required check of R6, the currency code list of R4 and the stale-message read of V17 are browser-proof items, not promises.
- 2026-10-09: `cds-mcp` `search_model` shows the pre-feature model in a worktree; implementers read `docs/registry/DOMAIN-MODEL.md` after `npm run docs:registry` for `namesakes`, `required`, `minValue`, `maxValue`, `atLeast`, `enables`, `enabledBy`.
- 2026-10-14 (this spec, research section 10.3): an association that starts at an entity outside the draft tree (`DetailAttributes.rows`) reads active rows while the user edits a draft; a rule between draft rows must start at the draft row (`product.details[...]`).
