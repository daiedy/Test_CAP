# Pattern catalogue: one task, one way

For every recurring task there is exactly one approved way here. An agent that meets a task from the table uses the specified way and example. If the way does not fit, work stops and an ADR is created, not a second way. Links to examples point to the current code; the registry in `docs/registry/` shows what already exists. Rows without an example describe a way that has not been applied in this project yet: the first agent that applies such a pattern adds the example path (and the ADR, if one was needed) to the row in the same change, and the reviewer checks it.

## Data model

| Task | Way | Example | Decision |
|---|---|---|---|
| New entity | `entity X : cuid, managed { ... }` in `db/schema.cds`; projection in the service; labels in `srv/annotations/X.cds`; UI in `app/<app>/annotations/X.cds`; data `cds add data --filter X --records N`; test `test/<service>.test.js`. Persistence constraints `@assert.unique` live in `db/` (DDL, not semantics; the one exception to "no annotations in `db/`"), for example `@assert.unique.pair` on an assignment entity; every other `@assert.*` stays in `srv/annotations/` | `db/schema.cds` → `Products`; `SubcategoryAttributes` (`@assert.unique.pair`) | ADR-0003, ADR-0026 (decision 1) |
| Code list with selection from a list | Entity `: sap.common.CodeList` with key `code : String(20)`, `UPPER_SNAKE` codes; association from the main entity; value help: see "Value help from a code list" | `db/schema.cds` → `Categories`, association `Products.category` | ADR-0003, ADR-0010 |
| Internal status not chosen by the user | `enum` in the element type, UPPER_SNAKE values | not in code | |
| Monetary amount | `Decimal(15, 2)` + `currency : Currency` + `@Measures.ISOCurrency: currency_code` | `Products.price` | |
| Calculated value | Calculated element `total : Decimal = price * quantity` in the schema; `virtual` + `after READ` only if the expression is impossible in SQL | not in code | |
| Parent-child relationship (document) | `Composition of many Items on items.parent = $self` in the parent, `parent : Association to Parent` in the children. Facts measured on a draft-enabled root (ADR-0012): the child inherits drafts from the root, so only the root projection carries `@odata.draft.enabled`; a top-level `POST` or `PATCH` to the child answers 422 `DRAFT_MODIFICATION_ONLY_VIA_ROOT` (a viewer's top-level `POST` without `IsActiveEntity` 403 by the grant first); a top-level `DELETE` is not refused by lean draft and is authorized exactly like a `DELETE` through the root: the child's grant, 403 `DRAFT_ACTIVE_DELETE_FORBIDDEN_DRAFT_EXISTS` while the root has a draft; only the target entity of a request is authorized, so each child projection (every composition level) carries its own `@restrict` as the root, which guards reads and active-path writes through the root. A second level (`Products.details.selections`) works the same; activation messages target `in/details(ID=...,IsActiveEntity=false)/selections(ID=...,IsActiveEntity=false)/<fk>` | `Products.details` and `ProductDetails.selections` in `db/schema.cds`, projections in `srv/catalog-service.cds` | ADR-0026 (decision 2), ADR-0027 (decisions 1, 2) |
| Typed attribute values | The type lives on the attribute: `DetailAttributes.valueType` (a `CodeList` of `TEXT`, `INTEGER`, `DECIMAL`, `LIST`, `MULTI_LIST`) plus `minValue`, `maxValue`, `scale`; the value row has one typed column per kind (`textValue`, `numberValue : Decimal(15, 3)` for INTEGER and DECIMAL, `listValue` association to a localized list entity per attribute, `selections` composition child for MULTI_LIST). Rules are `@assert` constraints in `srv/annotations/<Entity>.cds` (column filled only for its type, range, whole number via `floor(x) != x`, list value belongs to the row's attribute, no duplicate selection); non-numbers and more than 3 decimals are the framework's `ASSERT_DATA_TYPE`. Values are optional. On the client the format, decimals and bounds come from a UI5 type (`sap.ui.model.odata.type.Decimal` with `scale` and `minimum`/`maximum` from the attribute), no hand-written regex; server texts have no placeholders (a constraint passes no arguments). No handler checks values | `ProductDetails` and `DetailAttributes` in `db/schema.cds`, `srv/annotations/ProductDetails.cds` | ADR-0027 (decisions 1, 4) |
| Reference to another entity | `Association to Target` in the singular | `Products.currency` | |
| Translatable data texts | `localized String(N)`, CSV `<Entity>.texts` | `Categories.name`, `db/data/my.catalog-Categories.texts.csv` | |

## Service and logic

| Task | Way | Example | Decision |
|---|---|---|---|
| Mandatory field | `@mandatory` in `srv/annotations/<Entity>.cds`; an action parameter the same way (`annotate <Service>.<Entity> with actions { <action>(<param> @mandatory) }`): the `Common.FieldControl: #Mandatory` it emits is the only signal Fiori Elements V4 reads to mark a dialog parameter required and to block an empty submit; `not null` (`Nullable="false"`) alone is ignored by the dialog, and for a file parameter the annotation goes on the parameter, not on the stream element of its type | `srv/annotations/Products.cds`, `importProducts(file)` | ADR-0004, ADR-0021 (amendment B) |
| Format or range check | `@assert.format`, `@assert.range` in `srv/annotations/<Entity>.cds`; a `before` handler only if it cannot be expressed with an annotation; a rule between two fields: see "Cross-field consistency check" | `Products.stock @assert.range: [0, 1000000]` | ADR-0004 |
| Association target existence check | `@assert.target` | `Products.category`, `Products.currency` | |
| Cross-field consistency check | A rule between fields, including fields reached through an association, is an `@assert: (case when <condition> then '<MESSAGE_KEY>' end)` constraint on the element in `srv/annotations/<Entity>.cds`, key in `_i18n/messages.properties` and `_ru`; no handler. Guard every nullable operand explicitly (`<assoc>.code is not null and <parent>.code is not null and ...`): CQL `!=` treats null as a value. The runtime rejects with 400 (key as `code`, the foreign key as `target`) on active writes, writes a draft message on a draft PATCH and rejects `draftActivate` with target `in/<fk>`; the draft message is written at commit, so it shows on the next `GET`, not in the PATCH response. The constraint is checked at commit, so the row mapping of `importProducts` never sees it: an import column for the field checks the rule per row before the inserts, see "Bulk create from a file". Set membership between a child row and a code list is the same form with `exists <to-many>[... $self.<path>]` (`$self` is the annotated entity inside an infix filter); a duplicate inside a draft tree is `exists <parent>.<children>[<key> = $self.<key> and ID != $self.ID]`, never `@assert.unique` (a violation is a 500 `ERR_SQLITE_ERROR` with `@cap-js/sqlite` and nothing on a draft) | `Products.subcategory` in `srv/annotations/Products.cds` (`PRODUCTS_SUBCATEGORY_MISMATCH`); `ProductDetails.attribute` in `srv/annotations/ProductDetails.cds` (`PRODUCTS_DETAIL_ATTRIBUTE_NOT_ASSIGNED`, `PRODUCTS_DETAIL_ATTRIBUTE_DUPLICATE`) | ADR-0024 (decision 2, amendment), ADR-0026 (decision 5) |
| Dependent field reset on a draft | `this.before('PATCH', <Entity>.drafts, ...)` in `srv/<name>-service.js` sets the dependent foreign key to `null` when the PATCH changes the parent key, does not carry the dependent one and the stored dependent value does not belong to the new parent (one `SELECT.one` on the code list); silent, no `req.reject`; active writes are not reset, the consistency check rejects there. In `app/<app>/annotations/<Entity>.cds` a `Common.SideEffects #<Parent>Changed` with `SourceProperties: [ <parent fk> ]` and `TargetProperties: [ '<dependent fk>', '<dependent assoc>/name' ]` makes Fiori Elements re-read the field and its text | `resetStaleSubcategory` in `srv/catalog-service.js`, `Common.SideEffects #CategoryChanged` in `app/products/annotations/Products.cds` | ADR-0024 (decision 3) |
| Rows generated from an assignment on a draft | When the child rows of a draft root follow an assignment (here the attributes assigned to the subcategory), extend the existing `this.before('PATCH', <Root>.drafts, ...)` registration, never add a second one: after the reset, when the PATCH carries a non-null parent key, keep the rows whose attribute is still assigned (values and children unchanged, new `position`), delete the others (their children cascade) and insert one empty row per missing assigned attribute into `<Child>.drafts` with the parent's `DraftAdministrativeData_DraftUUID`. When removed rows held a value, `req.warn` with the number and the localized names (read names with `SELECT.localized`: a handler's SELECT is not localized); the warning lives only in the `sap-messages` header of the PATCH, it is not a draft message. A `null` key keeps the rows. `this.after('EDIT', <Root>, ...)` fills the missing rows of the new draft. Active writes are never reconciled: the constraint (`PRODUCTS_SUBCATEGORY_HAS_FOREIGN_DETAILS`) rejects them. Pair it with `Common.SideEffects #<Parent>Changed` with `TargetEntities: [ <composition> ]` so FE re-reads the section | `reconcileDetailRows` and `fillDetailRows` (`after('EDIT')`) in `srv/catalog-service.js`, `Common.SideEffects #SubcategoryChanged` in `app/products/annotations/Products.cds` | ADR-0027 (decision 3) |
| Read-only | `@readonly` on the projection in the service | | |
| Authorization | `@requires: 'authenticated-user'` on the service, `@restrict` on the entity; mock users in `package.json` → `cds.requires.auth.users`. Entity grants cover the draft actions too (`draftEdit`, `draftPrepare`, `draftActivate`, discard need the same `grant`); UI tests authenticate via `app/<app>/ui5-test-runner.json`. A composition child projection needs its own `@restrict` with the root's grants: without it a viewer creates a child through `POST <Root>(...)/<composition>` (201) and a user without a catalog role reads the child set (measured, ADR-0026) | `srv/catalog-service.cds` | ADR-0013, ADR-0026 (decision 2) |
| Role-aware UI visibility | A read-only singleton `<Service>.Permissions` (`@odata.singleton @cds.persistence.skip @readonly`) served by an `on('READ')` handler in `srv/<name>-service.js` returning `req.user.is('<Role>')`; the UI reads it via `UI.CreateHidden`/`UI.UpdateHidden`/`UI.DeleteHidden` in `app/<app>/annotations/<Entity>.cds`, each `{ $edmJson: { $Not: { $Path: '/Permissions/<flag>' } } }`; a `DataFieldForAction` record in `UI.LineItem` reads the same expression as `![@UI.Hidden]` on the record itself, a fourth consumer next to the three `UI.*Hidden` terms. Write the short absolute path `/Permissions/<flag>`: the container-qualified form `/<Service>.EntityContainer/Permissions/<flag>` also works and hides the same actions, but trips an unguarded UI5 `TypeError` (`_Helper.aggregateExpandSelect`) once when the Object Page opens (measured on 1.152.0 and 1.153.0; 0 occurrences with the short path, ADR-0013 amendment). A per-row element cannot answer this in a List Report toolbar (no row context, none at all on an empty list), so the singleton is the only mechanism. The mock fixture `mockdata/Permissions.json` is a one-element array like every mock file (an object form throws on the `$batch` path). Verify List Report and Object Page separately: an unresolved `$Not` binding defaulted to visible on one and hidden on the other (measured 2026-09-16) | `srv/catalog-service.js`, `app/products/annotations/Products.cds` (`UI.*Hidden`, ADR-0013; `importProducts`'s `UI.Hidden`, feature `products-excel-upload`, ADR-0021) | ADR-0013, ADR-0021 |
| Action on a single record | Bound action in the projection: `actions { action reorder(amount: Integer) }`; handler `this.on('reorder', 'Products', ...)`; in the UI `DataFieldForAction` | not in code, template `templates/service.cds` | |
| Action on a set or without context | An action bound to the collection, `action <name>(in: many $self, ...) returns ...` inside the projection's `actions`, is the bound variant for a set and inherits the entity's `@restrict`; unbound `action` in the service only if a bound one is impossible | `importProducts` in `srv/catalog-service.cds` (feature `products-excel-upload`) | ADR-0021 (decision 2) |
| File upload through an action | A structured action parameter of a service type with `content: LargeBinary @Core.MediaType: mediaType`, `mediaType: String(100) @Core.IsMediaType`, `fileName: String(255) @Core.ContentDisposition.Filename: fileName`, and `@Core.AcceptableMediaTypes` on `content` restricting the format — the shape Fiori Elements V4 documents for a file upload action parameter. A body-size limit only bounds what travels over HTTP, not what an archive unzips to: guard the unzipped size by counting inflated bytes with `node:zlib` before the parsing library reads the file, and reject above the limit before any parsing | `CatalogService.ProductsImportFile` (`srv/catalog-service.cds`); `unzippedSize`/`MAX_UNZIPPED_BYTES` in `srv/lib/products-import.js` (feature `products-excel-upload`) | ADR-0021 (decisions 1, 2, 7; amendment D) |
| Bulk create from a file | Parse the file into rows with a small library run on the server, no `req`, in `srv/lib/<topic>.js`; create each row with its own `INSERT` inside the action's transaction so the per-row `@mandatory`/`@assert.*` checks fire and attribute their error to a row number; collect every row's error with the object form of "Business logic error" so the request is all-or-nothing and the transaction rolls back on any failure. An `@assert: (case ...)` constraint is checked at commit (`req.before('commit')` of the root transaction), not per row, so a per-row `INSERT` cannot report it: a cross-field rule is checked per row before the inserts (one `SELECT` for the file's codes, the same reason texts, rows with an empty or unknown operand left to `@mandatory`/`@assert.target`) and the constraint stays as the guard | `srv/lib/products-import.js`, `on('importProducts', Products)` in `srv/catalog-service.js` (feature `products-excel-upload`); the per-row pre-check `subcategoryMismatches` in `srv/catalog-service.js` (feature `products-subcategory-cascade`) | ADR-0021 (decisions 1, 3, 4; amendment 4 E) |
| Business logic error | `req.reject(400, 'KEY', [args])` for a single error, key in `_i18n/messages.properties`; when a handler collects several messages into one response, use the object form `req.error({ status, code: 'KEY', args })` per message instead — cds 10.0.6 (`@sap/cds/lib/req/response.js`, `lib/srv/protocols/http.js`) rewrites `code` to the key only for the top-level error of `req.reject`/a single `req.error`, so a collected detail keeps the numeric status in `details[].code` unless it is given its own `status` | `templates/handler.js`; `rejectImport` in `srv/catalog-service.js` (feature `products-excel-upload`, several collected `PRODUCTS_IMPORT_*` messages) | ADR-0021 (decision 4) |
| Success message of an action | `req.info({ code: 'KEY', message: cds.i18n.messages.at('KEY', req.locale, args), args })`: cds 10.0.6's OData `sap-messages` header resolves a message key only in `i18n.default_language` (`ODataAdapter.sap_messages4` calls `normalized()`, never `localized()`), so a success message that must appear in the caller's language is localized by hand before it reaches `req.info` | `srv/catalog-service.js` `PRODUCTS_IMPORT_DONE` (feature `products-excel-upload`) | ADR-0021 (decision 4) |
| Logging | `const LOG = cds.log('catalog')`; `LOG.info`, `LOG.warn`, `LOG.error` | `templates/handler.js` | |
| Shared function for several handlers | `srv/lib/<topic>.js`, named export, JSDoc by the rule set of "JSDoc requirement and gate", unit test; check `docs/registry/REUSE-CATALOG.md` before creating | `srv/lib/products-import.js` (feature `products-excel-upload`, first `srv/lib` module) | ADR-0021 |
| Description of an entity, element, action or type | A description is a CDS doc comment (`/** ... */`), one English sentence for the API consumer, never `@description`, `@Core.Description` or `@Core.LongDescription`. Placement: a projection and its elements in `srv/annotations/<Entity>.cds` (one comment above `annotate <Service>.<Entity> with {`, one above each element next to its `@title`); the service, an action and its parameters, a service-level type and its elements, a singleton at their definition in `srv/<name>-service.cds`; a `db/` entity may carry a developer-note doc comment, its elements none; a developer note in `srv/*.cds` that is not an API description is a `//` comment. The switch is `cds.cdsc.docs: true` in `package.json`, no command passes `--docs`. The service header carries `@protocol: 'odata-v4'`, `@title`, `@Core.SchemaVersion` (bumped together with `package.json` `version`). Descriptions are English literals, the recorded exception to "texts through i18n" | `srv/annotations/Products.cds`, `srv/catalog-service.cds` (header, `importProducts`), templates `annotations-semantic.cds`, `service.cds`, `entity.cds` | ADR-0029 (decisions 1-3) |
| Drafts | `@odata.draft.enabled` only on the root projection of the FE application that edits the data; never on the parent and the children of a composition at the same time; non-Fiori clients and tests address active data explicitly with `IsActiveEntity=true` | `CatalogService.Products` (`srv/catalog-service.cds`) | ADR-0012 FE V4 facts (verified 2026-09-07): shell or browser Back with a persisted draft change opens the Save / Keep Draft / Discard Draft dialog; without a `Common.SemanticKey` the List Report shows no draft or lock marker in the row (Editing Status filter and the Object Page lock popover still work), until `@Common.SemanticKey` is set (ADR-0015). |
| Side effect after write | `this.after('CREATE', 'Entity', ...)` or an `srv.emit` event; no manual transactions | | |
