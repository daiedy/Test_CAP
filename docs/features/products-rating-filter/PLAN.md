Shape (ADR-0018): one criterion per line under "Acceptance criteria", table rows only under "Steps"; explanations belong in `CONTEXT.md` or `research/`. `node scripts/check-feature-docs.mjs <name>` verifies the shape at the phase 1 gate.

Contract rule: a step that changes the OData model (`db/*.cds`, `srv/**/*.cds`, `app/*/annotations/*.cds`) schedules `npx vitest -u` and `cds compile '*' --to edmx-v4 -s CatalogService -l en > app/products/webapp/localService/metadata.xml` in the same phase, never in a later one; the sync test in `test/metadata.test.js` turns red at that phase's gate otherwise (PATTERNS "OData contract").

This plan follows the user's answers of 2026-09-25 (CONTEXT "User decisions"): RangeSlider (ADR-0020), 0..5 step 1, slider only, `liveMode: true` together with this feature. **The OData contract is untouched in every phase**: no step edits `db/`, `srv/` or `app/*/annotations`, so neither `npx vitest -u` nor the `metadata.xml` regeneration is scheduled; the gate figure for `test/__snapshots__/metadata.test.js.snap` and `app/products/webapp/localService/metadata.xml` is "no line in `git diff --numstat main`" at phases 2 and 3 (`liveMode` is a `manifest.json` page setting, not part of `$metadata`).

## Acceptance criteria
- [ ] The List Report filter bar shows a Rating filter after Price as a `sap.m.RangeSlider` from 0 to 5 with step 1, both handles at 0 and 5 on first load, verified by OPA5 "The rating filter is a slider from 0 to 5 labelled Rating" (`RatingRangeFilterJourney.js`).
- [ ] On first load the filter bar holds no condition for `rating` (`sap.ui.mdc.FilterBar#getConditions().rating` empty) and the table shows 15 rows, verified by the same OPA5 test.
- [ ] Setting the range to 4..5 shows 8 rows, all with rating 4 or 5, with no Go press (`liveMode`), verified by OPA5 "Rating 4 to 5 shows 8 products".
- [ ] Setting the range to 2..4 shows 9 rows with no Go press, verified by OPA5 "Rating 2 to 4 shows 9 products".
- [ ] The rating range combines with the category filter (KITCHEN and 5..5 give 2 rows, no Go press), verified by OPA5 "The rating range combines with the category filter".
- [ ] Moving the slider back to 0..5 removes the `rating` condition and shows 15 rows again with no Go press, verified by OPA5 "The full range removes the rating filter".
- [ ] The filter label is the `Products.rating` text in `en` and `ru` (`RatingTexts.labels`), verified by OPA5 "The rating filter is a slider from 0 to 5 labelled Rating" and the `ru` assertion added to `RussianLocaleJourney.js`.
- [ ] Adapt Filters lists Rating once (the slider), with no second standard `rating` condition field, verified by OPA5 "Adapt Filters offers the rating slider only".
- [ ] The mapping from a slider range to a condition returns `BT [lo, hi]` for a band and "clear" for 0..5, verified by QUnit "toCondition maps a band to BT and the full range to clear" (`webapp/test/unit/RatingRangeFilter.qunit.js`).
- [ ] The display formatter turns an empty or out-of-range value into a range inside 0..5, verified by QUnit "formatRange keeps the slider inside 0..5".
- [ ] The List Report filter bar has no Go button (`liveMode: true` on `ProductsList`), verified by OPA5 "The List Report applies filters without a Go button" (mdc FilterBar `getLiveMode()` true, no visible search button; ids measured).
- [ ] The 5 `iExecuteSearch()` calls in `FilterProductsByCategoryJourney.js` (2), `DraftMarkerInListReportJourney.js` (2) and `RussianLocaleJourney.js` (1) are replaced by a wait for the table, no `iExecuteSearch` is left under `webapp/test/`, and `npm run test:ui` reports all 28 previous `opaTest`s plus the new ones passed, 0 skipped.
- [ ] `manifest.json` was changed only through Fiori MCP `execute_functionality`, recorded in `research/fiori-mcp-custom-filter.md` with the functionality id and parameters.
- [ ] OData contract unchanged: `git diff --numstat main` has no line for `test/__snapshots__/metadata.test.js.snap` or `app/products/webapp/localService/metadata.xml`, and `npm test` is green (69 tests).
- [ ] `ui5lint` reports 0 problems and `npm run lint:js` 0 errors in `app/products` (the known `Component.js` timeout warning excepted).
- [ ] Measured on `npx cds serve --in-memory --port 4004`: the first `Products` request carries no `rating` in `$filter`, setting 4..5 sends `rating ge 4 and rating le 5` on the handle's release without a Go press, and the console shows no RangeSlider "not in the range" warning, recorded in `research/custom-filter-mechanism.md` section 8 and in `VERIFICATION.md`.
- [ ] `ui-verifier` confirms in a browser: mouse drag and keyboard (arrow keys on a handle) change the range and the table reloads without Go, a saved variant restores the range and the rows, `viewer` gets the same filter, `ru` label, mock mode filters too.
- [ ] `ui-verifier` confirms in a browser (en and ru, `alice` and `viewer`): no Go button in the List Report filter bar, and a change of Name, Category, Price, Editing Status or Rating reloads the table once per change (one `Products` request per change in the network log), recorded in `VERIFICATION.md`.
- [ ] ADR-0020 accepted and `PATTERNS.md` has the row "Custom filter field" with this feature as the example; `CONVENTIONS.md` names `ext/fragment/<Name>.js`.

## Decisions that require an ADR
- Custom filter field in the FE V4 filter bar (no PATTERNS row): `docs/decisions/ADR-0020-custom-filter-field.md`, accepted by the user 2026-09-25; `liveMode` needs no ADR (manifest page setting, pattern "Manifest change").

## Risks
- The Fiori MCP functionality for a custom filter may not exist in `fiori-mcp` 1.12.2 or may generate another shape (for example a custom operator handler): step 3 records it before any edit; no functionality means stop and ask, generated JS/XML is adapted by hand to ADR-0020, the manifest never.
- The one-way display binding with `Range` type plus `formatter` is predicted from source, not measured; detection: step 4 measurement (slider shows the condition after a variant switch and after a filter change) and `ui-verifier` variant scenario. If the display does not follow the condition, the formatter reads the conditions instead; that is a change of ADR-0020 before acceptance, not a silent variant.
- The label fallback to `Common.Label` is read from the converter source; detection: step 4 (en/ru on :4004) and the OPA5 label assertions. If it fails, add `ProductsList.ratingFilter.label` in `webapp/i18n/i18n.properties`, `i18n_en.properties` and `i18n_ru.properties` in step 4 and set `label` through `execute_functionality`.
- `sap.fe.test` has no API for a custom filter control, and FE ids of the wrapper are unknown ahead of rendering; detection: `test-ui` probes ids with a failing assert (its memory), never guesses.
- A programmatic `setRange` + `fireChange` in OPA5 bypasses pointer handling; covered by `ui-verifier` (mouse drag and arrow keys).
- A leftover draft or a saved variant changes row counts; the journey saves no variant, runs before `DraftMarkerInListReportJourney`, and restores the full range before teardown.
- `docs/registry/UI-ARTIFACTS.md` lists the `ext/` files but not the manifest wiring; the reviewer checks the manifest by diff.
- Products with `rating` null (possible, `rating` is not mandatory) must not vanish without a rating filter; covered by `toCondition` clearing on 0..5 (QUnit) and the first-load criterion.
- `liveMode` reloads on every filter change: a drag must fire `change` only on the handle's release (`RangeSlider` `change` vs `liveChange`, predicted) and the Name field only on Enter or leave; detection: step 4c network log (one `Products` request per change) and `ui-verifier`. A request per keystroke or per drag pixel is a defect of step 4, reported, not tuned silently.
- Without `iExecuteSearch` an OPA5 row assertion could pass on the stale table if the expected count equals the count before the change; step 6a keeps only waits whose count differs from the previous state (all 5 do today), and the new journey follows the same rule.
- Between step 4c and step 6a the 3 existing journeys are red by design (no Go button to press); both steps belong to the orchestrator's UI phase (`fiori-app-dev`, then `test-ui`), whose single commit is made only after `npm run test:ui` is green with step 6a done.
- `FE_FilterSearch` (Ctrl+Enter) is not registered with `liveMode` (research section 5); `SCREENS.md` keyboard text is updated by `ux-designer` accordingly.
