# Categories as a code list with value help: plan

Date: 2026-09-07. Status: done (2026-09-07, `docs-keeper`, step 17; review: "ready to commit" without blocking findings). Gate mode: semi-autonomous.

Context and research: `CONTEXT.md` in this directory, including the "Screens" section by `ux-designer`. Feature name `categories-code-list`, branch `feature/categories-code-list`. First run of the `/feature` pipeline: phases and commits per the `feature` skill, agent reports per the protocol, section 7. The user decisions of 2026-09-07 (relayed by the orchestrator) and the designer's additions have been incorporated; phase 2 starts from this version.

## Key plan decisions

| Question | Decision | Rationale |
|---|---|---|
| Field name and form | `category : Association to Categories` in `Products`; the foreign key `category_code : String(20)` is generated by the compiler | Patterns "Code list with selection from a list" and "Reference to another entity"; the name `category` is kept so that the UI annotations and tests change minimally. The OData contract changes deliberately: the property `category` (Edm.String 50) is replaced by `category_code` (Edm.String 20) plus the NavigationProperty `category`; the snapshot `test/__snapshots__/metadata.test.js.snap` is updated via `npx vitest -u` with an entry in CHANGELOG. The only consumer of the contract is `app/products` |
| Where `Categories` lives | `db/schema.cds`, namespace `my.catalog` | Same domain area; a separate module `db/<module>.cds` per CONVENTIONS is needed only for a new domain |
| Exposure of `Categories` | explicit projection `@readonly entity Categories as projection on catalog.Categories;` in `CatalogService` | Pattern "Read-only"; an autoexposed entity cannot be annotated in `srv/annotations` (lesson "Titles live on the projection"); one projection per entity |
| Validation | `@mandatory` stays, `@assert.target` is added on `category` | Pattern "Association target existence check"; no handler needed |
| Code list codes | `ACCESSORIES`, `ELECTRONICS`, `FURNITURE`, `KITCHEN`, `SPORTS`, `STATIONERY` (UPPER_SNAKE, `String(20)`) | ADR-0010, accepted 2026-09-07 |
| Code list data | `db/data/my.catalog-Categories.csv` (`code;name`, en, rows in alphabetical order of the English names) and `db/data/my.catalog-Categories.texts.csv` (`code;locale;name`, only `ru`); `descr` is not filled | Pattern "Translatable data texts", rule `data.md` (separator `;`). The files are created with `cds add data --filter Categories --records 6`, then normalized: the generator writes `,` and random locales (verified in CONTEXT). Alphabetical order at the request of `ux-designer`: the generated ValueList has no sorting, the list arrives in server order |
| Existing products | In `my.catalog-Products.csv` the column `category` is renamed to `category_code`, the values are replaced with codes per the table below; the IDs and the other columns are not touched | Rule `data.md`: foreign key `<assoc>_<key>`, reference consistency |
| Value help: source | `Common.ValueList` is not written by hand: the compiler generates it from the `@cds.odata.valuelist` aspect of CodeList (this is how `currency_code` already works). The old ValueList block with `CollectionPath: 'Products'` is removed | ADR-0011 part 1, accepted 2026-09-07; verified by compilation (CONTEXT) |
| Value help: presentation | On the association `Products.category` in `app/products/annotations/Products.cds`: `Common.Text: category.name`, `Common.TextArrangement: #TextOnly`, `Common.ValueListWithFixedValues: true` (dropdown: multi-select in the filter, single-select in the form; no dialog) | ADR-0011 part 2, accepted 2026-09-07; the designer's rationale in CONTEXT "Presentation decision" |
| Text of the list items | New file `app/products/annotations/Categories.cds`: on `CatalogService.Categories.code` the annotations `Common.Text: name`, `Common.TextArrangement: #TextOnly`; the line `using from './annotations/Categories';` in `app/products/annotations.cds` | Mandatory addition by `ux-designer`: for `sap.common.Currencies` the `@Common.Text: name` is set on `code` in the definition itself in `@sap/cds/common`, the `CodeList` aspect does not provide this, so without the annotation the dropdown would show `ELECTRONICS` rather than "Electronics". Recorded in ADR-0011 |
| Where `category_code` is in the UI | `UI.SelectionFields`, `UI.LineItem`, `UI.HeaderInfo.Description`, `UI.FieldGroup#GeneralInfo`: `category` is replaced with `category_code` everywhere | As in `templates/annotations-ui.cds`; TextOnly shows the name in all places |
| Labels | `Products.category` = "Category" / "Категория" (exists); `Categories.code` = "Category" / "Категория"; `Categories.name` = "Category Name" / "Название категории"; `Categories.descr` = "Category Description" / "Описание категории" | User decision 5: the header "Category Code" above a column of names would be misleading |
| Code list page | not created, `manifest.json` is not changed | Confirmed by `ux-designer`: the code list is `@readonly`, maintained via CSV; Fiori MCP `list_functionality`/`execute_functionality` are not needed |
| Mock mode | `localService/metadata.xml` is regenerated; `mockdata/Categories.json` (6) and `mockdata/Categories_texts.json` (6 `ru` records) are added; `mockdata/Products.json` is moved to `category_code` and synchronized with the 15 CSV records | User decision 4; patterns "metadata.xml snapshot update", "UI without backend"; closes the STATE debt "mock data not synchronized" |
| Backend tests | `test/catalog-service.test.js`, `test/metadata.test.js`; a fallback is added to the localization test (`Accept-Language: de` → English name) | Patterns "Service test", "OData contract"; addition by `ux-designer` |
| UI tests | In this feature (step 13, `test-ui`): `@sap-ux/ui5-test-writer` and `ui5-test-runner` in the devDependencies of `app/products`, Test Starter, OPA5 journeys on `sap.fe.test.ListReport`/`ObjectPage`, running `ui5-test-runner` against the live stack (`npm run watch` + `npm start`) | User decision 3; closes the STATE debt "no UI tests". Mock mode is not used for the journeys: `metadata.xml` is built with `-l en`, `sap-fe-mockserver` ignores `Accept-Language`, the `ru` scenario is not verifiable there |
| Handlers | not added | Everything is expressed with annotations and `localized` |

### Step details for developers

Step 3, `db/schema.cds`. The import is extended to `using { cuid, managed, Currency, sap.common.CodeList } from '@sap/cds/common';`. An entity is added with a doc comment, like `Products`:

```cds
/** Product category, user-facing code list. Labels: srv/annotations/Categories.cds */
entity Categories : CodeList {
  key code : String(20);
}
```

In `Products` the line `category : String(50);` is replaced with `category : Association to Categories;`. There are no annotations in `db/`.

Step 4, data. After `cds add data --filter Categories --records 6` both files are brought to the form: separator `;`, only the columns `code;name` and `code;locale;name`, values from the migration table, rows in the order of the table (alphabet of the English names), only the `ru` locale in the texts (the generator creates random locales and `,`). In `my.catalog-Products.csv` the header `category` → `category_code`, values per the migration table; row order and IDs are preserved.

Step 5, `srv/catalog-service.cds`. `@readonly entity Categories as projection on catalog.Categories;` is added to the service after `Products`; `using from './annotations/Categories';` at the end of the file. Nothing else appears in the service file.

Step 6, semantics. `srv/annotations/Products.cds`: the `category` line gets `@assert.target` next to `@mandatory`, the title does not change. The new `srv/annotations/Categories.cds` contains only `annotate CatalogService.Categories with { code @title: '{i18n>Categories.code}'; name @title: '{i18n>Categories.name}'; descr @title: '{i18n>Categories.descr}'; };`. The i18n keys from the table above go into both `_i18n` files.

Step 7, tests. Test names and expectations from the acceptance criteria. Request with a locale: `GET(url, { headers: { 'Accept-Language': 'ru' } })`; the same test makes three requests (`ru`, `en`, `de`) and checks "Кухня", "Kitchen", "Kitchen". The contract change in the snapshot is recorded in CHANGELOG with the words "`Products.category` (String 50) replaced with `category_code` (String 20) and the navigation `category`; entity sets `Categories`, `Categories_texts` added".

Step 9, `Products` UI annotations. In `app/products/annotations/Products.cds`: in all four places (`HeaderInfo.Description`, `SelectionFields`, `LineItem`, `FieldGroup#GeneralInfo`) `category` → `category_code`; the block `annotate CatalogService.Products with { category @Common.ValueList: { CollectionPath: 'Products', ... } }` is replaced with

```cds
annotate CatalogService.Products with {
  // Category is a fixed code list: dropdown with localized names, never the code.
  // Common.ValueList is generated by the compiler from sap.common.CodeList (ADR-0011).
  category @(
    Common.Text                     : category.name,
    Common.TextArrangement          : #TextOnly,
    Common.ValueListWithFixedValues : true
  );
};
```

`FilterRestrictions`, `FilterDefaultValue`, `UI.Criticality` are not added (decision of `ux-designer`).

Step 10, `Categories` UI annotations. New file `app/products/annotations/Categories.cds` per `templates/annotations-ui.cds` (the target is always the service projection):

```cds
using { CatalogService } from '../../../srv/catalog-service';

// Presentation of the Categories code list in dropdowns and value help: localized name, never the code (ADR-0011).
annotate CatalogService.Categories with {
  code @(
    Common.Text            : name,
    Common.TextArrangement : #TextOnly
  );
};
```

`using from './annotations/Categories';` is added to `app/products/annotations.cds`. There are no other annotations (`@UI.*`) for `Categories`: the code list has no page.

Step 11, mock. `Categories.json`: an array of 6 objects `{ "code", "name", "descr": null }` in the order of the migration table. `Categories_texts.json`: 6 objects `{ "code", "locale": "ru", "name", "descr": null }`. `Products.json`: 15 objects per the CSV (ID, name, description, price as a string, currency_code, stock, category_code, imageUrl from the CSV, managed fields as now).
