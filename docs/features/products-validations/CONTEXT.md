# products-validations: context

Date: 2026-10-13. Author: `architect`. Branch: `spec/products-validations` (feature branch `feature/products-validations` at implementation). Issue #10.

This file is the brief for the implementers: every agent of the feature reads it whole (protocol step 1), so it holds only the sections below (ADR-0018). Screens go to `SCREENS.md` (`ux-designer`). Experiments, measurements, rejected mechanisms and framework facts are in `research/validation-facts.md`, read by `architect` and `reviewer` unless a plan step names it.

## Request
Issue #10: Object Page validations, through annotations where possible. The user's addition at `/spec` start: come up with logical constraints for all fields, including the typed details of feature #9; not every field needs one; the point is a set of not-so-ordinary validations that show what the project can do. So the deliverable is a showcase: every rule has a domain reason in a product catalog, together they cover what CAP and Fiori Elements V4 do declaratively (format, open range, association data, cross-field with two targets, conditional requirement, set membership on the details), with a handler only where an annotation cannot express the rule, and with messages that explain the reason, in `en` and `ru`.

## User decisions
None yet; the plan-gate questions are in "Open questions". Standing decisions that shape the design: semantics in `srv/annotations/`, presentation in `app/products/annotations/` (ADR-0004); `@assert: (case ...)` constraints before handlers (ADR-0024 decision 2); persistence `@assert.unique` only in `db/` and never for a user-facing rule on a draft entity (ADR-0026 decision 1, TESTING); the Details section is the generated typed form of ADR-0027, whose rows come from the subcategory's assignments.

### Rule catalogue

Mechanism, timing and target per candidate. "Draft PATCH" = the message appears after the field change in edit mode; "Save" = at `draftActivate`; "commit" = active API writes. Target "field" = Fiori Elements puts the message on the field (value state plus message popover entry); "popover" = message popover only. Facts: `research/validation-facts.md` section 1.

|---|---|---|---|---|---|---|
| R1 | `Products.name` | At least 3 characters after trimming: one- or two-letter names are not searchable product names | `@assert.format: '^\s*\S.+\S\s*$'` + `@assert.format.message: 'PRODUCTS_NAME_TOO_SHORT'` (regex trick for a minimum length, the issue's hint) | draft PATCH (in the PATCH response), Save, commit; code `ASSERT_FORMAT` | field | recommended |
| R2 | `Products.name` | Unique in the catalog, case-insensitive and trimmed: "Backpack" and "backpack " are the same listing; the import already refuses duplicates, the UI does not | `@assert: (case when name is not null and exists namesakes then 'PRODUCTS_NAME_DUPLICATE' end)` over the new self-association; never `@assert.unique` (500 on SQLite, silent on drafts) | draft PATCH when `name` is touched (next `DraftMessages` read), Save, commit | field | recommended |
| - | `Products.name` | mandatory | `@mandatory` | Save, commit | field | exists |
| R3 | `Products.price` | Strictly positive: a catalog has no free products, 0 is a data entry error | `@assert.range: [(0), 99999999.99]` (open lower bound) + `@assert.range.message: 'PRODUCTS_PRICE_POSITIVE'`; code stays `ASSERT_RANGE` | draft PATCH (in the response), Save, commit | field | recommended |

| - | `Products.price` | mandatory, currency unit | `@mandatory`, `@Measures.ISOCurrency` | | | exists |
| R5 | `Products.imageUrl` | `https://` and no whitespace: the header image is loaded by the browser, mixed content is blocked and a space breaks the URL | `@assert.format: '^https://\S+$'` + `@assert.format.message: 'PRODUCTS_IMAGE_URL_HTTPS'` | draft PATCH (in the response), Save, commit; code `ASSERT_FORMAT` | field | recommended |

## Applicable patterns
Rows from `docs/architecture/PATTERNS.md`:
- "Format or range check": `@assert.format`, `@assert.range` in `srv/annotations/` (R1, R3, R5). The row does not mention `@<anno>.message` and open bounds: ADR needed (ADR-0028 decision 1).
- "Cross-field consistency check": `@assert: (case ...)` with null guards, `exists` set membership, no `@assert.unique` inside a draft tree (R2, R4, R6-R8). Uniqueness across the whole entity through a self-association and the two-target `error()` form have no row: ADR needed (ADR-0028 decisions 2 and 3).
- "Field editable only when another field is filled" (ADR-0025): the dynamic `Common.FieldControl` shape, integer codes, association paths; a conditionally required field that stays editable (`7 : 3`) is a variant with no row: ADR needed (ADR-0028 decision 4).
- "Rows generated from an assignment on a draft" (ADR-0027 decision 3): unchanged under D5 = A; under D5 = B the copied column extends it.
- "Typed attribute values" (ADR-0027 decision 4): R8 adds the required branches to the same constraints.
- "Bulk create from a file" (ADR-0021): a root constraint is checked at commit and names no row, so every new root constraint gets a per-row pre-check (R4, R6, R7); the row says it for one rule, the ADR generalises it (decision 6).
- "Custom section or column" (ADR-0027): the required marker in `DetailsForm.js`.
- "Business logic error", "Shared function for several handlers": R9's handlers and lib function; a handler-based validation on a draft child has no row: ADR needed (ADR-0028 decision 7, only if R9 is chosen).
- "OData contract": `npx vitest -u` and `metadata.xml` in the same phase as each model change (phases 2 and 3).
- "Texts": message keys in `_i18n/messages*.properties`, labels in `_i18n/i18n*.properties`.

## Relevant lessons
From `docs/LESSONS.md`:
- 2026-10-10: making a field mandatory breaks every writer that omits it: R6's writers are listed in research section 8 and in the plan (tests, fixtures, README).
- 2026-10-10: an `@assert` constraint is checked at commit, not per row, so the import maps it only through a per-row pre-check: R4, R6, R7 get one.
- 2026-10-10: a missing `@mandatory` value hides another field's rule; at activation the input validation hides the constraints (research section 1): the tests assert one kind per request.
- 2026-10-12: decide the mechanisms of a custom fragment at plan time and prove them in a skeleton: the required marker is a `setRequired` on the existing label, the messages use the proven `requestDraftMessages` path; the activation-error mapping onto a custom control is the one unproven piece and has a fallback (plan risks).
- 2026-10-12: a criterion that names a verb is measured for every verb: the plan names active `POST`, active `PATCH`, draft `PATCH`, `draftActivate` and the import per rule.
- 2026-10-09: measure a UI claim before the plan gate: the `additionalTargets` rendering is a browser-proof item, not a promise.
- 2026-10-09: `cds-mcp` `search_model` shows the pre-feature model in a worktree; implementers read `docs/registry/DOMAIN-MODEL.md` after `npm run docs:registry` for `namesakes` and `required`.

## Open questions
Decisions for the user at the plan gate (D1-D3 are the issue's questions):
- D1 Rule list: the recommended set is R1-R6 and R8; R7 and R9 are optional. Cut or add? (Fields without a sensible rule: stock, rating, currency, category, subcategory, the managed fields.)
- D2 Message texts: recommended custom texts per rule (the keys above) through `@assert.format.message` / `@assert.range.message` and constraint keys; the cds defaults stay for `@mandatory`, `@assert.target` and the existing stock and rating ranges. Alternative: override `ASSERT_RANGE` / `ASSERT_FORMAT` globally in `_i18n/messages.properties` (one text for every field).
- D3 Timing: the framework gives format and range messages in the PATCH response and constraint messages right after the field change through the `DraftMessages` read, `@mandatory` only at Save (research section 1). Recommended: accept that; no handler for typing feedback except R9, whose draft `PATCH` rejection is the typing feedback by design.
- D4 R6 condition: `stock > 0` (recommended, in stock = on sale) changes `newProduct` in the tests, `generatedRow` in the fixtures and the README. Alternative with no writer impact but a weaker reason: required when `rating > 0`.
- D5 R8 source of the required flag: A (recommended) the constraint and the form read the assignment (`exists attribute.subcategories[... and required = true]`, `$expand=attribute($expand=subcategories($select=subcategory_code,required))`), no handler change, no stale copy; B a `ProductDetails.required` column copied by the draft handler like `position` (+5 EDMX, handler and test changes, simpler form code).
- D6 Required assignments: `LAPTOPS/SCREEN_SIZE`, `MICE/DPI`, `SEATING/MAX_LOAD`, `APPLIANCES/POWER`, `APPLIANCES/CAPACITY`, `DRINKWARE/CAPACITY`, `FITNESS/THICKNESS` (every seeded product of these subcategories is filled, the journeys never save into them). Confirm or change.
- D7 Import: per-row pre-checks for R4, R6, R7 as pure functions in `srv/lib/products-import.js` (recommended, the ADR-0021 amendment 4 E shape); alternative: accept a commit-time error without a row number for those three rules.
- D8 `error()` with two targets (R4, R6): a source-level API of `@cap-js/db-service`, not in the capire docs, measured on 10.1.1 and pinned by tests (recommended); alternative: single-target constraints, then the message appears while typing only when the constraint's own field is touched (always at Save).
- D9 R9: include the imperative pattern rule (model element, CSV, lib function, three handler registrations, three backend tests, one OPA5 case, one `ru` text) or leave the showcase declarative.
- D10 UI: `ux-designer` writes `SCREENS.md` in this spec phase (messages per field, both-field highlight of R4 and R6, the required marker on Description and on the detail labels, the popover entry of a MULTI_LIST required detail, `en` and `ru`); the user reviews it with the plan.
