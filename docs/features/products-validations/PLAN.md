## Decisions that require an ADR
- ADR-0028 "Validation toolkit" (accepted by the user on 2026-10-14, `docs/decisions/ADR-0028-validation-toolkit.md`): decision 1 custom texts through `@assert.format.message` / `@assert.range.message` with a message key; decision 2 user-facing uniqueness through a self-association in `db/schema.cds` plus an `exists` constraint, never `@assert.unique`; decision 3 the two-target `error('KEY', args, ('a', 'b'))` form in a constraint, also with path arguments and `coalesce(localized.name, name)` for localized names, pinned by tests; decision 4 a conditionally required field as `@assert` + `error()` with both targets + `Common.FieldControl: (cond ? 7 : 3)` in the app annotations; decision 5 a required flag on the assignment entity read by the constraints and the form (D5 = A); decision 6 every new root constraint gets a per-row import pre-check as a pure function; decision 7 withdrawn with R9; decision 8 bounds per assignment as a branch with the `$self` value compared inside the infix filter, the client type constraints plus a placeholder as the control; decision 9 a rule between two child rows through an association on the attribute entity and one `exists product.details[...]` starting at the draft row, never through an association that starts outside the draft tree, no mirror branch; decision 10 a value-driven dependency between attributes as a control (disabled and cleared row) plus one guard branch marked "guard, not user-facing"; decision 11 the "prevent before validate" principle: every rule names its preventing control, the server constraint stays the guard.
- No ADR for R1, R3, R5 themselves (PATTERNS "Format or range check"), for the R8 and R13 branches (ADR-0026 decision 5 form), for the `DetailsForm` label marker (ADR-0027 decision 5, a `setRequired` in the existing factory) or for the managed associations `atLeast` and `enables` (PATTERNS "Reference to another entity").

## Risks
- `error()` with targets and with path arguments is not in the capire docs (research sections 2 and 10.6): a cds or db-service minor could change it; the R4, R6 and R11 tests pin the shapes, and the fallback is a single-target constraint with a plain key, a one-line change per rule.
- Fiori Elements may not render `additionalTargets` as a second error state (not measured): `ui-verifier` scenario in phase 3; fallback: accept one highlighted field, SCREENS and the OPA5 case adapt, the server rule is unchanged.
- An activation error on a custom form control (`in/details(...)/numberValue`, R8 and R11) may stay in the message popover without a value state on the input: `ui-verifier` measures; fallback: `DetailsForm.js` adds a client `validation: true` message for an empty required field at commit (the ADR-0027 B6 shape), a `fiori-app-dev` round in phase 3.
- Input validation at activation hides the constraints until fixed (research section 1, P8d): a user can see a second set of messages on the second Save; SCREENS documents it, the OPA5 cases assert one kind per Save.
- R6 breaks every writer that omits a description (LESSONS 2026-10-10): `newProduct`, `generatedRow`, README are in steps 4 and 5; a forgotten writer shows as a red existing test at the phase 2 gate.
