Learned 2026-10-13 while designing `products-validations` (#10), fiori-mcp up all session (7 queries).
- Citable fiori-mcp documents: "Using Messages in SAP Fiori Elements" (step 1 state vs transition messages, state messages only in edit mode; step 2 the backend revalidates after each change, multi-target messages "only for special scenarios (inter-field dependency, unit-of-measure associated field)" and all targets on one page; step 5 V4 refills the entity's state messages on each read; step 8 message button and popover anatomy: grouping by section, subtitle, navigation on click, severity filter, count = errors). "Draft Validation" (Enter triggers the global side effect; CAP's generated `#alwaysFetchMessages` with `SourceEntities: ['']` is one; fpmExplorer URL `.../#/advancedFeatures/guidance/draftValidation`). "Field Control" (the FormElement building block renders the mandatory marker itself). "Support for Extended OData Annotations (V4)" (`If` expressions supported for `Common.FieldControl`, `UI.Hidden`, `Core.OperationAvailable`). "Draft Handling" step 10 returns the draft design guideline URL `https://experience.sap.com/fiori-design-web/draft-handling/`. "Handling Inconsistent Input" step 4: client type errors block Save, business rules are state messages.
- Not in the snapshot (three phrasings each): how `additionalTargets` renders, whether `Validation.Pattern` / `Validation.Exclusive` reach the client, message-wording rules, a required-field design document. "Validation.Pattern" queries return only "Input Mask" (`UI.InputMask`) and OData V2 `InsertRestrictions.RequiredProperties` (V2 only, not applicable). Write those rows as expected plus a verifier scenario.
- UI5 facts (`get_api_reference`, small outputs): `sap.m.Label#required` (asterisk on the label; FE shows it on filled fields too, measured #8), `sap.m.InputBase#valueStateText` (framework default when empty), `sap.ui.model.odata.type.Decimal` constructor lists `minimumExclusive`/`maximumExclusive`; `ODataMetaModel#requestUI5Type` does NOT document which annotations become constraints. The claim that the V4 meta model maps `Validation.Minimum`+`Exclusive` to the Decimal constraints (so an open `@assert.range` bound is checked on the client with the framework text before any PATCH) and nothing for `Validation.Pattern` comes from the UI5 source `ODataMetaModel` `mUi5TypeForEdmType`: mark "not verified by MCP", hand to the verifier, and raise it as a user question (framework text on the screen vs project text).
- Measured facts reused from earlier features (cite the SUMMARY, the folders are pruned): #9 a client validation message makes FE refuse Save and open the popover (`iSeeSaveBlockedBy`); #8 F1 a Save-time `@mandatory` entry stays in the footer count until the next read, and an empty Category lists the disabled Subcategory too; `req.warn` on a PATCH = Warning state, not counted.
- Shape that worked for SCREENS of a validation feature: a "when a message appears and where" table (rule, kind, moment, on the field, in the popover) derived from the architect's timing matrix; a marker table (field, marker, source, when it changes); one subsection per rule group; "Save and the second round" for the cds order (input validation before constraints); the texts review as action-first rewrites with the `#XMSG` comment column; verifier scenarios that name the network proof (PATCH sent or not, DraftMessages in the batch).
- Check the seed against the "popover-only" cases early: #10's D6 required attributes were all numeric, so the MULTI_LIST popover-only message was unreachable on the screen and became an open question instead of a scenario.
