# ADR-0011: Value help for associations to a CodeList

Date: 2026-09-07. Status: accepted (user, 2026-09-07, both parts, feature `categories-code-list`).

Two independent decisions; both accepted.

## Context
The row "Value help from a code list" in `PATTERNS.md` and the template `templates/annotations-ui.cds` prescribe writing `@Common.ValueList` by hand, but the only example in the code (`Products.currency_code`) contains no ValueList: it is generated by the compiler from `@cds.odata.valuelist`, which the `sap.common.CodeList` aspect carries. The experiment during the planning of `categories-code-list` (cds-dk 10.0.7, see `docs/features/categories-code-list/CONTEXT.md`, "Verified by compilation") showed: an explicit annotation compiles and "wins" over the auto-generation, but duplicates ten lines and loses the `Label`; without the explicit annotation the compiler creates a ValueList with the `Label` from `@title`, a `CollectionPath` to the code list projection and the parameters `InOut code`, `DisplayOnly name`; `Common.ValueListWithFixedValues` is copied from the association to the foreign key. The Fiori Elements guideline "Value Help as a Dropdown" recommends a dropdown instead of a dialog for a fixed stable set of values; the project had no row on when to choose which presentation. `ux-designer` additionally established (`search_model` on `CatalogService.Currencies`): on `sap.common.Currencies` the annotation `@Common.Text: name` is on the `code` element in the definition in `@sap/cds/common` itself, the `CodeList` aspect does not provide it, so for an own code list without such an annotation the list items and the dialog columns show the code.

## Decision

Part 1, ValueList source. For an association to an entity based on `sap.common.CodeList` (own or from `@sap/cds/common`), `@Common.ValueList` is not written by hand: it is provided by the aspect's `@cds.odata.valuelist`, and the `Label` is taken from the element's `@title` in `srv/annotations`. In `app/<app>/annotations/<Entity>.cds` only the presentation annotations remain on the association: `Common.Text: <assoc>.name`, `Common.TextArrangement: #TextOnly` and flags like `Common.ValueListWithFixedValues`. For an own code list, `app/<app>/annotations/<CodeList>.cds` is additionally created with `Common.Text: name` and `Common.TextArrangement: #TextOnly` on the `code` key (`Currencies` already has this in `@sap/cds/common`), so that the list items and the dialog columns show the name. An explicit `@Common.ValueList` is allowed only for targets not based on a CodeList, or when additional parameters are needed (`In`/`Out` to other fields, `ValueListParameterConstant`, `PresentationVariantQualifier` for sorting); then it is written per the template, and the EDMX must still end up with one ValueList per property.

Part 2, presentation. A code list that is maintained by developers through CSV and has no maintenance screen (a fixed stable set) gets `Common.ValueListWithFixedValues: true` on the association: the field is rendered as a dropdown (multi-select in the filter, single-select in the form). Code lists that grow, are maintained by users or contain hundreds of values (`Currencies`, `Countries`) keep the default value help dialog. If a code list gets a maintenance screen, it loses its fixedness and returns to the dialog. Radio buttons (`ValueListShowValuesImmediately`), `FilterRestrictions`, `FilterDefaultValue` and `ValueListForValidation` are not used.

First application: `Products.category` → `Categories` (`app/products/annotations/Products.cds`, `app/products/annotations/Categories.cds`).

## Alternatives
| Option | Why rejected |
|---|---|
| Explicit `@Common.ValueList` for all code lists (the previous wording of the pattern) | Duplicates the compiler output, loses the `Label`, diverges from the only existing example; a code list change requires editing two places |
| Value help dialog for all code lists | For 6 fixed categories the dialog is heavier than a dropdown and shows the code column as an `InOut` parameter; the Fiori guideline explicitly recommends a dropdown for fixed values |
| A numeric threshold (for example ≤ 20 values) for the dropdown | The guideline sets no such threshold (the number ≤ 8 applies only to radio buttons); the criterion "stable set without a maintenance screen" is checked by the code, not by the data |
| Radio buttons for very short lists | Require `mandatory`, do not support `TextArrangement`, do not allow multi-select in the filter |
| `Common.ValueListForValidation` on the client | The existence of the code is already checked by `@assert.target` on the server; with a dropdown entering a non-existent value is unreachable |
| `Common.Text` on `code` in `srv/annotations/<CodeList>.cds` | This is presentation, not data semantics: per ADR-0004 its place is in `app/` |

## Consequences
- `PATTERNS.md`, row "Value help from a code list": rewrite as "`Common.Text` + `Common.TextArrangement: #TextOnly` on the association and on the key of an own code list (`app/<app>/annotations/<CodeList>.cds`); the ValueList is generated from the CodeList; `Common.ValueListWithFixedValues: true` for fixed code lists without a maintenance screen", example `Products.category_code`.
- `templates/annotations-ui.cds`: remove the explicit `Common.ValueList` from the `category` block, keep `Text`, `TextArrangement`, `ValueListWithFixedValues`; add an annotation block for `Categories.code`.
- `.claude/rules/ui-annotations.md`: the row about an association to a code list is extended with the words "do not write a ValueList by hand for a CodeList; `Common.Text` on the code list key" (the file is protected, edited on a separate user request).
- The reviewer treats a hand-written `@Common.ValueList` on a foreign key to a CodeList as a duplicate.
- Known limitation: sorting and grouping by such a column go by the code; sorting by the translated name would require an explicit ValueList with `PresentationVariantQualifier` (an exception to part 1).
