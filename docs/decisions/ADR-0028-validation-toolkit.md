# ADR-0028: Validation toolkit: custom texts, uniqueness, two-target constraints, conditional requirement

Date: 2026-10-13. Status: proposed (feature `products-validations`; decision by the user pending).
<!-- On acceptance replace the whole Status sentence with the accepted form; never append to the proposed one. -->

## Context
Issue #10 asks for Object Page validations through annotations, and the user's addition makes it a showcase: logical constraints over every field that deserves one, including the typed details of #9, with a handler only where an annotation cannot express the rule. `PATTERNS.md` has rows for `@assert.format`/`@assert.range` ("Format or range check"), for `@assert: (case ...)` constraints with null guards and `exists` set membership ("Cross-field consistency check", ADR-0024, ADR-0026) and for a dynamic `Common.FieldControl` on a dependent field ("Field editable only when another field is filled", ADR-0025). Five things the showcase needs have no row: a project text for a format or range rule, a uniqueness rule a Fiori user sees on a draft-enabled root (the row forbids `@assert.unique` inside a draft tree, and ADR-0026 measured a 500 on SQLite), a constraint message that marks two fields, a field that is required only while another field has a value, and an imperative rule on a draft child. The import (ADR-0021) maps per-row errors only for input validation; a constraint is checked at commit and names no row (ADR-0024 amendment).

Evidence: `docs/features/products-validations/research/validation-facts.md` (capire via `mcp__cds-mcp__search_docs`, `@sap/cds` 10.1.1 and `@cap-js/db-service` sources, a scratch copy with probes P0-P14 and Q1-Q4).

## Decision
1. **Custom texts for input validation.** A format or range rule whose default text would not explain the domain reason carries `@assert.format.message: '<KEY>'` or `@assert.range.message: '<KEY>'` in `srv/annotations/<Entity>.cds`, the key in `_i18n/messages.properties` and `messages_ru.properties`; the error code stays `ASSERT_FORMAT` / `ASSERT_RANGE`, so the import's `validationErrors` mapping and the Fiori message handling are unchanged. Open bounds are written as `[(0), max]`; `_` is infinity. The global `ASSERT_*` keys are not overridden in the project bundle.
2. **User-facing uniqueness on a draft root.** A uniqueness rule a user must see is a self-association in `db/schema.cds` (a structural element, no annotation) whose `on` condition states the equality, for example `namesakes : Association to many Products on lower(trim(namesakes.name)) = lower(trim($self.name)) and namesakes.ID != $self.ID`, plus `@assert: (case when name is not null and exists namesakes then '<KEY>' end)` in `srv/annotations/`. From a draft the association resolves to active rows (lean draft), so the own active sibling is excluded by `ID` and the message appears while editing; at activation the active row is checked against the others. `@assert.unique` stays a DDL constraint for CSV-only writers (ADR-0026 decision 1). The navigation property is visible in `$metadata` (`@cds.api.ignore` does not hide navigations) and gets a `@title`.
3. **Two targets and arguments in a constraint.** When a rule reads two fields the user edits, its `then` branch is `error('<KEY>', <args or null>, ('<field1>', '<field2>'))`, the CQL function of `@cap-js/db-service` that `assert.js` turns into `target` and `additionalTargets` (and message arguments). Targets are string literals of the flattened element names (a path is shortened to its last segment; a generated foreign key name is a compile error in an expression). On a draft the message is written when either field is touched; on activation the OData error carries the first target. The function is not in the capire docs: the feature pins its shape with a backend test per rule, and the fallback is a plain key with one target.
4. **Conditionally required field.** A field that is required only while another field has a value is never `@mandatory`; it is an `@assert` constraint with both targets (decision 3) in `srv/annotations/` plus `Common.FieldControl: (<condition> ? 7 : 3)` on the element in `app/<app>/annotations/<Entity>.cds` (the ADR-0025 shape: CDS expression, integer codes, association paths; `7` Mandatory marks the field, `3` Optional unmarks it, both editable). The server never evaluates the field control; the constraint is the guard on every path.
5. **Required details per assignment.** `SubcategoryAttributes.required : Boolean` names the attributes a subcategory requires; the `ProductDetails` constraints add one branch per value column guarded by the value type, in the ADR-0026 decision 5 form `exists attribute.subcategories[subcategory.code = $self.product.subcategory.code and required = true]`, the MULTI_LIST branch on `attribute` (`not exists selections`); the custom form reads the flag from the expanded assignment (`$expand=attribute(...;$expand=subcategories($select=subcategory_code,required))`) for the label marker. No copied column on the row (the user's D5 may choose the copied column instead; then the draft handler copies it like `position`).
6. **Import pre-check per root constraint.** Every constraint on the root entity gets a per-row pre-check before the inserts, as a pure function in `srv/lib/products-import.js` (rows in, `PRODUCTS_IMPORT_ROW_INVALID` entries out, reason text passed in), the handler owning one `SELECT` for the codes the rule needs; the constraint stays the guard. Generalises ADR-0021 amendment 4 E.
7. **Imperative rule on a draft child (only if the user includes R9).** A rule no portable expression can state (a regex per row) is one pure function in `srv/lib/<topic>.js` and three registrations in `srv/<name>-service.js`: `before('SAVE', <Root>)` over the deep child rows (fires on a deep `POST`, an active `PATCH` and at activation with `req.event` `UPDATE`), `before('SAVE', <Child>)` for the active child write through the root, `before('PATCH', <Child>.drafts)` for typing (400, the value is not stored). Messages in the object form with `code`, `args` and `target`.

First application: feature `products-validations` (#10), rules R1-R8 (R9 optional) of its `CONTEXT.md`.

## Alternatives
| Option | Why rejected |
|---|---|
| Override `ASSERT_RANGE` / `ASSERT_FORMAT` in the project bundle | one text for every field; the per-field `.message` explains the domain reason |
| `@assert.unique` on `Products.name` | 500 `ERR_SQLITE_ERROR` with `@cap-js/sqlite`, nothing on a draft (ADR-0026 measurement) |
| `exists (select ...)` in the constraint | subqueries are not allowed in annotation expressions (capire) |
| `before(['CREATE','UPDATE'], Products)` handler for uniqueness | imperative where a constraint works; no draft message while editing; the import's `validationErrors` would need a mapping for a non-`ASSERT_*` key |
| Two single-target constraints for a cross-field rule (one per field) | two messages at activation for one defect; `error()` gives one message with two targets |
| `@mandatory` with a condition | `@mandatory` is static (capire, ADR-0025 point 3); a dynamic field control alone is not enforced by the server |
| Copied `ProductDetails.required` column (decision 5 variant B) | a second source of truth that is `null` on rows created through the API before the Edit fill; kept as the user's option D5 = B |
| Row-less commit error in the import for the new constraints | the user sees a message without a row number; ADR-0021 decision 4 promises one message per bad row |
| `@assert.format` or a SQL `like`/`glob` for a per-attribute pattern | static per element; `glob` and `regexp` are not portable between SQLite and HANA |
| Client-only check (UI5 type constraint) for the pattern | the server must guard the API (invariant 6, ADR-0027 split) |

## Consequences
- `PATTERNS.md`: "Format or range check" gets the `.message` key and open bounds (decision 1); "Cross-field consistency check" gets the self-association uniqueness form (decision 2) and the `error()` two-target form (decision 3); new row "Conditionally required field" (decision 4); "Typed attribute values" gets the required branch (decision 5); "Bulk create from a file" gets "every root constraint needs a per-row pre-check" (decision 6); with R9 a new row "Imperative validation on a draft child" (decision 7). Examples: `srv/annotations/Products.cds`, `srv/annotations/ProductDetails.cds`, `app/products/annotations/Products.cds`, `srv/lib/products-import.js`.
- `TESTING.md` "cds 10 specifics": the timing matrix of research section 1 (format and range in the `PATCH` response, constraints on the next `DraftMessages` read for touched or additional targets, input validation hides constraints at activation), `additionalTargets` in draft messages, `before('SAVE', <Root>)` sees the deep children at activation.
- `templates/annotations-semantic.cds`: one commented example each of `.message`, an open bound and `error()` with two targets.
- The reviewer accepts: a self-association only with a `@title` and a constraint that uses it; `error()` only with string-literal targets and a pinning test; a dynamic field control for a requirement only together with its constraint; a validation handler only with the research note that names the annotation limitation.
- EDMX on this model (research section 7): self-association +5, `Validation.Exclusive` +2, `Validation.Pattern` +1 each, `required` with title +4, the field control +10; `.message`, constraints and `error()` 0.
- Known limits: SQLite's `lower()` folds ASCII only; `error()` is a source-level API; the client may apply `Validation.Pattern`/`Validation.Exclusive` itself (phase 3 measures the shown text).
