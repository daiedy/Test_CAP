Background: `docs/STATE.md` "Open debt" (last row) and `docs/features/products-draft-edit/VERIFICATION.md` scenarios 4 and 6. `CatalogService.Products` is draft-enabled (ADR-0012) and everything around drafts works — Edit/Save/Cancel, the Editing Status filter with its six options, the Object Page "Locked" button with the popover — but a row in the List Report shows no indication that it is an own draft or that another user holds a lock. ## The `name` uniqueness question

`Products.name` is `String(100)` with `@mandatory` and no uniqueness constraint; the 15 seeded rows in `db/data/my.catalog-Products.csv` have 15 distinct names (checked). The vocabulary intent of a semantic key is a human-readable business key, so the question is fair. Recommendation: **use `name` and do not add a uniqueness constraint in this feature.** Reasons, each backed above:

- Nothing in FE V4 dereferences a semantic key: it is used to choose the marker column, to render `ObjectIdentifier`, and to add the property to `$select` (experiment 4). Identity, navigation, delete and drafts all run on the technical key `ID` + `IsActiveEntity` (experiment 5). A duplicate name therefore produces two rows that look alike — the same cosmetic situation that already exists today — and never an ambiguous action.
- `@assert.unique: { name: [ name ] }` is a `db/` change (MCP #6) that turns a naming coincidence into a runtime rejection on Create and on `draftActivate`. That is a domain rule, needs its own tests and error text, and would silently forbid legitimate duplicates (same product name in two categories, variants). It does not belong in a UI-marker feature, and it would drag `cap-backend-dev`, a `db/` migration question and new `@assert` messages into a one-line change.
- The alternative "introduce a real business key (`productNumber` / SKU) and make it the semantic key" is a bigger, separate feature (new element, data migration for the CSV, new column in the LineItem, filter, i18n) with its own value; if the user wants it, this feature should be postponed rather than half-done.
- The plan does add the guard that actually matters for correctness: `ui-verifier` checks the marker on a row whose name is unique in the seeded data, and the OPA5 journey asserts `iCheckRows({ name: 'Laptop Pro 15' }, 1, ...)` with an explicit expected row count of 1, which would fail loudly if a duplicate ever appeared in the seed data.

The decision and its alternatives are written down in `docs/decisions/ADR-0015-list-report-draft-marker.md`; a follow-up row for `productNumber` goes into `docs/STATE.md` only if the user asks for it.

## Layer

`@Common.SemanticKey` is presentation: it decides where the FE table renders the editing status and how the cell is rendered. CLAUDE.md invariant 5 and `docs/architecture/CONVENTIONS.md` section 2 put "`@UI.*`, `@Common.ValueList`, `@Common.Text`" — i.e. presentation — in `app/<app>/annotations/<Entity>.cds`, and reserve `srv/annotations/` for meaning and validation (`@title`, `@mandatory`, `@assert.*`, `@readonly`). `db/` carries no annotations at all. So the single line goes into the existing `annotate CatalogService.Products with @( ... )` block of `app/products/annotations/Products.cds`. This is also the layer the user named, and ADR-0004 already covers the split. (If the project ever exposed a second UI over the same service, a semantic key would arguably be service-wide semantics; with one app this is a hypothetical and is recorded in ADR-0015 "Consequences" rather than acted on.)

### 1. Verdict on the standard result: accept it, unchanged

**Yes — `sap.m.ObjectIdentifier` in the `Product Name` cell is the correct Fiori design here.** Reasons, each sourced:

- It is not a choice, it is the documented rendering of a semantic key in a responsive table: "Fiori elements renders semantic key fields in responsive tables using `sap.m.ObjectIdentifier`" and "If no text available: first line is bold ID; no second line" (`mcp__fiori-mcp__search_docs` → "Handling Semantic Key Fields in SAP Fiori Elements", doc `handling-semantic-key-fields-aa2793c.md`, steps 5 and 8). Choosing the marker while refusing the `ObjectIdentifier` is not possible without reimplementing the column (rejected in ADR-0015).
- The control's purpose matches the column's job: "enables the user to easily identify a specific object. The `ObjectIdentifier` title is the key identifier of the object" (`mcp__ui5-mcp-server__get_api_reference` `sap.m.ObjectIdentifier`, UI5 1.136.5 — the version the app runs, `minUI5Version` 1.136.0). Design guideline behind it: <https://experience.sap.com/fiori-design-web/object-display-elements/> (the `references` entry of both `sap.m.ObjectIdentifier` and `sap.m.ObjectMarker` in the API reference).
- Emphasising the identifying attribute of a line item is the intended List Report look; `name` is already the first column, the `UI.HeaderInfo.Title` and `@mandatory`, so the bold cell and the page title now agree instead of diverging.
- **The UUID question is already answered correctly and must stay that way**: `ID` is neither in `UI.LineItem` nor in the semantic key, so no UUID is ever displayed and **no `Common.TextArrangement` is needed** — `name` *is* the human-readable text, there is no code-plus-text pair to arrange. Contrast with `category_code`, which does need `Common.Text` + `#TextOnly` and already has it (ADR-0011).
- **Guard for the implementer**: do **not** add `Common.Text` (or a `TextArrangement`) to `name` in this or a later feature. With a text present the same rule renders "bold text / second line ID" — a two-line cell and a taller row for no gain (same doc, step 5).
- Single-line, bold, no second line is therefore the expected and accepted look. Nothing about it warrants reconsidering the floorplan or the table type; the grid-table variant (marker in its own unlabelled second column) is rejected in ADR-0015 and I confirm that rejection: an unlabelled column is worse for screen-reader users than a marker read together with the object name.

Screen budget check, unchanged by this feature and inside the defaults: 4 table columns (`name`, `category_code`, `price`, `stock`) of a maximum of 7; 3 `UI.SelectionFields` plus the framework "Editing Status" filter = 4 filters of a maximum of 5; actions unchanged (Create and Delete in the table toolbar, row click navigates). One screen, one task: "find a product and see whether it is being edited".

### 2. Marker semantics, placement and texts

| Row state | Backend condition | `Product Name` cell shows | `sap.m` text key |
|---|---|---|---|
| Active, unchanged | no draft sibling | bold `name`, **no marker** | — |
| Own draft | draft owned by the logged-in user | bold `name` + `ObjectMarker` type `Draft` — **text only, no icon** | `OM_DRAFT` |
| Locked by another user | another user's draft, lock still valid | bold `name` + `ObjectMarker` type `LockedBy`: icon `sap-icon://private` **and** text above 600 px, **icon only below 600 px**; text is a link | `OM_LOCKED_BY`, fallback `OM_LOCKED_BY_ANOTHER_USER` |
| Unsaved changes by another user | another user's draft, lock expired | bold `name` + `ObjectMarker` type `UnsavedBy`, same icon/text breakpoint rule | `OM_UNSAVED_BY` |

Placement: **inside the existing first column, after the name, in the same cell** — no new column, no new column header (`mcp__fiori-mcp__search_docs` → "Configuring Display of Editing Status in List Report Tables", step 5: responsive table → key column; and "Fiori Elements — Editing Status": grid/analytical/tree tables would instead get an unlabelled second column). The `Product Name` column header text does not change.

The icon/text rule above is **a correction to the marker definition used by the verifier scenarios** and comes from the pinned API, not from recollection: `sap.m.ObjectMarker`, property `type` — "If the `visibility` property is not specified explicitly, every `type` comes with predefined one as follows: … For `Draft` the text is visible and **the icon is not displayed** … For `Locked`, `LockedBy`, `Unsaved` and `UnsavedBy` — on screens larger than 600px both icon and text are visible, otherwise only the icon" (`mcp__ui5-mcp-server__get_api_reference` `sap.m.ObjectMarker`, 1.136.5). Fiori Elements sets `type` and `additionalInfo` only, so these defaults apply. See addition A1 below.

Lock popover (click or keyboard-activate the marker link): full user name if master data has one, else the technical user name, else the generic "another user" wording, plus the time of the last change ("Fiori Elements — Editing Status", step "Display user/time access for specific statuses"; consistent with what the Object Page popover already showed on 2026-09-07). Content and layout are framework-owned; we specify nothing.

**i18n: no project key is needed, in `en` or `ru`.** Every string of this feature is a `sap.m` library text (`OM_DRAFT`, `OM_LOCKED_BY`, `OM_LOCKED_BY_ANOTHER_USER`, `OM_UNSAVED_BY`) shipped translated in `sap/m/messagebundle.properties` and `sap/m/messagebundle_ru.properties` (measured, CONTEXT experiment 4), and the marker carries no application-authored label. So `app/products/webapp/i18n/i18n.properties`, `i18n_ru.properties` and `_i18n/*` are untouched and CLAUDE.md invariant 7 is satisfied by adding nothing. The Russian wording is not quoted in this document (invariant 10); `ui-verifier` records it from the running app in scenario 4. A missing or wrong `ru` string would be an upstream finding, never a reason to introduce a project override.

### 3. Accessibility

Checklist of the `ui5-best-practices-accessibility` skill (all eight topics), against a page whose controls are entirely framework-generated. Verdict: **we supply nothing, and there is nothing we could supply without the custom column that ADR-0015 rejects.**

| # | Topic | Verdict for this feature |
|---|---|---|
| 1 | Landmarks | unchanged; the FE List Report page owns them |
| 2 | Labeling | **the marker's accessible name is its own text**, which is why the text-only `Draft` type is safe. `ariaLabelledBy` / `ariaDescribedBy` exist on `sap.m.ObjectMarker` and on `sap.m.ObjectIdentifier` (API reference) but are **unreachable from an annotation** — FE instantiates the controls. We add nothing; instead `ui-verifier` asserts the accessible name in the accessibility tree (A2). Cell-to-column-header association is done by `sap.m.Table` |
| 3 | Heading levels | unchanged |
| 4 | Focus and keyboard | the `LockedBy`/`UnsavedBy` marker is interactive (inner `sap.m.Link`, `press` event) inside a navigable row, so it must be tab-reachable, activate with Enter/Space and return focus after Escape — framework behavior, asserted in A2, not implemented by us. The `Draft` marker and the `ObjectIdentifier` are non-interactive here (`titleActive` stays `false`: FE makes the title a link only when a semantic object is annotated, and we annotate none), so they add no tab stop and the row's own navigation is unaffected |
| 5 | Keyboard shortcuts | not applicable — no new action |
| 6 | Invisible messaging | no new dynamic state change on this page; the draft state arrives with the row data, and the existing FE toasts ("Draft discarded" etc.) are unchanged |
| 7 | Reading order | the marker is rendered **after** the name in the same cell, so a screen reader reads "Product Name — `<name>` — Draft": identity first, status second. Correct, and the reason the marker must stay inside this cell rather than become a leading element |
| 8 | Target size (WCAG 2.5.8 AA) | the one real gap. `reactiveAreaMode` defaults to `Inline` on `sap.m.ObjectMarker` and FE exposes no way to set `Overlay`, while the marker link sits in an interactive (navigable) list item — exactly the pattern `references/target-size.md` flags. **Accepted as a framework-level limitation, not fixed here**: fixing it needs a custom column or CSS, both forbidden (ADR-0015, and custom CSS needs its own ADR). `ui-verifier` measures the link's rendered box once (A3); below 24x24 CSS px it is recorded as an upstream note against `sap.m`/`sap.fe`, not as a defect of this feature |

Non-text conveyance (WCAG 1.4.1): the design never relies on colour — `Draft` is plain text, `LockedBy`/`UnsavedBy` are icon **plus** text on normal screens. Below 600 px the marker is icon-only, which is acceptable only because the control keeps the text as its accessible name; that is what A6 verifies. Bold is styling of the identifier, not a status carrier: the editing status is always conveyed by the marker's text, so the bold key column alone is never asked to mean anything.

Theme and tokens (`mcp__ui5-mcp-server__get_guidelines`): standard `sap.m` controls only, `sap_horizon`, no custom colour, no CSS class, no formatter — the guidelines' rules on avoiding custom formatting and on keeping all locales in sync are satisfied trivially because we add no control and no string.

### 4. Object Page: no change needed, one thing to re-check

- **Lock: nothing to add.** The Object Page already surfaces it fully — header "Locked" button, popover "This object is being edited by bob. Last changed on …", and a clean error dialog on Edit (verified 2026-09-07, `docs/features/products-draft-edit/VERIFICATION.md` scenario 6). The row marker was the only missing half.
- **Draft: nothing to add.** Own drafts already open in edit mode with the "Draft" header menu button and the Save / Discard Draft footer.
- **One gap the research did not cover, and it is a check rather than a change**: the semantic-key rendering rules also apply to object pages in OData V4 ("Handling Semantic Key Fields", step 8), and `name` is a field of `UI.FieldGroup#GeneralInfo`, i.e. it is rendered next to a `sap.m.Label` in a form — a combination the API explicitly warns against ("This control should not be used with `sap.m.Label` or in Forms along with `sap.m.Label`", `sap.m.ObjectIdentifier`). Expected behavior: forms are unaffected, the rule concerns table columns, so the "Product Name" field of General Information keeps its label and its plain display rendering. **Not verified**, therefore it becomes verifier assertion A4. If the field does turn bold or loses its label, that is a finding for `architect` (candidate answer: move the semantic key rendering question into the ADR's "Consequences"), never a hand fix in the form.
- Header title and breadcrumb are unaffected: `UI.HeaderInfo.Title` already renders `name`.

### 5. Row states the design covers

1. **Active, unchanged** (13 of the 15 seeded rows in the normal case): bold name, no marker, no extra tab stop. This is the state scenario 1 pins.
2. **Own draft**: bold name + text-only `Draft` marker. Reachable and asserted in OPA5 (`iCheckRows({ name: … }, 1, { isDraft: true })`) and in verifier scenario 2.
3. **Locked by another user**: bold name + `LockedBy` marker with icon and a link to the user/time popover; the `Locked by another user` fallback wording is equally correct when the technical name cannot be resolved. Verifier scenario 3 (`curl -u bob:`); not automatable in OPA5.
4. **Unsaved changes by another user** (`UnsavedBy`): reachable only after another user's draft lock expires, which no scenario can force in a dev session. Framework-covered by the same annotation and the same cell; **explicitly out of verification scope**, recorded here so its absence from `VERIFICATION.md` is not read as a gap.
5. **New, unsaved object in the list** (Create, then leave the Object Page keeping the draft before `name` is filled): the key cell has no title yet, so the row is identified only by the marker plus the remaining columns; the framework "New Object" title exists on the Object Page, not in the row. No design change is warranted — the state is short-lived and self-inflicted — but what the empty cell renders (nothing versus an FE empty indicator) is **not verified**, hence the optional assertion A8. `sap.m.ObjectIdentifier.emptyIndicatorMode` defaults to `Off`, so "nothing" is the likelier outcome; FE may override it.

Empty state and errors: unchanged and not owned by this feature. A filter with no hits keeps the standard FE "no data" table text; the marker has no empty state of its own. If `DraftAdministrativeData` cannot be read, the row loses its marker but stays usable — no project-side error handling, no message, and nothing for `ui-verifier` to force.

### 6. Review of the seven `ui-verifier` scenarios

I reviewed all seven scenarios and the "marker visible" definition in the section below. **Keep all seven, in that order and with that priority (2 and 3 first).** One assertion in the shared definition is wrong and must be corrected before the run; the rest are additions. None of them adds a screen, a text or a turn-expensive setup step.

- **A1 — correct the pass criterion for the own-draft marker (blocking, otherwise a correct implementation fails verification).** The definition requires "a `sap.m.ObjectMarker` with the icon `sap-icon://request` and the text `Draft`". For type `Draft` the pinned `sap.m` (1.136.5) renders **text only and no icon** by default; `sap-icon://request` is in the control's internal type map but is not displayed. Correct criterion: a `sap.m.ObjectMarker` whose text is the `OM_DRAFT` value, in the `Product Name` cell, in the accessibility tree and the screenshot. Keep the icon requirement **only** for the lock case (`sap-icon://private`) and only at a window width above 600 px.
- **A2 — add the missing accessibility assertions to scenarios 2 and 3 (the definition currently checks only that the marker is present).** (a) the marker's **accessible name** in the accessibility tree, not just the visible text; (b) reading order inside the cell — name before status; (c) keyboard for the lock marker: Tab reaches the link inside the row, Enter (or Space) opens the popover, Escape closes it and focus returns to the link. Reason: this is the one page change of the feature and topics 2, 4 and 7 of the accessibility checklist are otherwise unverified.
- **A3 — measure the lock marker link's rendered box once (scenario 3).** Reason: `reactiveAreaMode` is `Inline` and unreachable from annotations; below 24x24 CSS px this is a WCAG 2.5.8 upstream note against `sap.m`/`sap.fe`, explicitly **not** a defect of this feature and **not** to be fixed with CSS.
- **A4 — add to scenario 5 (no regression): the Object Page "General Information" → "Product Name" field still shows its label and its plain, non-bold display rendering.** Reason: the semantic-key rendering rules also apply to object pages in V4 and `sap.m.ObjectIdentifier` must not be combined with a `sap.m.Label`; see section 4.
- **A5 — add to scenario 1: the `Product Name` column header text is unchanged, the table still has exactly 4 columns, the marker occupies no column of its own, and the bold cell shows no second line.** Reason: it pins the three ways this could go wrong invisibly (a stray extra column, a renamed header, an accidental `Common.Text` on `name` producing a two-line cell).

- **A7 — in scenario 3, assert the popover *content*, not only that it opens: it names the user and the time of the last change.** Reason: the documented behavior of the state (user plus timestamp) is the actual user value of the link.
- **A8 — optional, last, only if the budget allows: Create, leave `name` empty, keep the draft, return to the list, and record what the key cell renders.** Reason: state 5 above is the only row state whose appearance is unverified; the answer costs one screenshot and belongs in `VERIFICATION.md` rather than in a guess here.

Not requested, deliberately: no new scenario for the `UnsavedBy` state (unreachable, see state 4), no scenario for mock mode beyond the existing optional one (the mock server cannot produce draft administrative data), and no request to re-verify the six Editing Status options (scenario 1 already pins them and `products-draft-edit` verified all six).
