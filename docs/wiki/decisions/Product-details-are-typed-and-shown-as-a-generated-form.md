# Product details are typed and shown as a generated form

## Decision

**Shape.** Every attribute has a value type: text, whole number, decimal, a choice from a list, or a choice of several values from a list. A number attribute may carry bounds and, for a decimal, a number of decimals. A list attribute owns its list of values, shared by every subcategory, with a position for the display order and names translated through the usual texts. An assignment of an attribute to a subcategory gets a position too. A detail row loses its free-text value and gets a text value, a number value, a list value or, for a multi-choice, a second level of selection records. The rows stay part of the draft of the product.

**Service.** The selection records carry the access rights of the product, measured again on the second level. The lists and the value types are read-only.

**Rows generated by the draft.** When a draft gets a subcategory, the draft handler keeps the rows whose attribute is assigned to the new subcategory, with their values and their new position, deletes the other rows with their selections, and adds an empty row for each assigned attribute that has none. If removed rows held a value, a warning on the Subcategory field names how many and which. A cleared subcategory keeps the rows, and editing a saved product fills the missing rows of its new draft. Saved products are never reconciled automatically: a subcategory change that leaves foreign rows is refused. In one line: after a subcategory change the draft holds exactly one row per attribute of the new subcategory, and the common ones are unchanged.

**Typed checks.** Values are optional. A text value is allowed only on a text attribute, a number only on a number attribute, a list value only on a list attribute and selections only on a multi-choice attribute. A number stays within the bounds and is whole for a whole-number attribute. A list value, or a selection, belongs to the list of the row's attribute, and a selection value appears once per row. Texts that are not numbers or have more than three decimals are refused by the platform itself. The client carries format, decimals and bounds, and the server constraints are the guard and the net at Save. The earlier guards on the attribute stay as the API guard.

**Screen.** One generic custom section "Details" after "Pricing & Stock", added through the Fiori tooling. A form with one row per detail shows the right control per value type: an input for text, a locale-aware number input with the attribute's bounds and decimals, a dropdown for a list, a multi-select for a multi-choice, plain display controls when not editing, units next to the values and a counter "Filled N of M".

The earlier free-text value, the pick list of attributes in a table row, the Save-time rejection on a subcategory change and the table section are replaced; the shape, the access rights and the guards of the earlier details decision stay. The first use is the details section of a product.

## Why

After the first screen the user rejected the table as clumsy and decided on 2026-10-12 that the details become form fields generated from the subcategory, typed by the attribute, with common values kept when the subcategory changes.
