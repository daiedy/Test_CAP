To verify what the running service actually returns (error `code`/`target`, `DraftMessages`, status of a second DELETE), write a throwaway `test/zz-probe.test.js` that appends its findings to a file in the session scratchpad, run it with `npx vitest run test/zz-probe.test.js`, then delete it before `npm test`.

**Why:** Vitest 5 in this project (`vitest.config.mjs`, `globals: true`) does not print `console.log` of passing tests even with `--silent=false`, and `npm test` runs `vitest run --silent`. Writing to a file is the only reliable way to see probe output. The probe must live under `test/` because the include pattern is `test/**/*.test.{js,mjs}`; it must be removed before the final `npm test` or it is counted as a test.

**How to apply:** Use this whenever a plan states expected runtime behavior that a test could pass vacuously (empty arrays, optional fields, regex targets). Confirmed on 2026-09-07 for the draft feature: `DraftMessages` is `[]` (present, empty) on a draft PATCH without violations; `ASSERT_MANDATORY` on `draftActivate` has target `in/name` while `ASSERT_TARGET` has plain `category_code`; DELETE of a missing draft is 404. Confirmed 2026-10-09 (products-subcategories): an `@assert: (case ...)` constraint message is NOT in the draft PATCH response (`DraftMessages: []`, it is written at `before('commit')`) and shows only on the next `GET ...?$select=DraftMessages`, while `@assert.target`/`.range` messages are already in the PATCH response; a constraint message stays after a later PATCH of another field fixes the pair (touched-only), activation still passes; `draftActivate` of a POST-created draft answers 201, of a `draftEdit` draft 200. Confirmed 2026-10-10 (products-subcategory-cascade): a missing `@mandatory` value hides an `@assert.target` error of another field in the same write (draft activation with category UNKNOWN and an emptied subcategory reports only `ASSERT_MANDATORY in/subcategory_code`; an import row with category NOPE and no subcategory reports only the subcategory), while two missing mandatory values give `MULTIPLE_ERRORS`; so a test of one annotation must keep every other mandatory field filled. Confirmed 2026-10-12 (products-details-section, first composition): a viewer's top-level `POST` of the child without `IsActiveEntity` is 403 (grant first) while the active one is 422 `DRAFT_MODIFICATION_ONLY_VIA_ROOT`; a draft row's constraint message shows on `GET Products(..,false)/details(..,false)?$select=DraftMessages` and on the root, but NOT on the top-level `GET ProductDetails(..,false)`; a deep active `POST` names a row as `details(ID=<id>)/attribute_code` (no `IsActiveEntity`), activation as `in/details(ID=<id>,IsActiveEntity=false)/attribute_code`; without the child's own `@restrict` a viewer POSTs a row through `Products(..,true)/details` with 201 (the root's grants do not cover it). Seeded-row restore in `afterEach` that works: `DELETE ... where\`ID not in ${ids}\`` (array binds as a list) plus `UPSERT.into(...).entries(seededRows)`. Confirmed 2026-10-12 (products-details-section revision 2, cds 10.1.1): lean draft refuses a top-level `POST`/`PATCH` of a composition child with 422 but NOT a top-level `DELETE ProductDetails(ID=..,IsActiveEntity=true)` (editor 204, viewer 403; `lean-draft.js` guards only NEW/CREATE/UPDATE), so never write a "no write outside the root" test that silently includes DELETE; a row with `position` null sorts FIRST under `$orderby=position` on SQLite; a `req.warn` of a handler is read from `JSON.parse(res.headers['sap-messages'])` (header absent when no message); a draft `POST Products` carrying `subcategory_code` creates no generated rows (only a PATCH reconciles). `mcp__cds-mcp__search_model` in a worktree returned the pre-feature model (no new entities), so verify new names with the EDMX/a probe.
