## 3. Where a description comes from and where it lands (probes A3, A4)
Scratch model: `probe.Base` with entity and element doc comments; projections P (`@description` via `annotate` on entity and element), Q (doc comment on the projection; element `@description: '{i18n>NameDescr}'`), R (inline `name @(description: ...)` in the select list), U (`@title` + `@description`), V (doc + `@title`), W (doc + `@description` on the same projection), X (doc comment above `annotate S.X with { /** */ ID; /** */ name @title: 'Name'; }`).

| Source | CSN `doc` / `@description` | EDMX `-l en` | OpenAPI `-l en` |
|---|---|---|---|
| doc comment on the `db/` entity or element | on `probe.Base` and its elements only; nothing on any projection or projection element | nothing (the service has no `probe.Base`) | nothing |
| doc comment on the projection (Q) | `doc` on `probe.S.Q` | `Core.Description` on `probe.S.Q` | schema `title` "Projection doc", tag `description` |

The inline form `name @description: '...'` inside a projection's select list needs the `@(...)` syntax (compiler error otherwise).

## 4. OpenAPI export (probes A, A2, A4; `@cap-js/openapi` 1.6.0 source)
- `npx cds compile srv --to openapi` works out of the box through cds-dk. With docs: OpenAPI 3.0.2, 69 paths, 44 schemas, 153,525 bytes (9,216 pretty-printed lines); with the scratch descriptions 155,967 bytes (9,292 lines). `--docs` on the command and `cdsc.docs` in the environment give byte-identical output; without either, `info.description` is the converter's placeholder.
- `-l en` applies to the openapi target: 7 `{i18n>...}` placeholders without it, 0 with it; no Cyrillic; `-l ru` produces Cyrillic. `-l en` is therefore mandatory for a committed document (invariant 10).
- `-o <dir>` (alias `--dest`) writes `<dir>/CatalogService.openapi3.json`; `-s all` gives the same single file for this one-service model.
- Default server URL is `/rest/catalog`: `lib/compile/index.js` `_getProtocols` takes `rest` when the service has no `@protocol`; `--openapi:url 'http://host/odata/v4/${service-path}'` yields `.../odata/v4/rest/catalog` (the variable already contains the protocol segment); `--openapi:url /odata/v4/catalog` works; `@protocol: 'odata-v4'` on the service gives `/odata/v4/catalog` with no flag and an unchanged EDMX.
- `--openapi:diagram false` adds a yuml diagram to `info.description` (the string "false" is truthy); without the flag no diagram. Do not pass the flag.
- Converter mapping (`csdl2openapi.js`): `info.title` ← `Common.Label` of the entity container (else "Use the title annotation on your CDS service..."); `info.description` ← `Core.LongDescription` or `Core.Description` of the container or schema; `info.version` ← `Core.SchemaVersion`; tag `name` ← `Common.Label` of the entity type (else the set name), tag `description` ← `Core.Description` of the set or type; schema `title` ← `Core.Description || name` (line 2174), schema `description` ← `Core.LongDescription` only (2187); property `description` ← `Core.LongDescription || Core.Description` (2612), no property `title` from `Common.Label`; action `summary` ← the action's `Core.Description` (1648), action `tags` ← the overload's `Common.Label` humanized before localization, hence "Products.import Products" for `importProducts` (cosmetic quirk); `GET /Products` summary "Retrieves a list of products." is generated.
- Today's document with docs on: `info.title` placeholder, `info.version` "", `info.description` = service doc; `Products` schema title "Products", no description; `ProductDetails`, `ProductsImportFile`, `Permissions` schema titles = their doc comments; `createdBy.description` "User's unique ID" and `currency_code.description` "Currency code as specified by ISO 4217" (SAP's `@description`, resolved by `-l en`); `importProducts` summary = its doc comment.

## 10. Rejected mechanisms
- `@description` as the project's description mechanism: works (section 3) but is a second mechanism next to the 16 doc comments, and the compiler lets it override a doc comment silently; kept as the fallback for localized descriptions.
- Doc comments on `db/` entities as the contract source: not propagated to projections or their elements (section 3), so they cannot be the API description; they stay developer notes.
- `--docs` per command: six places must agree (`cds watch`, snapshot test, registry, OpenAPI export, MCP, CI); the `package.json` switch is read by all.
- `--openapi:url` flag: `${service-path}` already contains the protocol segment (`rest/catalog`), a literal URL repeats what `@protocol: 'odata-v4'` states declaratively with an unchanged EDMX.
- `--openapi:diagram false`: parsed as truthy (section 4).
- `-l ru` or no `-l` for the committed OpenAPI document: Cyrillic or raw `{i18n>}` placeholders (section 4).
- OpenAPI JSON under `docs/registry/`: no first-line header, blocked by `protectedWriteHit` as a hand write; YAML there would need an emitter.
- Byte-comparison freshness in `check-docs-fresh.mjs`: a `cds compile` per Stop and per CI run; the `x-sources` stamp costs one file read, the byte comparison lives in `npm test`.
- `jsdoc-to-markdown`, `jsdoc`, TypeDoc for the JSDoc page (section 6).
- `flat/recommended-error` wholesale: 120 findings in `ext/`, 49 UI5 types and 55 style lines among them.
- `require-jsdoc` on every function kind in `srv/`: the same 4 errors today, but every future arrow callback inside a handler would need a block; `publicOnly` plus class methods matches CONVENTIONS section 4.
- `tag-lines` with a fixed `startLines`: 18 or 55 blocks to rewrite for a blank-line style nobody asked for; `startLines: null`.
- `cds-swagger-ui-express` as a runtime dependency; a hand-written `server.js` registration (auto mode is the documented default).
- Extending `HANDLERS.md`/`REUSE-CATALOG.md` tables with full JSDoc instead of a page: tables answer "what exists"; #28 links a page.

## 12. Plan-gate questions as presented on 2026-10-14

Decided by the user on 2026-10-14, all by the recommended answer (CONTEXT.md "User decisions"). Kept here as the record of the options and their bases.

Recommended answers with their basis; the user decides at the plan gate.

1. **Single way for descriptions (issue question 1).** Recommended: CDS doc comments only, never `@description`/`@Core.Description` in project CDS. Placement per artefact kind: `db/` entity → optional developer note (reaches CSN, registry, HANA `COMMENT`, never the contract); projection and its elements → `srv/annotations/<Entity>.cds`, a doc comment above `annotate <Service>.<Entity> with {` and one above each element next to `@title` (measured: a doc comment on an `annotate` statement and on its elements lands in CSN `doc`, EDMX `Core.Description` and the OpenAPI schema title and property description; the `db/` doc comment propagates to neither); service, action, service type and its elements, singleton → doc comment at the definition in `srv/<name>-service.cds` (already so); `//` for developer notes in `srv/*.cds`. Basis: capire "Doc comments are not propagated"; probes P/Q/W/X in `research/docs-facts.md` section 3; the compiler lets `@description` win over a doc comment on the same target, so two mechanisms would be two ways (invariant 4). Alternative if rejected: `@description` in `srv/annotations/<Entity>.cds` next to `@title` (same files, annotation form, localizable).
   1b. **Language of descriptions.** Recommended: English literals (API documentation for developers; `Core.Description` is not rendered by Fiori Elements, no occurrence in the fiori-mcp snapshot; invariant 10 requires English in sources; `-l en` keeps the OpenAPI document free of Cyrillic).
