# products-validations: screens

Written by `ux-designer` (2026-10-13, amended 2026-10-14 after the plan-gate decisions) from the SAP Fiori guidelines, `CONTEXT.md` (rules R1-R8 and R10-R13, the "Preventing controls" table, decisions D1-D13), `PLAN.md` step 1b and `research/validation-facts.md` sections 1 and 10; read by `fiori-app-dev`, `test-ui` and `ui-verifier`. Backend agents do not read this file. One screen, one user task: edit a product (or create one) and save it without errors. No new screen is added; what changes is when and where a required marker, a range hint, a disabled row and a validation message appear on the existing Product Object Page. The user reviews this file at the plan gate together with D1-D13 (D10 is this file).

The user's principle, binding for every rule below: prevent before validate. Wherever a control can make the mistake impossible, the control comes first and the message is the fallback; the server constraint stays the guard on every path. Each rule section therefore starts with what the user sees before any request and ends with the message that remains for the API paths. R9 (text pattern on Dimensions) and R14 (at most N selections) are out (user, 2026-10-14): nothing of them is designed here; the Dimensions remodel is issue #26.

## Floorplan and duplication check

Floorplan: the existing List Report + Object Page of `app/products` (`docs/registry/UI-ARTIFACTS.md`: `ProductsList`, `ProductsObjectPage` with the custom section `Details` after `PricingStock`, `ext/fragment/DetailsForm.fragment.xml` and `DetailsForm.js`, ADR-0027). Nothing is added: no page, no section, no column, no filter, no action, no `manifest.json` change. The feature changes the behaviour of mechanisms the page already has in edit mode: the required marker on a label, the message on a field (value state plus message popover entry), the per-row `Decimal` type of a numeric detail, and adds two states to the Details rows that the Fiori Elements sections of the same page already know: a placeholder hint (`UI.Placeholder` is the framework's own annotation for it) and a disabled field (the Subcategory field before a Category, ADR-0025, measured in #8).

Where MCP corrected my assumptions: (1) I assumed a required or cross-field rule is checked only at Save; the FE document expects the backend to revalidate after every field change and the client to show the result in the popover while editing, so the live R4, R6, R10, R11 and R13 messages are framework-conform, not an oddity. (2) I assumed one message marks one field; the FE document names the multi-target message as the intended form for an inter-field dependency, with the condition that both fields are on the same page (they are: one Object Page). (3) I assumed a tooltip could explain the disabled Battery Life row; `sap.m.InputBase#enabled` says "Disabled controls cannot be focused and they are out of the tab-chain", so a tooltip would be mouse-only and never announced: the explanation moved into the placeholder, which a disabled input still renders (expected, V19). (4) I assumed the Connectivity selection commits per checked item; `sap.m.MultiComboBox#selectionFinish` fires "when user has finished a selection of items in a list box and list box has been closed", so the Battery Life row enables or disables when the list closes (or a token is removed), not per click.

UI5 facts (`mcp__ui5-mcp-server__get_api_reference`, resolved against OpenUI5 1.136.5; the app runs 1.152 or 1.153 from the CDN): `sap.m.Label#required` adds the asterisk to the label text (FE shows it on a filled required field too, measured in #8); `sap.m.InputBase#valueStateText` is the text of the value state pop-up, a framework default text when empty; `sap.ui.model.odata.type.Decimal` has the constraints `minimum`, `minimumExclusive`, `maximum`, `maximumExclusive`, `precision`, `scale`, and `validateValue` throws a `ValidateException` on a violation; `sap.m.InputBase#enabled` (disabled: not focusable, out of the tab chain) versus `#editable` ("A user can tab to non-editable control, highlight it, and copy the text from it"); `sap.m.Input#description` is "a text after the input field, e.g. units of measurement" (the unit slot the Details inputs already use); `sap.m.InputBase#placeholder` "defines a short hint intended to aid the user with data entry when the control has no value"; `sap.m.Input#showSuggestion` fires `suggest` while typing and "when runs on phone, input will first open a dialog where the input and suggestions are shown"; `sap.m.InputBase#ariaDescribedBy` (since 1.90); `sap.ui.core.InvisibleMessage#announce(text, mode)`; `sap.m.MessageToast.show` (default duration 3000 ms, width 15em, bottom centre); `sap.ui.layout.form.FormElement#fields` allows form controls only, which `sap.m.Text` and `sap.m.Input` are; `sap.ui.model.odata.type.Currency` takes its currency customizing from `ODataMetaModel#requestCurrencyCodes` and `validateValue` throws "if the entered amount has too many decimals for its currency" (D13a). Not verified by MCP: the V4 `ODataMetaModel` maps `Validation.Minimum` and `Validation.Maximum` with `Validation.Exclusive` on an `Edm.Decimal` property to exactly these constraints (UI5 source `sap/ui/model/odata/v4/ODataMetaModel`, `mUi5TypeForEdmType`) and maps nothing for `Validation.Pattern` on `Edm.String`; the UI5 core texts of the `Decimal` type (`EnterNumberMinMax` "Enter a number between {0} and {1}", `EnterNumberMinExclusive`, `EnterInt`, `EnterNumberFraction`) and their `ru` translations in the core bundle. If the verifier confirms it, R3 and R10 are checked on the client with the framework text before any request, while R1 and R5 are checked by the server with the project text (see "R3 and R4", "R10", UX risk 1, Q2).

Guidelines of the UI5 MCP (`get_guidelines`, 2026-10-14): data binding in views, built-in OData types with format options before formatters (the range hint is formatted by the row's own `Decimal` type, not by a formatter), every `*.properties` change in every locale, no globals, no inline script, `Form` + `ColumnLayout` (already the case).

### Prevent before validate: control first, message second

What the user meets per rule, in the order the user meets it. "Control" is what refuses or prevents the mistake before any request; "message" is what remains when the control cannot act (API, import, a draft created elsewhere, a race). A rule with "none" has no control the framework offers without a handler (CONTEXT "Preventing controls").

| Rule | Control the user sees first | Message that remains, and when it is seen on this screen |
|---|---|---|
| R1 name too short | none | `PRODUCTS_NAME_TOO_SHORT` on Name after leaving the field (unless the client applies `Validation.Pattern`, V6 records) |
| R2 duplicate name | none | `PRODUCTS_NAME_DUPLICATE` on Name after leaving the field, and at Save for a concurrent draft |
| R3 price above 0 | the client `Decimal` type refuses `0` and negatives at once, framework text, no request (expected, V5) | `PRODUCTS_PRICE_POSITIVE` reaches the API and the import only |
| R4 whole amounts for a currency without minor units | [D13a] the currency type refuses `10.50` for `JPY` at once, framework text, no request (expected, V23); without D13a none | `PRODUCTS_PRICE_MINOR_UNIT` on Price and Currency after leaving either field; with D13a only on the path the client does not check (V23 records which) |
| R5 https image URL | none | `PRODUCTS_IMAGE_URL_HTTPS` on Image URL after leaving the field |
| R6 description while in stock | the required marker on Description follows Stock at once; the client required check at Save (expected, V3) | `PRODUCTS_DESCRIPTION_REQUIRED_IN_STOCK` on Description and Stock after leaving either field; at Save |
| R7 description repeats the name | none | `PRODUCTS_DESCRIPTION_EQUALS_NAME` on Description after leaving the field |
| R8 required detail | the required marker on the detail label (no client check in the custom form) | `PRODUCTS_DETAIL_VALUE_REQUIRED` on the detail after leaving it empty; at Save |

| R11 Storage not below Memory | none (a cross-row comparison on the client would duplicate the server rule without preventing anything) | `PRODUCTS_DETAIL_VALUE_BELOW_OTHER` on the Storage row after leaving it; at Save when only Memory was changed |
| R12 Battery Life only with a wireless connectivity | the Battery Life row is disabled and empty while Connectivity has no wireless value, with the hint "Depends on Connectivity" in the input; enabled the moment a wireless value is selected | `PRODUCTS_DETAIL_VALUE_NOT_ENABLED` never on this screen (the form never sends a value of a disabled row); API only |

### When a message appears and where

The timing matrix of `research/validation-facts.md` sections 1 and 10, translated into what the user sees. "Leaving the field" means Tab, a click elsewhere or Enter: Fiori Elements writes the field (`PATCH`) and reads the draft messages in the same `$batch` (`#alwaysFetchMessages`; the custom Details form does the same after its own writes through `requestDraftMessages`, ADR-0027 amendment D-2), so every server message of this feature reaches the field in one step, right after the field is left. Nothing happens per keystroke, except the client type checks (R3, R10, decimals), which fire when the field is left without any request.

| Rule | Kind | Appears | On the field (value state Error with the text) | In the message popover |
|---|---|---|---|---|
| `@mandatory` on Name, Price, Currency, Stock, Category, Subcategory (exists) | input validation | only at Save (activation 400) | yes, after Save, framework text "Provide the missing value." (cds bundle, `en` and `ru`) | one entry per empty field |
| R1 name too short, R5 image URL not https (`@assert.format`) | input validation, message in the `PATCH` response | after leaving the field; again at Save while still wrong | yes | yes |
| R3 price not above 0 (`@assert.range` open bound) | expected: client type check (framework text) before any request; server `ASSERT_RANGE` with the project text on API paths and in the import | at once when the field is left | yes, framework text expected | yes, as a client validation entry; Save refused on the client |
| R2 duplicate name, R4 price x currency, R6 description x stock, R7 description = name (`@assert` constraints) | state message written at the commit of the field's `PATCH`, read in the same batch | after leaving a field that is one of the rule's targets (`touched` or `additionalTargets`); at Save for everything | yes, on every target field | one entry per message (expected: a two-target message is one entry) |
| R8 required detail (`@assert` on the row) | state message on the row and on the product | after leaving the detail field; at Save | yes for TEXT, INTEGER, DECIMAL, LIST (the control binds the column); no for MULTI_LIST (target `attribute_code`, nothing binds it) | yes |
| R10 bounds per subcategory | client type check with the assignment's bounds (framework text, no request); the server branch only for a value the client never checked | at once when the field is left; the server text at Save (V16) | yes | yes; a client entry blocks Save on the client (measured in #9) |
| R11 Storage not below Memory | state message on the Storage row and on the product (`error()` with the two attribute names) | after leaving the Storage field; at Save also when only Memory changed (no mirror branch, D11) | yes, on Storage only | yes, one entry under the Details group with the subtitle "Storage" (group and subtitle are V8's finding) |
| R12 guard | state message, API only | never while editing in the form; at Save only for a draft whose battery value was written outside the form | yes on the Battery Life input if it ever appears (the input binds `numberValue`), but the row is disabled then: V21 records what a red disabled input looks like | yes, if ever |
| R13 power of two | state message on the Memory row and on the product | after leaving the Memory field; at Save | yes | yes |

Order at Save (research P8d): input validation (`@mandatory`, format, range, types) refuses first and alone. The constraint messages the draft already carries stay visible, but a constraint that has not fired yet (its fields were never touched in this draft) is reported only on the next Save, after the input errors are fixed. See "Save and the second round".

### Required markers and the create flow

The marker is the asterisk in front of the label text, rendered by the framework from `Common.FieldControl` in the FE sections and by `DetailsForm.js` from the assignment in the Details section. A marker blocks nothing by itself; the server rule behind it does (ADR-0025 point 3, ADR-0028 decision 4).

| Field | Marker | Source | When it changes |
|---|---|---|---|
| Name, Price, Currency, Stock, Category | always in edit mode | static `@mandatory` (exists) | never |
| Subcategory | once a category is set; disabled and unmarked before | `(category.code is null ? 0 : 7)` (ADR-0025, exists) | on the client when Category is committed |
| Description | while Stock is above 0; unmarked at 0 or empty | `(stock > 0 ? 7 : 3)` (R6, new) | on the client when Stock is committed (field left or Enter), before the server answers, no request needed; clearing Stock or setting 0 unmarks it; the marker stays while the field is filled |
| Image URL, Rating | never | optional | |
| Details: a required attribute of the subcategory (D6: Screen Size on Laptops; Sensor Resolution on Mice; Maximum Load on Seating; Power and Capacity on Appliances; Capacity on Drinkware; Thickness on Fitness) | in edit mode only, like the FE sections | `SubcategoryAttributes.required` from the row's expanded assignment, `isRequired(row, subcategoryCode)` (R8, new); set with `labelFor` in `applyLabelTarget`, so display mode shows none | when the rows are built or rebuilt (Edit, subcategory change); hidden in display mode, where no FE label carries a marker either |
| Details: every other attribute | never | | |

Create (the plus button of the List Report, a new draft): before anything is typed, Name, Price, Currency, Stock and Category carry the marker; Subcategory is disabled without a marker; Description, Image URL and Rating have none; the Details section shows the existing hint "Select a subcategory to fill in the details.". Choosing a category enables and marks Subcategory. Choosing a subcategory lets the server create the detail rows, and the Details form shows them with the marker on the required ones (Laptops: Screen Size marked, Memory (RAM) and Storage not), with the range hint in every empty numeric input (Laptops: "10–18" in, "4–128" GB, "32–8,192" GB under D12) and, on a new mouse, with the Battery Life row disabled and hinting "Depends on Connectivity" until a wireless value is chosen (see "R12"). Typing a stock above 0 and leaving the field marks Description at once; if Description is still empty, the R6 message follows on both fields in the same step (see "R6 and R7").

Edit of an existing product: the same markers, Description marked for every seeded product (all have stock above 0). A seeded product carries no message after Edit: its required details are filled and no rule is violated by the seed (research sections 8 and 10.1). A seeded numeric detail shows its value ("15" with "in" after it), so its range hint is not visible until the field is emptied (UX risk 21); Wireless Mouse shows Battery Life enabled and empty with the hint "1–2,000".

### R1 and R2: Name

- R1: the user types a name shorter than 3 characters after trimming (`AB`, ` A `) and leaves the field. The field turns red with `PRODUCTS_NAME_TOO_SHORT`; the popover lists it under General Information with the subtitle "Product Name". A corrected name clears both when the field is left.
- R2: the user types a name that another product has, in any case and padding (`backpack `), and leaves the field: same rendering with `PRODUCTS_NAME_DUPLICATE`. The product's own name never triggers it (Edit of Backpack, retype `Backpack`, Save: no message). A name another user is drafting at the same time is not detected until that draft is saved; the later Save then fails with this message (plan risk, by design).
- Both at once are not reachable with the seed (a one- or two-letter duplicate does not exist); if a name violated both, the field would carry two entries (UX risk 2).
- `@mandatory` on Name is unchanged: an empty Name is reported at Save only.

### R3 and R4: Price and Currency

- R3: the user types `0` or a negative price and leaves the field. Expected (not verified by MCP; verifier V5): the client `Decimal` type carries `minimumExclusive` from the new `Validation.Exclusive`, so the field turns red at once with the framework text (expected "Enter a number greater than 0", the UI5 core text `EnterNumberMinExclusive`, in `ru` from the UI5 bundle), no `PATCH` is sent, nothing is stored, and Save is refused on the client with the entry in the popover (the behaviour measured in #9 for a client validation message). The project text `PRODUCTS_PRICE_POSITIVE` is then seen by API clients and in the import's row errors, not on this screen. If the verifier finds that the client ignores the exclusive bound, the server text appears in the `PATCH` response like R1. Either way the user sees one immediate message on Price. Decision for the user: Q2.
- The existing client checks stay: more than two decimals (`10.505`) and a non-number are refused by the type with framework texts.
- R4 without D13a (today's field): the user has a currency without decimal places (`JPY`; 33 of the 204 standard currencies) and a price with decimals (`10.50`), in either order: `JPY` chosen on a draft that holds `10.50`, or `10.50` typed with `JPY` set. After the second field is left, Price and Currency both turn red with the same text `PRODUCTS_PRICE_MINOR_UNIT`, and the popover shows one entry (expected: the V4 model keeps one `sap.ui.core.message.Message` with two targets; verifier V4). Fixing either side (price `11`, or currency `USD`) clears both fields in one step, because the constraint re-runs when either target is touched. At Save the server reports the first target only (research): Price red, one entry.
- R4 with D13a (the optional control: `@CodeList.CurrencyCodes` on the service and `Common.UnitSpecificScale` on `Currencies/code`): the Fiori Elements price field is a `sap.ui.model.odata.type.Currency` composite whose customizing then knows that `JPY` has 0 decimals. What the user would see: with `JPY` set, typing `10.50` and leaving Price turns the field red at once with the UI5 currency type's text (expected: a framework text naming the allowed decimals, in `ru` from the UI5 bundle), no request is sent, nothing is stored, Save is refused on the client with the entry in the popover. The other order (`10.50` stored, then `JPY` chosen) is the open point: either the composite type re-validates the amount when the currency part changes (then Currency or Price turns red on the client, framework text, no request) or it does not (then the `PATCH` of the currency goes out and the server's two-target message of the paragraph above appears on both fields). V23 records both orders. Consequence for the showcase: with D13a the two-field highlight of R4 is seen on the screen only on the path the client does not check, or never; the project text keeps the API and the import. With the user's principle, the control wins and the two-target message becomes the API guard (UX risk 24); the R6 two-field highlight stays the showcase of a multi-target message on the screen.
- Both fields are in the same section (Pricing & Stock), so the two red fields are visible together, as the FE document requires for a multi-target message.

### R5: Image URL

The user types an address that does not start with `https://` or contains a space (`http://example.com/a.png`, `https://example.com/a b.png`) and leaves the field: red with `PRODUCTS_IMAGE_URL_HTTPS`, entry under General Information. An empty Image URL stays allowed (optional field; `null` passes the format check). The header image keeps the stored (active) image while the draft is edited; a wrong draft URL cannot be saved, so a broken header image never reaches display mode.

### R6 and R7: Description and Stock

- Marker: Description is marked while Stock is above 0 (table above).
- R6 message: the rule fires when Stock is committed above 0 while Description is empty, and when Description is emptied while Stock is above 0. Both fields turn red with `PRODUCTS_DESCRIPTION_REQUIRED_IN_STOCK`, one popover entry (expected; verifier V3). Description is in General Information and Stock in Pricing & Stock: both are on the one page but not always in one view, so the user who typed Stock sees Stock red and reads the text there; the popover entry navigates to Description. The text is therefore written to read naturally on Stock as well ("Enter a description. Products in stock are visible to customers."). Typing a description and leaving the field clears both; setting Stock to 0 clears both and removes the marker.
- At Save the message is on Description only (first target). Expected (V3): the Fiori Elements client check of required fields refuses the Save of an empty marked Description before any request, with the framework text "Provide the missing value." as for the static `@mandatory` fields; the server text then appears only on a draft whose Stock was set through the API.
- Alternative the user can choose (Q1): a single-target constraint on `description` (D8 alternative). Then typing Stock marks Description but shows no message; the message appears when Description itself is left empty after being touched, and at Save. That is the conventional "required field, checked at Save" behaviour of a Fiori form; the recommended two-target form is the showcase of the inter-field dependency the FE document describes, and it explains on the spot why Stock made Description required.
- R7 (optional): a description that only repeats the name (` backpack ` on the product `Backpack 2`; case and padding ignored) turns Description red with `PRODUCTS_DESCRIPTION_EQUALS_NAME` when the field is left. R6 and R7 cannot fire together (one needs an empty, the other a filled description). R7 fires while editing only when Description is touched; a rename that makes Name equal to the description is reported at Save.

### R8: required details

- Marker: on the label of each required attribute of the product's subcategory, edit mode only.
- TEXT, INTEGER, DECIMAL, LIST: the user empties a required field (clears Screen Size on Laptop Pro 15) and leaves it. The input turns red with `PRODUCTS_DETAIL_VALUE_REQUIRED`; the row message is also written on the product, so the message survives the reads that other field changes trigger. The popover entry is expected under the Details group with the attribute name as subtitle; the framework derives both from the control's place in the page, and the verifier records what appears (V8). Entering a value clears it when the field is left. An emptied numeric field shows its range hint again (the placeholder returns when the value is gone), so the red field and the hint "10–18" are visible together: the message says that a value is needed, the hint says which (UX risk 17).
- Save with an empty required detail is refused; the activation error targets `in/details(ID=...,IsActiveEntity=false)/numberValue`. Expected: the same input shows the Error state and the popover entry navigates to it. The plan's fallback, if the activation error stays popover-only, is a client validation message of the B6 shape added at commit; the user's view is the same except for the moment the red state appears.
- MULTI_LIST: the rule targets `attribute_code`, which no control of the form binds. The message appears in the popover only, without a field highlight and without navigation on click; the marker on the label is what points the user to the field. With D6 as proposed no MULTI_LIST attribute is required, so this case is not reachable on the screen (Q3).
- The counter badge "Filled N of M" stays Warning while any enabled field, required or not, is empty; it is a completeness indicator, not a validation indicator. The only change of this feature: a disabled row is outside N and M (see "R12").

### R10: bounds per subcategory

The control. A numeric detail row (INTEGER or DECIMAL) applies the bounds of the product's subcategory assignment (`SubcategoryAttributes.minValue`/`maxValue`; the attribute's own `minValue`/`maxValue` when the assignment has none) as the `minimum` and `maximum` constraints of its `Decimal` type (`numberTypeSettings(attribute, assignment)`, the existing per-row type of ADR-0027 B5), and shows the same bounds as a hint:

- Where: the placeholder of the input (`sap.m.InputBase#placeholder`: "a short hint intended to aid the user with data entry when the control has no value"), the slot Fiori Elements fills from `UI.Placeholder` on its own fields and the slot the Input Mask document pairs with a format rule. The unit stays where it is, after the input (`description`), so the row reads "[10–18] in": label "Screen Size" with the marker, the hint inside the empty field, the unit after it. No extra control, no extra line, nothing in display mode (the placeholder is a property of the edit control, which display mode does not render).
- Format: `{0}–{1}` with an en dash (U+2013, no spaces), the bounds formatted by the row's own `Decimal` type, so the decimal separator, the grouping and the number of decimals follow the locale and the attribute's scale: `en` "10–18", "4–128", "32–8,192", "400–32,000", "0.2–10", "0.1–2"; `ru` "10–18", "32–8 192" (the UI5 `ru` locale groups with a space and uses a comma: "0,2–10"). INTEGER rows never show decimals. One-sided bounds, not in the seed (every numeric assignment and every numeric attribute has both): "from {0}" / "up to {0}". The texts are three keys of the app bundle ("Texts"); `test-ui` asserts the input's `placeholder` property (`iSeeTheRangeHint(name, text)` of the plan reads it).
- Outside the range: the user types `19` in Screen Size and leaves the field. The type refuses it at once: the field turns red with the framework text (expected "Enter a number between 10 and 18", UI5 core `EnterNumberMinMax`, `ru` from the UI5 bundle), the typed `19` stays in the field (the placeholder is hidden by it; the error text names the bounds instead), no `PATCH` is sent, the stored value is unchanged, and Save is refused on the client with the entry in the popover (measured in #9 for a client validation message). Correcting to `15` writes it and clears the state. The same for `9`. The global bounds of the attribute (1–100) are never reached from the screen: the assignment's bounds are inside them.
- The project text `PRODUCTS_DETAIL_VALUE_OUT_OF_SUBCATEGORY_RANGE` on this screen: only for a value the client never validated. Two reachable cases: (a) a subcategory change that keeps a row whose value is outside the new bounds (Wireless Mouse with Battery Life `500` h, Subcategory changed from Mice to Audio: the server keeps the Battery Life row because Audio assigns it too, the Sensor Resolution row is removed with the #9 warning, and `500` is outside Audio's 1–100): the input shows "500" with the new type behind it (the type validates user input, not a stored value), so nothing turns red until Save; the activation error then targets the row and the field shows the project text (V16, the same custom-control question as V8); (b) a product created through the API with a value outside its assignment's bounds, likewise at Save. The two texts for one rule (framework while typing, project at Save) are the R3 pattern (UX risk 1).
- Create flow: the rows of a new subcategory come with their hints; the user sees the allowed range before typing.
- Subcategory change: the rows are rebuilt from the new assignments (`clearFormElements` on the refresh of the `details` binding), so the hints and the bounds follow the new subcategory at once; a row that survives the change (Capacity across Appliances, Drinkware and Bags; Battery Life across Mice and Audio) shows its new hint when empty and its kept value otherwise (UX risk 18).
- Alternative B the user can choose (Q5): an always-visible hint line under the input (a `sap.m.Text` as a third field of the row, in edit mode only, placed before the input in `fields` so that `ariaDescribedBy` never points forward in the DOM, a11y skill topic 7). Cost: one more line in every bounded numeric row (every numeric row of the seed), uneven row heights in the 4-6 column layout, a second place that must be hidden in display mode, and a text that repeats what the error message says. Gain: the range is visible while the field is filled. Recommended: the placeholder; the framework hint slot, the create flow (empty fields) is where the hint prevents, and a filled field that is edited gets the bound-naming error the moment it leaves the range.

### R11: Storage not below Memory

No control: a client comparison of two rows would duplicate the server rule without making the mistake impossible (both fields stay editable), so the message is the whole UX. Data-driven: `DetailAttributes.atLeast` (`STORAGE` -> `RAM`); the texts name the attributes in the user's language.

- While editing, the Storage row touched: on Laptop Pro 15 (Memory 16, Storage 512) the user sets Memory `128`, then Storage `64` and leaves the field. The Storage input turns red with "Storage must not be below Memory (RAM)." (the `error()` arguments are the localized attribute names, research 10.3 A14 and A17); the popover shows one entry under the Details group (V8's finding) with the subtitle "Storage". Storage `256`, Tab: clears. Memory `32` with Storage still `64`: the Memory field is touched, not Storage; the Storage message stays until Storage is touched or the next read (the message is a state message on the Storage row and on the product; the `DraftMessages` read after the Memory `PATCH` re-evaluates the product's rows: expected that it clears, V17 records).
- Only Memory changed: Storage `64` first (above Memory 16, no message), then Memory `128`, Tab: no message, nothing red (no mirror branch, D11 recommended: one defect, one message). Save: refused with the message on the Storage row, the popover entry navigates there (V18). The user who edited Memory finds the error on Storage, which the text explains by naming both. With the mirror branch (D11 alternative) the message would appear live on Memory and twice at Save (A18, A15), which the plan's risk lists; not recommended.
- D12 consequence: with the user's bounds (Memory 4–128, Storage 128–8,192) a storage below the memory is never inside both ranges, so on this screen R10's client bound refuses the value first (Storage `64` is outside 128–8,192: framework text, no request) and R11 is never seen; it would only show for API data. With the architect's Storage 32–8,192 the hint reads "32–8,192", `64` passes the bound and R11 shows live as described. Recommended for the showcase: 32.
- `ru`: "Znachenie <Storage ru> ne mozhet byt menshe znacheniya <Memory ru>." with the attribute names from `DetailAttributes.texts.csv`; a draft message keeps the locale of the request that wrote it (research 10.6), which the Fiori session never mixes.

### R12: Battery Life follows the wireless connectivity

A control, not a validation (user decision). Data-driven: `DetailListValues.enables` (`BLUETOOTH_5_0`, `BLUETOOTH_5_3`, `WIRELESS_2_4_GHZ`, `WIFI` -> `BATTERY_LIFE`); the form reads `attribute/enabledBy` of the dependent row and the selected codes of the product's MULTI_LIST rows (`isEnabled(row, selectedCodesByRow)`), re-evaluated when the rows are built and after every `selectionFinish` of a multi combo box.

- The disabled state: the Battery Life input is `enabled=false` (not `editable=false`): the control is greyed, cannot be focused and is out of the tab chain (`sap.m.InputBase#enabled`), the same state the Subcategory field has before a Category on this page (ADR-0025, `FieldControl` 0 measured as disabled in #8), which is the project's precedent for "not applicable in this state". Read-only would keep it in the tab chain and let the user copy a value that cannot exist: wrong signal. The label stays normal (no marker: a dependent attribute is never required in D6; if one ever were, the marker would still show, UX risk 17). The unit "h" stays after the input. The value is empty.
- The hint: the placeholder of the disabled input reads "Depends on Connectivity" (`en`) / "Zavisit ot polya <Connectivity ru>" (`ru`), with the enabling attribute's localized name as `{0}` (`enabledBy` codes belong to one list attribute; the form finds its name in the product's own row of that attribute, so no extra request). The text is data-driven like the rule; it tells where to look, and the row enables the moment a suitable value is chosen, which is the feedback that completes the explanation. A seed-specific wording ("Available for wireless products") reads better in a demo but is wrong for any other dependency the data may define: offered in Q4 as the alternative. A disabled input renders its placeholder greyed (expected, V19 screenshot checks that it is legible in `sap_horizon`).
- Enabling: the user selects a wireless value in Connectivity (list closes, or a token appears); the Battery Life input becomes enabled and empty, the placeholder switches to the range hint ("1–2,000" on Mice, "1–100" on Audio), the counter changes from "Filled 2 of 2" (Success) to "Filled 2 of 3" (Warning): the badge is the nudge to fill the row that just opened. Keyboard: Tab from Sensor Resolution now reaches Battery Life.
- Disabling and clearing: the user removes the last wireless value (Wireless Mouse: remove Bluetooth 5.0, still enabled because Wireless 2.4 GHz remains; remove Wireless 2.4 GHz: disabled). If the row held a value (the user typed `12` before), the form writes `null` to the row (`setProperty`, the proven write path) and the input shows empty and disabled with the dependency hint; the counter goes back to "Filled 2 of 2" Success. A `MessageToast` names it, only when a non-empty value was cleared: "Battery Life cleared: it depends on Connectivity." (3 s, bottom centre, no action). Why a toast and not a dialog or a field warning: the clear is the direct consequence of the user's own action on the field next to it, needs no decision and no fix (a confirmation dialog would block a routine edit; a Warning value state on the Connectivity field would stay until something clears it and has no counterpart in the project's client messages), and the draft itself is the undo (Discard Draft restores the value; re-selecting the wireless value re-enables the row, the value is typed again: one re-entry, the plan's accepted cost). No undo button. The toast is the first in the app (no `MessageToast` in `webapp` today); it follows the `sap.m.MessageToast` rule learned in #9 (not for errors or warnings; this is an information). Alternative the user can choose (Q6): no toast, the greyed empty row and the counter are the only feedback.
- Create flow (new mouse): Category Electronics, Subcategory Mice: the three rows appear with Battery Life disabled and hinting "Depends on Connectivity" at once (no selection yet). Connectivity "Wired (USB)": still disabled. Add "Bluetooth 5.3": enabled, hint "1–2,000". The same on Audio, where Battery Life is the row right after Connectivity: a user who closes the Connectivity list with Tab moves to the next tab stop before the row is enabled, so Battery Life is skipped once (UX risk 22, V20).
- Edit of a product whose data was written outside the form (API: Wired (USB) with Battery Life 12): display mode shows "12 h" as stored (display mode has no disabled state: the row is a text). Edit: the rows are built in edit mode, the row is disabled and cleared at once, the toast names it; Save stores the empty value, Discard restores "12 h" (V21). This is the one moment the form changes data without a field action of the user; the toast and the Discard path make it visible and reversible (UX risk 23).
- The server guard `PRODUCTS_DETAIL_VALUE_NOT_ENABLED` is never produced by the form: a disabled row sends no value, and the clear precedes any Save. It is reachable only through the API (a value typed in another client after the wireless selections were deleted, research 10.4 A25-A27) and is marked "guard, not user-facing" in the bundle; if it ever reaches the screen (a draft written by two clients), it targets the Battery Life row's `numberValue` and lands in the popover with the row disabled (V21 records whether a disabled input shows a red state).
- Counter rule: a disabled row is outside "Filled N of M" (`countFilled` skips it): a wired mouse with Connectivity and Sensor Resolution filled is "Filled 2 of 2" Success, not "2 of 3" Warning forever for a row that cannot be filled. Confirm in Q7.

### R13: Memory is a power of two

- Without D13b (recommended by the architect): the user types `12` in Memory (Laptop Pro 15) and leaves the field. The value is inside the bounds (4–128), so the client accepts it and writes it; the `DraftMessages` read of the same batch brings `PRODUCTS_DETAIL_VALUE_NOT_POWER_OF_TWO` ("Enter a power of two, for example 8, 16 or 32."): the field turns red, one popover entry under Details with the subtitle "Memory (RAM)". `16`, Tab: clears. Save with `12` is refused with the entry (V22).
- With D13b (optional control): the Memory input has `showSuggestion` with the items `4, 8, 16, 32, 64, 128` from `DetailAttributes.suggestions`; typing `1` opens a popup with "16" and "128", typing `12` shows "128" only, typing `3` shows "32"; an item is chosen with the arrow keys and Enter or a click; a value that matches no item (`12`) is still accepted by the input and reaches the server rule as above (suggestions do not restrict). On a phone the input "will first open a dialog where the input and suggestions are shown" (`sap.m.Input#showSuggestion`), a different interaction from every other numeric field of the form. UX view: a suggestion popup on a number field that is not a list makes the user expect the list to be exhaustive (256 GB and 512 GB are valid) and makes one numeric row behave unlike its neighbours; the bounds hint "4–128" plus the message already make the mistake rare and explain it. Agree with the architect: no (D13b), the row stays a plain number input.

### Save and the second round

- Save refused on the client: when a client validation message exists (R3 expected; R10's bound; type errors; the list message "Select a value from the list." of #9; [D13a] the currency decimals), the popover opens with the entry and no request is sent (measured in #9).
- Save refused by the server (400 on `draftActivate`): for `@mandatory` and for every rule still violated, including R11 when only Memory was edited and R10 for a kept value. The user stays in edit mode, the draft keeps its values, each reported field is red with its text, the popover lists them (verifier V10 records whether the popover opens by itself after the 400 or on the footer button).
- Two rounds: when a Save carries an input-validation error (an empty mandatory field, a format error, a range error) together with a constraint violation that was never shown during this edit (its fields were not touched: an untouched empty required detail of a product created by the import, a description emptied through the API, a storage below the memory where only Memory was edited), the first Save reports the input errors only; the second Save, after they are fixed, reports the constraint. Draft messages the user already saw while editing stay visible through both rounds. In normal editing the second round does not occur, because every constraint message appears when its field is left.
- After a successful Save the page switches to display mode: no markers, no hints, no disabled rows, no messages, no footer button.

### List Report and display mode

Nothing changes in the List Report: columns, filters, the draft and lock marker, the import action and the row count are as before. A draft that carries messages looks like any other draft in the list (UX risk 14). The Object Page in display mode shows no marker, no range hint, no disabled state and no message (state messages are not supported in display mode, FE doc steps 1 and 8); a dependent row shows whatever value is stored, also an inconsistent one written through the API.

## Empty state and errors

- No messages: no footer message button, every field in the None state, markers as in the marker table, the range hint in every empty numeric detail, the dependency hint in a disabled Battery Life row. This is the state of every seeded product after Edit.
- Message popover (framework `sap.m.MessagePopover` behind the footer button): entries grouped by section title ("General Information", "Pricing & Stock"; the group of a Details message is verifier item V8), the entry title is the message text, the subtitle the field label; errors above warnings (framework); a click or Enter on an entry scrolls to the field and focuses it (FE doc step 8). The popover's severity filter stays (framework).
- How many at once: one entry per violated rule. A field carries two entries only when two rules of different kinds fail on it (a format error of the `PATCH` plus a constraint written at its commit), which no seeded case produces. A two-target message (R4, R6) is one entry (expected). The `@mandatory` entries after Save add one per empty field; the known #8 behaviour stays: with an empty Category the disabled Subcategory is listed too.
- After fixing one field: when the field is left, the message read of the same batch removes its entry and its red state; the footer count drops; at zero the button disappears. A message raised by a failed Save stays on the field and in the count until the next field change or Save triggers a read (measured in #8 for the subcategory).
- Discard Draft removes the draft with its messages; display mode shows the active values, including a Battery Life value the form cleared in this draft.
- Keep Draft and reopen: the state messages are persisted on the draft and appear again on the fields when the draft is opened for editing (expected; verifier V11).
- The toast of a cleared row (R12) is the only transient notification of the feature: 3 s, bottom centre, closes on touch, no entry in the popover, no footer count.

## Accessibility

Checklist of the `ui5-best-practices-accessibility` skill (topics 2 labeling, 4 focus and keyboard, 6 invisible messaging, 7 reading order apply; 1 landmarks, 3 headings, 5 shortcuts, 8 target size are unaffected by this feature):

- Labels and the required marker: the FE fields keep their framework labels with `labelFor`; a required label gives the labelled control `aria-required="true"` (UI5 `LabelEnablement`, framework), so a screen reader announces "required" for Name, Price, Currency, Stock, Category, the enabled Subcategory, and Description while Stock is above 0. In the Details form `labelFor` is set in edit mode only (ADR-0027 amendment), so `setRequired(true)` on the row label gives the input `aria-required` in edit mode and nothing in display mode, where no marker is shown either: consistent with the FE sections. Expected, verifier V14 (DOM check).
- Hints: the range hint and the dependency hint are the input's native `placeholder`, which the skill's labeling reference itself shows on an `Input` next to its label; a screen reader reads a placeholder when the field is empty (expected, V14), and the field's label stays the accessible name (the placeholder never replaces a label, skill topic 2). No `ariaDescribedBy` is needed for the placeholder. With alternative B of Q5 the hint text must precede the input in the DOM and be referenced by `ariaDescribedBy` (skill topic 7: no forward references).
- Disabled row: `enabled=false` removes the Battery Life input from the tab chain and from focus; a screen reader in browse mode still reads the label, the greyed placeholder "Depends on Connectivity" and the unit in DOM order, so the reason is available without focus. No `aria-disabled` is added by hand: the framework renders the native disabled state.
- Invisible messaging (skill topic 6: a dynamic state change that is visible only is a finding): the clear of a dependent row is announced with `sap.ui.core.InvisibleMessage#announce(text, Polite)` using the toast's text, in the same handler that clears the row; whether the `MessageToast` itself is announced is a verifier DOM check (V19), and if it is, the explicit announcement is dropped to avoid a double reading. The enabling of the row needs no announcement: the user is on the Connectivity field, and the next Tab lands on the newly enabled row (on Mice after Sensor Resolution; on Audio directly).
- Value state: `sap.m.InputBase` renders `aria-invalid="true"` on an Error and announces the value state text as the field's description (`aria-describedby` to the hidden value-state text) and shows it in the pop-up on focus; framework behaviour, the only custom part is the text. No custom `valueStateText` is set by the Details module for these rules (the rule of #9: never a `valueStateText` without an Error state); the R10 client text comes from the type, like the existing decimals text.
- Keyboard and focus: the footer message button is in the Tab order; Enter opens the popover; arrow keys move through the entries; Enter on an entry navigates and focuses the field (framework, FE doc step 8); Esc closes. After a refused Save focus must land in the popover or stay on Save, never be lost (verifier V12). Removing a Connectivity token with the keyboard (Backspace) keeps the focus in the multi combo box (REVIEW R2-D6 of #9) while the Battery Life row changes state two cells away; the toast and the announcement cover it.
- Reading order: unchanged DOM order; a message on Stock about Description relies on the popover navigation, which is keyboard-reachable; a message on Storage about Memory names Memory in its text.
- Headings: unchanged; each section title is one H2 (measured in #9).
- Contrast and colour: the Error state is framework-rendered (red border, icon and text, not colour alone); the marker is a text character; the disabled state is the theme's (reduced opacity, exempt from the contrast rule as an inactive component), and the placeholder in it must still be legible (V19 screenshot).

## Theme and tokens

Standard controls only, `sap_horizon`: the required marker, the value states, the message popover, the footer button, the Details inputs with their placeholder, description and disabled state, the toast and the counter badge are framework-rendered. No custom CSS, no custom colour, no style class is needed or allowed; the one custom module touched (`DetailsForm.js`) sets properties the controls already have (`required`, `placeholder`, `enabled`, the type constraints) and shows a `MessageToast`. Guideline reference: `mcp__ui5-mcp-server__get_guidelines` (data binding, built-in types for formatting, no globals, keys in every locale; section 4 form rules already met by the existing `Form` + `ColumnLayout`).

## UX risks

1. R3 shows two different texts for one rule: the framework's client text on the Object Page (expected) and the project text in the API and the import. Notice: V5 records a text that is not in `_i18n`. If the user wants the project text on the screen, the only declarative way is to state R3 as an `@assert` constraint instead of `@assert.range` (then no `Validation.Exclusive`, no client check, the message comes with the `DraftMessages` read like R2, and the import needs a per-row pre-check): Q2. The same split holds for R10 by design (framework text while typing, project text only for a kept or API value, V15 and V16).
2. Two entries on one field: a format error (in the `PATCH` response) and a constraint message (written at the same commit) can coexist on Name or Price. Notice: two popover entries with the same subtitle. Not reachable with the seed; acceptable when it occurs, both texts are true.
3. Marker timing on Description: the marker switches when Stock is committed, so with the keyboard the user sees it change on Tab, not while typing; it switches before the server message arrives, so two visual changes follow each other (marker, then red state). Notice: V3; acceptable, both are immediate.
4. A message on a field the user has not reached yet: in the create flow the R6 text appears on Description (above, possibly out of view) the moment Stock is left; the Stock field itself is red with the same text, which is why the text names the description. With Q1's alternative this risk disappears and the message moves to Save.
5. The MULTI_LIST required message cannot highlight or navigate to its field; only the label marker points to it. Mitigation if Q3 adds such an assignment: the architect checks whether `error()` can pass the attribute's localized name as `{0}` (research section 10.6 proves the mechanism), so the entry at least names the field; otherwise the popover entry reads "Fill in this detail..." with no field reference.
6. The activation error of R8, R10 (kept value), R11 (only Memory edited) and R13 may stay in the popover without a red input (plan risk): the user sees the entry, clicks it, and may not land on the field. Fallback in the plan (client validation message at commit). V8, V16 and V18 decide.
7. A two-target message may be rendered on one field only (plan risk): then R4 and R6 look like single-field rules while editing; the texts still name both fields implicitly. V3 and V4 decide; the OPA5 cases adapt.
8. The second Save round (research P8d) surprises a user who edits a product created by the import or the API: the first Save shows only the mandatory or format errors, the second one the constraints. Notice: V10. Mitigation is documentation (this file, TESTING); no mechanism changes the cds order.
9. A message raised by a failed Save stays on the field after the user fixes the value, until the next read (measured in #8): the field may look red a moment longer than the user expects. Notice: V13 after V10.
10. The group and subtitle of a Details message in the popover are framework-derived from a custom control's position and may read "General" with an empty subtitle. Notice: V8. Acceptable; the entry still navigates when the target binds.
11. Mixed authorship of texts in one popover: the cds text "Provide the missing value.", the UI5 texts for R3 and R10 and the project texts of this feature. All are imperative single sentences in both locales, so the mix is consistent; notice any `ru` text in the popover that is English (an untranslated framework key).
12. With an empty Category the disabled Subcategory is still listed as missing (#8 F1, accepted behaviour); unchanged by this feature.
13. R2 is not seen between two concurrent drafts until the first Save (plan risk); the second user gets the message at Save, not while typing.
14. A draft with errors is indistinguishable from any other draft in the List Report (the marker says "Draft" only); the user finds the errors on opening it. Standard Fiori Elements, no change proposed.
15. The Stock field turns red for a rule about Description, and Currency for a rule about Price: a user may try to "fix" Stock. The shared text names the field to fill ("Enter a description", "Enter the price as a whole number"), which is why the proposed texts lead with that action.
16. Clear-on-disable surprise (R12): a user who removes a Connectivity token loses a typed Battery Life two cells away, at once and without a question. Notice: V19; the greyed empty row, the counter drop, the toast and the announcement are the mitigations; Discard Draft and a re-entry are the recovery. With Q6's "no toast" answer the only feedback is the row and the counter, which a user looking at the token may miss.
17. Two or three signals on one row: the required marker on the label, the range hint in the field and the unit after it (Screen Size on Laptops: "* Screen Size [10–18] in"); after emptying a required field the red state, the message pop-up and the hint show together. Notice: V2 and V8 screenshots; acceptable, each signal is in its own slot and says a different thing; the hint never repeats the unit.
18. The hint changes on a subcategory switch, and a kept value may be outside the new bounds without any red state until Save (V16): the user sees "500 h" on an Audio product whose hint, invisible behind the value, is 1–100. Notice: V16; the Save message names no bound (a constraint text carries no arguments), so the user must empty the field to see the hint or read the framework text when typing a new value. Mitigation if it matters: alternative B of Q5 (always-visible hint) makes the kept value's problem visible at once.
19. R11 unreachable within the user's bounds (D12): with Storage 128–8,192 the client bound refuses every storage below the memory before R11 can fire, so the showcase of a cross-row rule would never be seen on the screen. Notice: V17 would end at the R10 framework text. Recommended: Storage 32–8,192.
20. The counter and a disabled row: with the disabled row inside M, a wired mouse reads "Filled 2 of 3" Warning forever and the badge loses its meaning; with it outside M (recommended), the badge jumps from Success to Warning the moment a wireless value is selected, which looks like a step back to a user who just made the product "better". Notice: V24; the second effect is the intended nudge to fill the opened row.
21. The placeholder hint disappears while the field has a value: a user editing a seeded value (15 in) never sees "10–18" unless the field is emptied; the framework text names the bounds the moment a value leaves the range. Notice: V15; alternative B of Q5 removes the risk at the cost of a line per row.
22. A row enabled by another field is skipped once by the Tab that closes the enabling list (memory of #8 for a combo box that commits on focus leave): on Audio products Battery Life follows Connectivity directly. Notice: V20 records it; acceptable (Shift+Tab reaches the row), no mechanism proposed.
23. The form changes data without a field action of the user when a draft with an inconsistent dependent value (API, or another client) is opened for editing: the Battery Life value is cleared on build. Notice: V21; the toast and the announcement make it visible, Discard makes it reversible; a value that the guard would reject at Save anyway.
24.
