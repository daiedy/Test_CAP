## Important

- `app/products/webapp/ext/fragment/DetailsForm.js:698` R2-D6 (brief item 1) is caused by this module, not native MultiComboBox behaviour. `syncSelections` runs on every `change` of the row's `selections` binding and always calls `multiComboBox.setSelectedKeys(codes)`. In UI5 1.153.0 `setSelectedKeys` calls `removeAllSelectedItems()` once the first keys are set (MultiComboBox-dbg.js 3034-3045). That runs `removeSelection` with `tokenUpdated` false and so `tokenizer.removeToken` for every remaining token, then `addSelectedKeys` creates new tokens. On the keyboard path, Backspace on a focused token goes through `Tokenizer#_handleKeyboardDeletion`: it fires `tokenDelete`, then `_applyFocusAfterDeletion` focuses the neighbouring token. Then `MultiComboBox#_handleTokenDelete`/`_removeSelection` fires `selectionFinish`, `onSelectionFinish` calls `context.delete()`, and the binding `change` makes `syncSelections` rebuild every token. The token that had just received the focus is removed, so the focus falls to `body`. The add path (F-1) keeps the focus because the focus is in the input, which the rebuild does not replace. This contradicts SCREENS "Accessibility", topic 4 ("a second Backspace (or Delete) removes it"; Tab-based keyboard flow) and scenario 9. The data is correct, so the finding does not block. → `fiori-app-dev`: in `syncSelections`, reuse the existing pure `diffSelections` and set the keys only when they really differ: `const delta = diffSelections(multiComboBox.getSelectedKeys(), codes); if (delta.added.length || delta.removed.length) { multiComboBox.setSelectedKeys(codes); }`. After a user's own add or remove the control already holds the binding's keys, so nothing is rebuilt and the native focus handling stays. A failed `DELETE` restores the context, the keys differ again, and the control is re-synced. Prove it with `ui-verifier` scenario 9 (`document.activeElement` after the second Backspace) and the OPA5 criterion 64 journey. If the orchestrator has no fix round left, `docs-keeper` adds a STATE "Open debt" row with this exact fix.

The cost is one own `GET .../details` per page load and per Edit (VERIFICATION final re-check, CHANGELOG 2026-10-12 "Details rows binding with its own cache").
