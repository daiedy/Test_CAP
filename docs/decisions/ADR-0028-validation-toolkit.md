# ADR-0028: Validation toolkit: custom texts, uniqueness, two-target constraints, conditional requirement, rules on detail rows, prevent before validate

Date: 2026-10-13, amended 2026-10-14. Status: proposed (feature `products-validations`; decision by the user pending).
<!-- On acceptance replace the whole Status sentence with the accepted form; never append to the proposed one. -->

## Context
Issue #10 asks for Object Page validations through annotations, and the user's addition makes it a showcase: logical constraints over every field that deserves one, including the typed details of #9, with a handler only where an annotation cannot express the rule. At the plan gate (2026-10-14) the user added rules on the details (bounds per subcategory assignment, a rule between two detail rows, a set-membership rule on one attribute, a dependency between a list value and another attribute) and the principle that every rule follows: prefer a control that makes the mistake impossible over validating after the fact; the server constraint stays the guard on every path. `PATTERNS.md` has rows for `@assert.format`/`@assert.range` ("Format or range check"), for `@assert: (case ...)` constraints with null guards and `exists` set membership ("Cross-field consistency check", ADR-0024, ADR-0026), for the typed value rules of a detail row ("Typed attribute values", ADR-0027) and for a dynamic `Common.FieldControl` on a dependent field ("Field editable only when another field is filled", ADR-0025). What the showcase needs and no row has: a project text for a format or range rule, a uniqueness rule a Fiori user sees on a draft-enabled root (the row forbids `@assert.unique` inside a draft tree, and ADR-0026 measured a 500 on SQLite), a constraint message that marks two fields or carries data from the row, a field that is required only while another field has a value, a bound that depends on the parent's assignment, a rule between two child rows of one draft, a dependency between attributes expressed as a control, and the principle itself. The import (ADR-0021) maps per-row errors only for input validation; a constraint is checked at commit and names no row (ADR-0024 amendment).

Evidence: `docs/features/products-validations/research/validation-facts.md` (capire via `mcp__cds-mcp__search_docs`, `@sap/cds` 10.1.1, `@cap-js/db-service` and `@cap-js/sqlite` sources, scratch probes P0-P14, Q1-Q4 and A1-A38, EDMX measurements in sections 7 and 10.7).

## Decision
1. **Custom texts for input validation.** A format or range rule whose default text would not explain the domain reason carries `@assert.format.message: '<KEY>'` or `@assert.range.message: '<KEY>'` in `srv/annotations/<Entity>.cds`, the key in `_i18n/messages.properties` and `messages_ru.properties`; the error code stays `ASSERT_FORMAT` / `ASSERT_RANGE`, so the import's `validationErrors` mapping and the Fiori message handling are unchanged. Open bounds are written as `[(0), max]`; `_` is infinity. The global `ASSERT_*` keys are not overridden in the project bundle.
2. **User-facing uniqueness on a draft root.** A uniqueness rule a user must see is a self-association in `db/schema.cds` (a structural element, no annotation) whose `on` condition states the equality, for example `namesakes : Association to many Products on lower(trim(namesakes.name)) = lower(trim($self.name)) and namesakes.ID != $self.ID`, plus `@assert: (case when name is not null and exists namesakes then '<KEY>' end)` in `srv/annotations/`. From a draft the association resolves to active rows (lean draft), so the own active sibling is excluded by `ID` and the message appears while editing; at activation the active row is checked against the others. `@assert.unique` stays a DDL constraint for CSV-only writers (ADR-0026 decision 1). The navigation property is visible in `$metadata` (`@cds.api.ignore` does not hide navigations) and gets a `@title`.
3. **Targets and arguments in a constraint.** When a rule reads two fields the user edits, its `then` branch is `error('<KEY>', <args or null>, ('<field1>', '<field2>'))`, the CQL function of `@cap-js/db-service` that `assert.js` turns into `target` and `additionalTargets` (and message arguments). Targets are string literals of the flattened element names (a path is shortened to its last segment; a generated foreign key name is a compile error in an expression). Arguments may be paths of the annotated row (`attribute.descr`, `attribute.atLeast.name`); a localized text is read as `coalesce(<assoc>.localized.<element>, <assoc>.<element>)`, which gives the text of the request's locale or the base text (research section 10.6; `coalesce` is ANSI SQL, the `case when ... is null` form is the CQL fallback). On a draft the message is written when either target is touched and keeps the locale of the request that wrote it; on activation the OData error carries the first target. The function is not in the capire docs: the feature pins its shapes with a backend test per rule, and the fallback is a plain key with one target.
4. **Conditionally required field.** A field that is required only while another field has a value is never `@mandatory`; it is an `@assert` constraint with both targets (decision 3) in `srv/annotations/` plus `Common.FieldControl: (<condition> ? 7 : 3)` on the element in `app/<app>/annotations/<Entity>.cds` (the ADR-0025 shape: CDS expression, integer codes, association paths; `7` Mandatory marks the field, `3` Optional unmarks it, both editable). The server never evaluates the field control; the constraint is the guard on every path.
5. **Required details per assignment.** `SubcategoryAttributes.required : Boolean` names the attributes a subcategory requires; the `ProductDetails` constraints add one branch per value column guarded by the value type, in the ADR-0026 decision 5 form `exists attribute.subcategories[subcategory.code = $self.product.subcategory.code and required = true]`, the MULTI_LIST branch on `attribute` (`not exists selections`); the custom form reads the flag from the expanded assignment (`$expand=attribute(...;$expand=subcategories($select=subcategory_code,required,minValue,maxValue))`) for the label marker. No copied column on the row (the user's D5 may choose the copied column instead; then the draft handler copies it like `position`).
6. **Import pre-check per root constraint.** Every constraint on the root entity gets a per-row pre-check before the inserts, as a pure function in `srv/lib/products-import.js` (rows in, `PRODUCTS_IMPORT_ROW_INVALID` entries out, reason text passed in), the handler owning one `SELECT` for the codes the rule needs; the constraint stays the guard. Generalises ADR-0021 amendment 4 E. A constraint on a child entity the import never writes needs none.
7. **Withdrawn (2026-10-14).** The imperative rule on a draft child for a per-row regex was proposed on the premise that no portable expression can state it; capire lists `matchespattern(x, pattern)` among the portable string functions and the scratch proved it in an `@assert` branch with a column as the pattern (research section 10.5), and the user dropped the rule itself (the free-text attribute is remodelled in a separate issue). The feature has no handler except the import pre-checks; a future rule that truly needs a handler on a draft child starts from the measured shape of research section 6 and its own ADR.
8. **Bounds per assignment.** When a numeric bound depends on the parent's assignment (here the subcategory), the assignment entity carries the nullable bounds (`SubcategoryAttributes.minValue`, `maxValue : Decimal(15, 3)`), the attribute's own bounds stay the first guard, and one branch in the decision 5 form compares the row's value inside the infix filter: `exists attribute.subcategories[subcategory.code = $self.product.subcategory.code and ((minValue is not null and $self.numberValue < minValue) or (maxValue is not null and $self.numberValue > maxValue))]` with its own key, so a client tells the two bounds apart. The preventing control is the client type: the form applies the assignment's bounds as the `Decimal` constraints and shows them as a hint; the branch is the guard.
9. **Rule between two child rows of one draft.** A rule that compares the values of two rows of the same parent is data-driven through an association on the attribute entity (`DetailAttributes.atLeast : Association to DetailAttributes`: this attribute's value must not be below that attribute's value in the same product) and one branch on the dependent row that starts at the draft row: `exists product.details[attribute.code = $self.attribute.atLeast.code and numberValue is not null and numberValue > $self.numberValue]`, with `error()` naming both attributes (decision 3). Never through an association that starts at an entity outside the draft tree (a backlink from the attribute to the rows): lean draft resolves it to the active rows, so the rule compares with the active sibling while the user edits (research section 10.3). Literal attribute codes in `srv/annotations/` are reserved for a showcase rule whose data model would be artificial (the power-of-two rule on `RAM`); a mirror branch on the referenced row is optional and gives two messages at Save for one defect.
10. **Value-driven dependency as a control plus guard.** When a value of a list attribute decides whether another attribute applies, the value entity names the attribute it enables (`DetailListValues.enables : Association to DetailAttributes`, backlink `DetailAttributes.enabledBy`), the custom form disables and clears the dependent row while no enabling value is selected in the product and enables it as soon as one is (the control; the user never sees a message), and the server keeps one branch as the API guard, marked "guard, not user-facing" in the catalogue: `when numberValue is not null and exists attribute.enabledBy and not exists product.details.selections[value.enables.code = $self.attribute.code] then '<KEY>'`. A dependent attribute needs its enabler in the same product; a seed test keeps every subcategory that assigns a dependent attribute assigning an enabling one.
11. **Prevent before validate.** Every rule of a validation catalogue names the control that prevents the error before the request, or "none, validation only": a client type constraint (`Validation.*`, the per-row `Decimal` type), a dynamic field control, a disabled and cleared control, a suggestion list, the code-list customizing of the currency type. A control is added when the framework offers one without a handler; the server constraint stays the guard on every path (API, import, draft, Save), and the import pre-check of decision 6 is its row-level form. A control alone is never accepted as the rule.

First application: feature `products-validations` (#10), rules R1-R8 and R10-R13 of its `CONTEXT.md`.

## Alternatives
| Option | Why rejected |
|---|---|
| Override `ASSERT_RANGE` / `ASSERT_FORMAT` in the project bundle | one text for every field; the per-field `.message` explains the domain reason |
| `@assert.unique` on `Products.name` | 500 `ERR_SQLITE_ERROR` with `@cap-js/sqlite`, nothing on a draft (ADR-0026 measurement) |
| `exists (select ...)` in the constraint | subqueries are not allowed in annotation expressions (capire) |
| `before(['CREATE','UPDATE'], Products)` handler for uniqueness | imperative where a constraint works; no draft message while editing; the import's `validationErrors` would need a mapping for a non-`ASSERT_*` key |
| Two single-target constraints for a cross-field rule (one per field) | two messages at activation for one defect; `error()` gives one message with two targets |
| `@mandatory` with a condition | `@mandatory` is static (capire, ADR-0025 point 3); a dynamic field control alone is not enforced by the server |
| Copied `ProductDetails.required` column (decision 5 variant B) | a second source of truth that is `null` on rows created through the API before the Edit fill; kept as the user's option D5 = B |
| Row-less commit error in the import for the new constraints | the user sees a message without a row number; ADR-0021 decision 4 promises one message per bad row |
| Handler for a per-row regex (former decision 7) | `matchespattern()` is portable and works in a constraint with a column as the pattern (measured); the rule was withdrawn anyway |
| Bounds per assignment as a copied column on the row | the stale-copy problem of variant B; the assignment is read in the same `$expand` as `required` |
| Reusing `PRODUCTS_DETAIL_VALUE_OUT_OF_RANGE` for the assignment bounds | a test and an API client could not tell which bound failed; one key, one `#XMSG` line |
| Rule between rows through `SubcategoryAttributes.atLeast` and a backlink `DetailAttributes.rows` (nested `exists` inside the assignment filter) | compiles and fires at Save, but reads the active sibling while the user edits a draft (research section 10.3) |
| Rule between rows with literal attribute codes (`attribute.code = 'STORAGE'`, `'RAM'`) | ties `srv/annotations/` to seed codes and names no attribute in the message; kept only for the power-of-two showcase, whose data model would be artificial |
| Dependency through `DetailAttributes.dependsOn` plus a Boolean flag on the values | two columns and two CSV edits for the same fact; `enables` on the value is one column, and the backlink says whether an attribute is dependent at all |
| Dependency as a validation (message when the battery has a value without a wireless connectivity) | the user's principle: the form can make the mistake impossible, so the server branch is a guard only |
| Counting rule "at most N selections" (R14) | aggregates and subqueries are not allowed in `@assert`, `exists` cannot count; a handler would be the only way and the domain gives no reason |
| Plain `String(30)` code columns instead of the associations `atLeast` and `enables` | +3 EDMX each instead of +28 (the generated `Common.ValueList` cannot be switched off per element, measured), but no foreign key and against PATTERNS "Reference to another entity" |
| Client-only checks (UI5 type constraints, disabled controls) without the server branch | the server must guard the API (invariant 6, ADR-0027 split); the import and a direct `POST` bypass the form |

## Consequences
- `PATTERNS.md`: "Format or range check" gets the `.message` key and open bounds (decision 1); "Cross-field consistency check" gets the self-association uniqueness form (decision 2), the `error()` two-target and path-argument forms (decision 3) and the `$self` value compared inside an infix filter (decision 8); new rows "Conditionally required field" (decision 4), "Rule between two child rows" (decision 9) and "Dependent field as a control plus guard" (decision 10); "Typed attribute values" gets the required and bounds branches (decisions 5 and 8); "Bulk create from a file" gets "every root constraint needs a per-row pre-check" (decision 6); a note above the validation rows states decision 11 ("prevent before validate": name the control, keep the guard). Examples: `srv/annotations/Products.cds`, `srv/annotations/ProductDetails.cds`, `app/products/annotations/Products.cds`, `srv/lib/products-import.js`, `app/products/webapp/ext/fragment/DetailsForm.js`.
- `TESTING.md` "cds 10 specifics": the timing matrix of research section 1 (format and range in the `PATCH` response, constraints on the next `DraftMessages` read for touched or additional targets, input validation hides constraints at activation), `additionalTargets` in draft messages, a rule between rows fires on the touched row and at activation, a deleted child touches no value row (the selection path is guarded at Save), a draft message keeps the locale of the writing request.
- `templates/annotations-semantic.cds`: one commented example each of `.message`, an open bound, `error()` with two targets and with path arguments.
- The reviewer accepts: a self-association only with a `@title` and a constraint that uses it; `error()` only with string-literal targets and a pinning test; a dynamic field control for a requirement only together with its constraint; a rule between rows only starting at the draft row; a disabled control only together with its guard branch; a catalogue rule only with its preventing control or "none"; a validation handler only with the research note that names the annotation limitation.
- EDMX on this model (research sections 7 and 10.7): self-association +5, `Validation.Exclusive` +2, `Validation.Pattern` +1 each, `required` with title +4, the field control +10, `minValue`/`maxValue` with titles +8, a managed association to a code list +28 (its generated value help), a backlink with title +5, the currency code list +10; `.message`, constraints and `error()` 0.
- Known limits: SQLite's `lower()` folds ASCII only; `error()` is a source-level API; `coalesce()`, `not in (...)` and the `$self` value inside a filter are measured on SQLite only; the client may apply `Validation.Pattern`/`Validation.Exclusive` itself (phase 3 measures the shown text); `DetailsForm.js` grows by three pure functions and sits at its `max-statements` limit (STATE open debt names the sibling module).
