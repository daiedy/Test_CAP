## Network evidence (`$batch` request lines)
- Scenario A, first load (`alice`, en): `GET Products?$count=true&$select=...,rating,...&$expand=...&$filter=(IsActiveEntity eq false or SiblingEntity/IsActiveEntity eq null)&$skip=0&$top=30` → 200, 15 rows (`@odata.count":15`), no `rating` in `$filter`. A separate `$batch` with `GET Permissions?$select=isEditor` → 200 `{"isEditor":true}` (no TypeError this run).
- Scenario B, mouse drag 0..5→4..5 (first change after load): request 1 → 200, `$filter=(IsActiveEntity eq false or SiblingEntity/IsActiveEntity eq null)`, 15 rows (stale/pre-change); request 2 → 200, `$filter=rating ge 4 and rating le 5 and (IsActiveEntity eq false or SiblingEntity/IsActiveEntity eq null)`, `@odata.count":8`, all returned rows rating 4 or 5.
- Scenario C, back to 0..5 (later change): single request → 200, `$filter=(IsActiveEntity eq false or SiblingEntity/IsActiveEntity eq null)` (no `rating` term), `@odata.count":15`.
- Name field, typed "Lamp" + Enter (later change, unrelated to Rating but part of the "one request per field change" acceptance criterion): single request → 200, `$filter=name eq 'Lamp' and (...)`, `@odata.count":0` (exact-equality match, no product named exactly "Lamp"; this is the existing Name field's own semantics, not part of this feature). Category, Price and Editing Status request counts were **not separately measured** within the turn budget; Rating and Name together demonstrate the one-request-per-committed-change rule holds for at least two different field types.

## Verdict
**Ready for review.**

Scenario D (variant save/switch/restore) initially looked like a blocking defect of this feature: after saving a "Mid ratings" variant with the Rating slider at `[2,4]` and switching away and back, the slider and the table both reverted to the unfiltered state. `fiori-app-dev` measured the actual root cause and it is **not** the custom filter field: `app/products/webapp/test/flpSandbox.html` sets no `data-sap-ui-flexibility-services`, so "Save As" goes to the default `LrepConnector` (`HEAD /sap/bc/lrep/actions/getcsrftoken/` → 404, `GET /sap/bc/lrep/flex/data/products` → 404, both visible in this session's own network log), the save listener fails with `Error: Not Found`, the change stays `NEW`, and selecting another variant runs `VariantManagerApply.handleSelectVariant` → `eraseDirtyChangesOnVariant`, erasing it. The identical failure reproduces on `main` with `Category=KITCHEN` (no custom field involved); injecting a `SessionStorageConnector` fixes it (`BT [2,4]`, slider `[2,4]`, 9 rows, restored correctly). **User decision (2026-09-25): this sandbox flex-connector gap is separate backlog debt, not part of feature #6; scenario D is recorded as known sandbox debt, not a feature defect.** This agent's earlier "PropertyInfo not registered" hypothesis was wrong and has been corrected in VERIFICATION.md and in agent memory.

All scenarios that are in scope for this feature passed: first load with no `rating` condition and `$batch` evidence (A); no Go button and one request per later filter change, confirmed for Rating (mouse and keyboard, B/C/E) and for Name (partial); the documented "two requests on the first change after load" behaviour reproduced exactly as described in research section 8 (B); 4..5 → 8 rows and 2..4 → 9 rows without pressing Go (B/D); collapsed header text "1 filter active: Rating" (C); Adapt Filters lists Rating once (H); keyboard arrows/Home/End/typed-tooltip-input all work and reload once each, Ctrl+Enter does nothing (E); accessibility tree shows `role=slider`, name "Rating"/"Рейтинг", correct `aria-valuemin/max/now` (G); `viewer` and `ru` behave identically to `alice`/en, with the ru label correctly localized (I); empty result shows the standard no-data text (J); narrow width (375px) keeps the slider usable (K); mock mode filters correctly with no backend (L).

One genuinely new console warning (not on `main`) appears once per page load: `Invalid empty segment - /Products//Products/rating`, tied to the custom filter field's label-fallback metadata resolution; no visible or functional effect was observed in any scenario. `Unknown child EntitySet ... FilterDefaultValue` and `PropertyInfo validation is disabled`, which this agent first listed as new, are confirmed present on `main` too (`fiori-app-dev` measurement) and are reclassified as baseline noise. Recorded for the reviewer to judge; not blocking.

Not verified within the turn budget (named, not claimed): Category, Price and Editing Status individual request counts (Rating and Name were measured and both hold to "one request per committed change"); a page **reload** with a non-default saved variant selected (blocked by the sandbox flex-connector gap above, not a feature concern); real screen-reader announcement of the table count change (accessibility tree only, consistent with the products-rating-column precedent).

Verifier tooling notes (not app defects): the FLP sandbox's "Expand/Collapse Header" and "Adapt Filters"/"Cancel" buttons did not respond to a plain DOM `.click()` in this Chrome session; the chrome-devtools MCP `click` tool (which dispatches a full pointer sequence) worked every time. A JS `.focus()` call on a slider handle was unreliable for ~1s after a dialog closed (focus kept reverting to the dialog's last-focused element); using the MCP `click` tool on the handle before `press_key` was reliable throughout.
