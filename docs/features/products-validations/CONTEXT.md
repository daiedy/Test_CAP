# products-validations: context

Date: 2026-10-13, amended 2026-10-14 (plan-gate decisions on the details). Author: `architect`. Branch: `spec/products-validations` (feature branch `feature/products-validations` at implementation). Issue #10.

This file is the brief for the implementers: every agent of the feature reads it whole (protocol step 1), so it holds only the sections below (ADR-0018). Screens go to `SCREENS.md` (`ux-designer`). Experiments, measurements, rejected mechanisms and framework facts are in `research/validation-facts.md`, read by `architect` and `reviewer` unless a plan step names it.

## Request
Issue #10: Object Page validations, through annotations where possible. The user's addition at `/spec` start: come up with logical constraints for all fields, including the typed details of feature #9; not every field needs one; the point is a set of not-so-ordinary validations that show what the project can do. At the plan gate (2026-10-14) the user asked for more rules on the details and set the principle that shapes the whole catalogue: wherever possible look for validations and controls that leave the user no way to make the mistake; then there is nothing to check. So the deliverable is a showcase: every rule has a domain reason in a product catalog, names the control that prevents the error before the request where the framework offers one, and keeps a server constraint as the guard on every path (API, import, draft, Save); the feature has no handler except the import pre-checks; messages explain the reason, in `en` and `ru`.

## User decisions
Plan gate 2026-10-14:
- Principle "prevent before validate": prefer controls that make the mistake impossible over validating after the fact; every rule in the catalogue names its preventing control ("Preventing controls" table below) and keeps the server constraint as the API guard.
- R14 "at most N selections in a MULTI_LIST": rejected (an aggregate or a subquery is not allowed in `@assert`, `exists` cannot count, a handler would be the only way, no domain reason).
- R10 "bounds per assignment": accepted as proposed, `SubcategoryAttributes.minValue` and `maxValue` narrow the attribute's global bounds for one subcategory; seed values in the "Seed" list below; the global bounds stay the first guard.
- R11 "Storage not below Memory (laptops)": accepted as a showcase of a rule between two detail rows of one product ("I would not add such items myself, but as an example of what we can do it is good"); the architect chose the form after the scratch probes: data-driven through `DetailAttributes.atLeast` (research section 10.3; the nested assignment-level form reads active rows on a draft and is rejected, the literal form is not needed); confirmation in D11.
- R13 "Memory is a power of two (laptops)": accepted on the same showcase grounds; the constraint stays, a suggestion list is the optional control (D13).
- R12 "battery life only for wireless connectivity": not a validation but a control: the Battery Life row is disabled (and its value cleared) while the Connectivity row of the same product has no wireless value or no value at all, enabled as soon as a wireless value is selected; data-driven through `DetailListValues.enables`; the server keeps one `@assert` branch as the API guard only (invariant 6, ADR-0027 split), marked "guard, not user-facing".
- R9 "text pattern": dropped entirely. The user replaces the free-text `DIMENSIONS` attribute by three numeric attributes (length, width, height) and a free-text `MODEL` attribute in a separate backlog issue (the dimensions remodel, A+), blocked by #10 because it reuses R10's bounds per assignment; a format rule on free text is then not needed. `DIMENSIONS` keeps its current seed in #10; `DetailAttributes.pattern`, the handler, the lib module and every R9 step, criterion and key are out of the feature. The `matchespattern` measurement stays a fact (research section 10.5, ADR-0028 alternatives).
- Standing decisions that shape the design: semantics in `srv/annotations/`, presentation in `app/products/annotations/` (ADR-0004); `@assert: (case ...)` constraints before handlers (ADR-0024 decision 2); persistence `@assert.unique` only in `db/` and never for a user-facing rule on a draft entity (ADR-0026 decision 1, TESTING); the Details section is the generated typed form of ADR-0027, whose rows come from the subcategory's assignments.

## What already exists and is reused

## Applicable patterns
Rows from `docs/architecture/PATTERNS.md`:
- "Format or range check": `@assert.format`, `@assert.range` in `srv/annotations/` (R1, R3, R5). The row does not mention `@<anno>.message` and open bounds: ADR needed (ADR-0028 decision 1).
- "Cross-field consistency check": `@assert: (case ...)` with null guards, `exists` set membership, no `@assert.unique` inside a draft tree (R2, R4, R6-R8, R10, R12, R13). Uniqueness across the whole entity through a self-association, the two-target `error()` form, a `$self` value compared inside the infix filter and a rule between two child rows have no row: ADR needed (ADR-0028 decisions 2, 3, 8, 9).
- "Field editable only when another field is filled" (ADR-0025): the dynamic `Common.FieldControl` shape, integer codes, association paths; a conditionally required field that stays editable (`7 : 3`) is a variant with no row: ADR needed (ADR-0028 decision 4).
- "Rows generated from an assignment on a draft" (ADR-0027 decision 3): unchanged under D5 = A; under D5 = B the copied column extends it.
- "Typed attribute values" (ADR-0027 decision 4): R8, R10, R11, R13 add branches to the same `numberValue` constraint; a value-driven dependency between attributes as a control plus guard (R12) has no row: ADR needed (ADR-0028 decision 10).
- "Reference to another entity": `atLeast` and `enables` are managed associations in `db/schema.cds` (the +28 EDMX each is measured and accepted, research section 10.7).
- "Bulk create from a file" (ADR-0021): a root constraint is checked at commit and names no row, so every new root constraint gets a per-row pre-check (R4, R6, R7); the row says it for one rule, the ADR generalises it (decision 6); the detail rules need none.
- "Custom section or column" (ADR-0027): the required marker, the range hint, the disabled dependent row and the suggestions in `DetailsForm.js`.
- "Prevent before validate" (the user's principle): no row yet; ADR-0028 decision 11 adds it to PATTERNS as the rule of every validation task.
- "OData contract": `npx vitest -u` and `metadata.xml` in the same phase as each model change (phases 2 and 3).
- "Texts": message keys in `_i18n/messages*.properties`, labels in `_i18n/i18n*.properties`.

## Relevant lessons
From `docs/LESSONS.md`:
- 2026-10-10: making a field mandatory breaks every writer that omits it: R6's writers are listed in research section 8 and in the plan (tests, fixtures, README); R10's bounds are checked against every seeded value and the journeys' inputs (Battery Life 12 on the mouse, inside MICE 1-2000).
- 2026-10-10: an `@assert` constraint is checked at commit, not per row, so the import maps it only through a per-row pre-check: R4, R6, R7 get one; the detail rules need none because the import creates no detail rows.
- 2026-10-10: a missing `@mandatory` value hides another field's rule; at activation the input validation hides the constraints (research section 1): the tests assert one kind per request.
- 2026-10-12: decide the mechanisms of a custom fragment at plan time and prove them in a skeleton: the required marker is a `setRequired` on the existing label, the bounds go through the existing `Decimal` type, the disabled row is `setEnabled` plus the proven `setProperty(null)` write; the activation-error mapping onto a custom control is the one unproven piece and has a fallback (plan risks).
- 2026-10-12: a criterion that names a verb is measured for every verb: the plan names active `POST`, active `PATCH`, draft `PATCH`, `draftActivate` and the import per rule.
- 2026-10-09: measure a UI claim before the plan gate: the `additionalTargets` rendering, the client required check of R6 and the currency code list of D13 are browser-proof items, not promises.
- 2026-10-09: `cds-mcp` `search_model` shows the pre-feature model in a worktree; implementers read `docs/registry/DOMAIN-MODEL.md` after `npm run docs:registry` for `namesakes`, `required`, `minValue`, `maxValue`, `atLeast`, `enables`, `enabledBy`.
- 2026-10-14 (this spec, research section 10.3): an association that starts at an entity outside the draft tree (`DetailAttributes.rows`) reads active rows while the user edits a draft; a rule between draft rows must start at the draft row (`product.details[...]`).

## Open questions
Decisions for the user at the plan gate (D1-D3 are the issue's questions; D9 was decided on 2026-10-14, R9 dropped):
- D1 Rule list: the recommended set is R1-R6, R8 and the accepted R10-R13; R7 is optional. Cut or add? (Fields without a sensible rule: stock, rating, currency, category, subcategory, the managed fields.)
- D2 Message texts: recommended custom texts per rule (the keys above) through `@assert.format.message` / `@assert.range.message` and constraint keys; the cds defaults stay for `@mandatory`, `@assert.target` and the existing stock and rating ranges. Alternative: override `ASSERT_RANGE` / `ASSERT_FORMAT` globally in `_i18n/messages.properties` (one text for every field).
- D3 Timing: the framework gives format and range messages in the PATCH response and constraint messages right after the field change through the `DraftMessages` read, `@mandatory` only at Save (research section 1). Recommended: accept that; no handler for typing feedback.
- D4 R6 condition: `stock > 0` (recommended, in stock = on sale) changes `newProduct` in the tests, `generatedRow` in the fixtures and the README. Alternative with no writer impact but a weaker reason: required when `rating > 0`.
- D5 R8 source of the required flag: A (recommended) the constraint and the form read the assignment (`exists attribute.subcategories[... and required = true]`, the `$expand` above, which R10 shares), no handler change, no stale copy; B a `ProductDetails.required` column copied by the draft handler like `position` (+5 EDMX, handler and test changes, simpler form code).
- D6 Required assignments: `LAPTOPS/SCREEN_SIZE`, `MICE/DPI`, `SEATING/MAX_LOAD`, `APPLIANCES/POWER`, `APPLIANCES/CAPACITY`, `DRINKWARE/CAPACITY`, `FITNESS/THICKNESS` (every seeded product of these subcategories is filled, the journeys never save into them). Confirm or change.
- D7 Import: per-row pre-checks for R4, R6, R7 as pure functions in `srv/lib/products-import.js` (recommended, the ADR-0021 amendment 4 E shape); alternative: accept a commit-time error without a row number for those three rules.
- D8 `error()` with two targets (R4, R6) and with path arguments (R11): a source-level API of `@cap-js/db-service`, not in the capire docs, measured on 10.1.1 and pinned by tests (recommended); alternative: single-target constraints with plain keys, then the message appears while typing only when the constraint's own field is touched (always at Save) and names no attribute.
- D10 UI: `ux-designer` amends `SCREENS.md` (R9 sections out; the R10 range hint and its client refusal, the R12 disabled-and-cleared row, the R11 message on the Storage row, the R13 suggestions if D13; `en` and `ru`); the user reviews it with the plan.
- D11 R11 form: recommended `DetailAttributes.atLeast` (data-driven, one `exists`, localized names in the message; research section 10.3). Confirm; and decide the mirror branch on the Memory row (live message when Memory is edited above Storage, but two messages at Save for one defect; recommended: no mirror, the Save message on the Storage row suffices).

Recommended: `STORAGE` 32-8192 for LAPTOPS (32 GB and 64 GB laptops exist); alternative: keep 128 and accept that R11 shows only through the API.

Recommended: (a) yes (it turns the only cross-field rule without a control into one), (b) no (the LAPTOPS bounds and the message already make the mistake rare; the showcase is the validation).
