# D-1: unfiltered attribute dropdown repeats names

Date: 2026-10-12. Author: `architect`. Defect: `VERIFICATION.md` scenario 6 (D-1). Status: analysis for the user's decision; no edits routed (the orchestrator reports the user may change the Details section itself).

## Defect
On a new product before a subcategory is chosen, the Attribute dropdown of a detail row reads `SubcategoryAttributes` without `$filter` (the In parameter `product/subcategory_code` is null, FE adds no condition) and lists the 45 assignment rows: Colour 11x, Material 9x and so on. PLAN D5 and SCREENS scenario 6 expected "all 20 attributes". A pick stores a valid `attribute_code`. With a subcategory set, the list is narrowed to three (scenarios 2, 5, 6).

Root cause: by construction, the value-list collection of ADR-0026 decision 4 holds one row per (subcategory, attribute) pair. An unfiltered read of a pair entity repeats every attribute that has more than one subcategory. The approved D5 text ("the dropdown is unfiltered") and its expectation ("the full attribute list") cannot both hold with this collection, so the gap is in the plan, not in the implementation.

## Recommendation
(a), if the table section stays. It reuses an accepted pattern, costs 9 contract lines, the compile and the data path are measured, and it closes both the new-product case and the reset case, matching the Subcategory field's own behaviour (disabled until a category is chosen). The browser proof of a parent-path FieldControl on a table cell is the first check of the fix phase; if FE ignores the path, fall back to (c).

Fix within approved decisions: no. Every option changes something the user approved: (a) changes D5 from "the dropdown is unfiltered" to "the Attribute cell waits for the subcategory"; (b) amends ADR-0026 decision 4 and the "Dependent value help" row; (c) changes the D5 expectation "the full attribute list"; (d) is the D5 alternative and needs an ADR. The D5 wording in PLAN and SCREENS changes in the same phase as the fix (LESSONS 2026-10-10: plan-gate changes are reconciled in SCREENS).

If the user replaces the table with form-like fields or another list (orchestrator note, 2026-10-12), D-1 is moot together with the table, and this analysis only keeps M1 to M6 as facts.
