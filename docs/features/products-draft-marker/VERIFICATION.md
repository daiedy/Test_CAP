## Verdict

**Ready for review.** All 7 mandatory scenarios from `CONTEXT.md` "Scenarios for `ui-verifier`" passed (scenario 8, the optional nameless-draft check, was skipped per the coordinator's instruction to conserve turns; its absence is by design, not a gap — the plan marks it optional). The corrected A1 pass criterion (own-draft `Draft` marker is text-only, no icon required) held exactly as documented. The core feature works end to end: `Common.SemanticKey: [ name ]` produces the draft/lock marker inside the `Product Name` cell, in both `en` and `ru`, with no regression to navigation, category display, filtering, or the Object Page, and no data left behind.

Two observed behaviors diverge from predictions written in `CONTEXT.md`/`PLAN.md`. Neither is a defect of this feature (both are `sap.m.ObjectMarker`'s own behavior, unreachable from the `Common.SemanticKey` annotation), but both should correct the ADR-0015 "Consequences" section and the LESSONS entries `docs-keeper` is about to write, so a future verifier or reader does not treat the wrong prediction as fact:

1. **The marker is a real, interactive tab stop for every type, including `Draft`** (scenario 2). `PLAN.md`'s acceptance criteria state the own-draft marker "adds no tab stop (it is non-interactive; ... `titleActive` stays `false`)". Measured instead: the marker's inner `<a>` has `tabindex="0"`, and the `sap.m.ObjectMarker` control registers a `press` handler (`ctrl.mEventRegistry` lists `"press"`) for the `Draft` type too. Pressing it opens a real, useful popover ("Last changed on \<date\>."), not a no-op. The `titleActive: false` fact quoted in the plan is true but describes the *`ObjectIdentifier`'s title* (the bold product name), not the *marker* next to it — the plan conflated the two controls. **Correction for architect/docs-keeper**: drop the "no tab stop" half of the criterion; the marker is always a tab stop with a meaningful popover, for `Draft` as much as for `LockedBy`.
2. **The lock marker does not go icon-only below a 600 px window width inside this table cell** (scenario 3, A6). `CONTEXT.md` cites the pinned `sap.m.ObjectMarker` API doc: "on screens larger than 600px both icon and text are visible, otherwise only the icon." Measured instead, at `window.innerWidth` 500 (confirmed via `sap.ui.Device.media.getCurrentRange('StdExt')` reporting the `"Phone"` range and `documentElement` carrying `sapUiMedia-Std-Phone`), after both a live resize and a full page reload at that width: the marker's class stayed `sapMObjectMarkerIcon sapMObjectMarkerText` and the text span remained `display: inline; visibility: visible`. The `Product Name` column instead stays full width while the responsive table pops `Category`/`Price`/`Stock Quantity` off first, which may be why the marker never loses its text. **This is accessibility-neutral-to-positive** (text stays available at every width tested, so WCAG 1.4.1 is not at risk either way) but it means the standalone-control API documentation does not describe what happens inside an FE V4 responsive table cell. **Correction for architect/docs-keeper**: either drop the icon-only-below-600px claim from any future documentation of this pattern, or scope it explicitly to standalone `ObjectMarker` usage outside a `sap.m.Table`/`sap.ui.mdc.Table` cell.

No mandatory scenario failed. No console error or warning was introduced. The `$batch` `$select` list is unchanged by the annotation (as `CONTEXT.md` experiment 4 predicted). Data hygiene is proven (15 products, 0 drafts, both touched products at seeded values) and the server this agent started (`npm run watch`, confirmed via `curl` on `$metadata`) was stopped and confirmed down.
