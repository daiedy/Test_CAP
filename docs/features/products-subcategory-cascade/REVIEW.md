## Important
- `docs/features/products-subcategory-cascade/SCREENS.md` (Field states S2 and S5, "Messages", scenario V7) still describes the design from before the user's mandatory requirement: S2 "enabled ... no asterisk (optional)", S5 and "Messages" "Saving with an empty category shows the existing server error on Category (S5); Subcategory gets no message", V7 "one error on Category in the message popover, nothing on Subcategory". The approved PLAN (status line, criteria "In edit mode Subcategory shows the required marker", ADR-0025 point 4) and the implementation make Subcategory `@mandatory` with `FieldControl` 7, so `ui-verifier` measured the opposite of S5/V7 (VERIFICATION F1: three popover entries, one of them `ASSERT_MANDATORY` on the disabled Subcategory, screenshots `06-v7b-*`, `10-v7d-*`). The behaviour was already measured at the plan gate (`research/framework-facts.md` section 7: "`draftActivate` of that draft | 400 `MULTIPLE_ERRORS` with `ASSERT_MANDATORY` on `in/category_code` and `in/subcategory_code`"), so the spec gap is that SCREENS was not reconciled with the plan-gate addition (`ux-designer`/`architect`, step 1b). This is VERIFICATION F1, assessed: not a code defect, and not blocking. Both messages are true (both fields are `@mandatory` and both are empty), `@mandatory` cannot be made conditional, and suppressing the second message needs either a handler (against invariant 6 and ADR-0025 point 3) or a `@assert` constraint in place of `@mandatory` (it is checked at commit, so it would write a draft message on every category change, and the import would lose the per-row `ASSERT_MANDATORY`, ADR-0021 amendment 4). The sub-observation "a stale draft message stays until revalidation" is the `ASSERT_MANDATORY` message the failed `draftActivate` persisted in `DraftMessages` (reqid 155); it stays true while the subcategory is empty and the next PATCH of `subcategory_code` replaces it, which is standard Fiori Elements draft behaviour, not a defect. Owner and fix: `docs-keeper` records F1 in `SUMMARY.md` as a known, accepted deviation from SCREENS S5/V7, with the reason above, and the orchestrator reports it to the user at the phase gate; if the user wants a single Category message, that is a follow-up issue through `/backlog` with an ADR, not a fix in this feature. SCREENS.md itself is pruned at completion (PLAN step 10), so it needs no edit.
- `docs/architecture/PATTERNS.md:25` (row "Cross-field consistency check") ends with "The key is not an `ASSERT_*` code, so `importProducts` needs its row mapping extended before an import column for the field". This feature proved that sentence wrong and the ADR-0024 amendment withdraws it (the constraint is checked at commit, `validationErrors` never sees it; the import checks the pair per row before the inserts, ADR-0021 amendment 4 E). PLAN step 9 lists the "Bulk create from a file" note but not this correction, so a later agent following PATTERNS would extend `validationErrors` again, which is the dead end `cap-backend-dev` measured. Owner: `docs-keeper` in phase 6 (non-blocking, expected-next): replace the sentence with a pointer to the per-row pre-check of "Bulk create from a file" and ADR-0021 amendment 4 E.

## Minor
- `srv/catalog-service.js:160-184` (`subcategoryMismatches`) and `test/catalog-service.test.js:1007-1010`: an import row with an unknown category and a valid subcategory gets two messages (row 5 of the invalid fixture: `category` "Target with this key doesn't exist." and `subcategory` "The subcategory does not belong to the category of the product."), while the function skips unknown subcategory codes. Assessed: conforms to ADR-0021 amendment 4 E as written (the skip list there is "an empty category, an empty subcategory or an unknown subcategory code", with "one `SELECT` on `my.catalog.Subcategories`"), the second message is true (`LIGHTING`/`APPLIANCES` belong to no category called `NOPE`), it is what the commit-time `@assert` would also say (`category.code` resolves to the foreign key `category_code`), the fixture JSDoc (`test/fixtures/build-workbooks.mjs:60-62`) and the test pin it deliberately, and nothing is written either way. Skipping unknown categories as well would need a second `SELECT` on `Categories`, which is an ADR change for a cosmetic gain. Not blocking. Owner: `docs-keeper` names it in `SUMMARY.md` as a known behaviour; a change, if the user wants one, is `architect` (ADR-0021 amendment wording) plus `cap-backend-dev`.
