## B1

Setup: Laptop Pro 15 display mode, `...flpSandbox.html?sap-ui-log-level=WARNING#products-display&/Products(ID=4b7e1d2a-...,IsActiveEntity=true)`, `en`.

Observed (3 `$batch` POSTs, all 200, none after the page settled):
- `GET Permissions?$select=isEditor` (group `$auto`).
- `GET Products(ID=4b7e1d2a-...,IsActiveEntity=true)?$select=DraftMessages,HasActiveEntity,HasDraftEntity,ID,IsActiveEntity,category_code,...,subcategory_code&$expand=DraftAdministrativeData(...),category(...),details($select=ID,IsActiveEntity,listValue_code,numberValue,position,textValue;$expand=attribute($select=code,maxValue,minValue,name,scale,unit,valueType_code;$expand=values($select=code,name,position;$orderby=position)),selections($select=ID,IsActiveEntity,value_code);$orderby=position),subcategory(...)`. FE merged the fragment's `details` binding (its `$select`/`$expand`/`$orderby` parameters verbatim) into the Object Page's own product GET, so there is no separate `GET Products(..)/details?...`; this is the "one GET per load" of the expectation, in the parent request. Response: 3 rows in position order 1-3 (`SCREEN_SIZE` 15.000, `RAM` 16.000, `STORAGE` 512.000) with `attribute` (unit, valueType_code, min, max, scale) and `selections: []`.
- `GET Products(...)?$select=createdAt,createdBy,modifiedAt,modifiedBy` (Administrative Data, group `$auto.Heroes`).
- No per-field late-property GET, no GET to `DetailListValues`/`attribute/values` separately.

Screen: `screenshots/proof-b1-display-laptop.png`: section "Details" after Pricing & Stock, three labelled fields in order Screen Size "15 in", Memory (RAM) "16 GB", Storage "512 GB", counter "Filled 3 of 3". Anchor bar shows the tab "Details" between "Pricing & Stock" and "Administrative Data".

Console (`sap-ui-log-level=WARNING`): no factory or binding error for the `formElements` factory. NEW against round 1, three errors from the skeleton fragment (defect D-1, not a risk):
- `FormatException in property 'visible' of 'Element sap.m.Text#products::ProductsObjectPage--fe::CustomSubSection::Details--detailsNoSubcategory': LAPTOPS is not a valid boolean value` (Hint: single properties in binding expressions are converted into the type of the bound control property unless `targetType:'any'` is given), the same for `detailsSelectSubcategory` and for `Form#...--detailsForm`.

- Known noise, same as round 1 (not new): `NavContainer page stack is empty`, `View is generated without a component`, `Set unchanged path ... HeaderInfo`, `toggleHeaderOnTitleClick`, `T_NEW_OBJECT|Products` assert, `PersonalizationV2`, sync ResourceModel loading, `[FUTURE FATAL] AddBookmarkButton`, 404 on `sap/bc/lrep/flex/*` (flpSandbox has no flex connector).

Verdict B1: proven. The factory resolved through `core:require`, three FormElements built with their labels and typed controls, no factory error.

## B4

The skeleton's own hook (`binding.attachPatchCompleted` -> `product.requestSideEffects([{$PropertyPath:'DraftMessages'}])`) did NOT fire: two row `PATCH`es (`{"numberValue":"1600"}` and `"1700"`) produced no `GET ...?$select=DraftMessages` (the `$batch` held only the PATCH), whereas FE's own field PATCH (`{"description":"x"}`) sends `PATCH` + `GET Products(...,false)?$select=DraftMessages` in the same batch. The `patchCompleted` of the dependent `details` binding is not raised for these PATCHes. Defect D-2 for step 8 (not a decision for the user): the module must read `DraftMessages` itself by another trigger (e.g. the field's `change` handler or `attachPatchSent`/`attachPatchCompleted` on the product's list/context, or at the Save/`draftPrepare` read that already exists).

Mapping itself, measured: API value `{"numberValue":"20000"}` PATCHed with curl on the draft row BATTERY_LIFE (server writes the draft message `PRODUCTS_DETAIL_VALUE_OUT_OF_RANGE`, target `.../details(ID=35e8d02a-...,IsActiveEntity=false)/numberValue`). Once a `DraftMessages` read ran (manual `requestSideEffects` first, later the Subcategory change), the message landed on that Input: `aria-invalid=true`, Error state, bubble "Enter a value within the allowed range." under Battery Life, footer button 1 error (screenshot above). Also seen: a second message with target `/Productsundefined/numberValue` (same text, no field) in the message model, a duplicate with an undefined path; it appears after the `draftPrepare` read, count in the footer badge goes 1 -> 2 on some reads. Not a risk of the plan; defect D-3 for the reviewer: server draft messages of a details row are listed twice in the model, one with a broken target.
Verdict B4: mapping proven (value state on the field, project text); the skeleton's trigger after a row PATCH is not working (D-2). Popover-only fallback not needed.

## B6 (Colour, LIST, on the Audio draft of `Proof API Mouse`, `en`)

- Typed `Purple` (focused field, text typed char by char, no Tab yet): the `$batch` held `PATCH Products(...,false)/details(ID=c68e267e-a0dd-4181-a407-15d84751d0ff,IsActiveEntity=false)` `{"listValue_code":null}` => 204. The two-way `selectedKey` writes `null` as soon as the typed text stops matching an item (type-ahead): a PATCH while typing, not at commit.
- Tab: no further request. `onListChange` set the Error value state: `getValueState()` = Error, text "Select a value from the list." (the fragment's i18n text), `getSelectedKey()` = "", value "Purple" stays in the box (`screenshots/proof-b6-purple-error-state.png`).
- This is the predicted refutation of SCREENS row 5 "the stored value stays unchanged": a previously stored colour is NULLed by the PATCH made while typing, and the Error shows after. Stored value after the sequence = empty (counter would drop).
- The module's error is `setValueState`, not a binding-type message: the UI5 message model did not gain an entry for it (only the server error of Battery Life was listed) and the footer count stayed at the existing 1; so a combo box in this Error state does not block Save by itself, but the stored value is NULL anyway (no silent save of an old value, and no invalid value is ever written).
- Typed `Black` over `Purple`: one `PATCH ... {"listValue_code":"BLACK"}` => 204 (sent on the last character, before Tab; the intermediate prefixes did not each send a request), Tab: no request, the Error state cleared (`aria-invalid` gone), counter "Filled 2 of 3".

Verdict B6: proven for the binding (ComboBox `selectedKey` two-way on `listValue_code`, PATCH to the relative draft path, state cleared by a valid item). Refuted in detail: SCREENS row 5's "stored value stays unchanged" (the PATCH `null` goes out while typing). Fallback named in PLAN: `sap.m.Select` (no free text, no check). Alternative inside the same control for the `ux-designer`/`architect`: accept NULL-on-invalid-text and word row 5 accordingly; the choice changes a SCREENS statement, not a U decision.

## Architect ruling on B2, B6, B7 (2026-10-12, before step 8)

Written by `architect` after the proof above; PLAN Risks B2, B6, B7, B9 and step 8 carry the result. Framework facts F1-F9 come from the UI5 1.153.0 CDN debug sources (`sap/m/ComboBox`, `sap/m/InputBase`, `sap/m/MultiComboBox`, `sap/ui/core/Messaging`, `sap/ui/core/message/Message`, `sap/ui/core/message/ControlMessageProcessor`, `sap/ui/core/message/MessageMixin`, `sap/ui/model/odata/v4/ODataModel`, `sap/ui/model/odata/v4/Context`, `sap/fe/core/controllerextensions/EditFlow`, `sap/fe/core/controllerextensions/messageHandler/messageHandling`): not verified by MCP (`ui5-mcp-server` was not in the architect's toolset in this session; fiori-mcp `search_docs` still down, embeddings). cds-mcp `search_docs` "Persistent Messages": CAP generates `Common.SideEffects #alwaysFetchMessages` (FE reads `DraftMessages` after its own `PATCH`es) and `Common.Messages: DraftMessages` (`metadata.xml` lines 463-477).

Framework facts:
- F1. ComboBox: `handleInputValidation` runs on every typed character; it calls `setSelection(null)` when the text matches no item and `handleTypeAhead` selects the first matching item, each firing `selectionChange`. With `selectedKey` two-way every such selection writes the model: the B6 `PATCH null` while typing, and on type-ahead an intermediate item. `change` fires only on commit: Enter, focus leave (`InputBase#onChange`, only when the value differs from the last committed one) and a list choice (`onSelectionChange`, `onItemPress`, parameter `itemPressed`). The clear icon fires `change` only when an item was selected; after a non-item text the cleared field is committed at the next focus leave.
- F2. A `OneWay` property binding never writes the model (`ManagedObject#updateModelProperty` writes only in `TwoWay`) and still has a data state, so `MessageMixin` (applied to `sap.m.InputBase`, so to ComboBox) maps messages of that property to the value state.
- F3. FE Save (`EditFlow#_executeSaveDocument`) first calls `removeTransitionMessages()` (removes every `persistent` bound message), then `_checkForValidationErrors()`, which stops the save when a message has `validation === true` and its last control id lies inside the visible view. That is how B11 blocked Save.
- F4. The client validation message that B5 and B11 saw is built by `Messaging._handleError` as `new Message({ type: Error, target: '<controlId>/<property>', processor: ControlMessageProcessor, validation: true, references })`; `ControlMessageProcessor` is a singleton (`new` returns the one instance); `validation` is a public constructor parameter (`Message#isValidation`, since 1.151).
- F5. `ControlMessageProcessor#checkMessages` puts the message into the data state of the control's binding of `<property>` (the property must be bound, otherwise no control id is set); `MessageMixin#refreshDataState` then adds the control id, sets `additionalText` to the label (the popover subtitle) and sets the value state and its text from the message; removing the message resets the state to None.
- F6. `ODataModel#reportStateMessages` runs on every `DraftMessages` read and removes every non-persistent message of the V4 model processor whose target lies under the product path. A model-processor message on `.../details(ID=...,IsActiveEntity=false)/listValue_code` would vanish at the next FE field `PATCH` (`#alwaysFetchMessages`) while the bad text stays, and a persistent one is removed by F3 just before the check: neither blocks Save reliably. Control messages (F4) are not V4 model messages and survive both.
- F7. FE `EditFlow#editDocument` binds the page to the new draft context (`_handleNewContext`) before `setEditMode(Editable)`: the fragment root sees the draft context first.
- F8. `MultiComboBox#_showWrongValueVisualEffect` flashes the control's own `valueStateText` when one is set while the state is None, otherwise the core text `VALUE_STATE_ERROR` ("Invalid entry", translated by UI5). This is the source of D-6.
- F9. An aggregation binding calls `model.bindList(path, context, sorters, filters, parameters)` with the binding info's `parameters`: a `dependents` binding with `parameters: { $$ownRequest: true, $select: 'ID,IsActiveEntity,value_code' }` makes the measured B7 binding, with its context and lifetime managed by the control (rebound with the row context, destroyed with the control).

Rulings (no user decision changes; U6 "ComboBox with validation" is kept):
- B6, LIST: ComboBox kept, SCREENS "Value states" row 5 stays true. `selectedKey` bound `OneWay` to `listValue_code` (F2); the module acts only in `change` (F1), never in `selectionChange`. Empty text: write `null`. Text equal to the selected item's text: write its key. Both through the row context `setProperty('listValue_code', ...)` only when the value differs from the stored one, and both remove the field's message. Any other text: write nothing and add one message shaped like F4 (`type` Error, `target` `<comboBoxId>/selectedKey`, `processor` `new ControlMessageProcessor()`, `validation: true`, text `ProductsObjectPage.details.valueNotInList`) through `sap/ui/core/Messaging`. The module sets no value state or `valueStateText` itself (F5 does). A message never outlives its control or its row: removed when the combo box's `modelContextChange` brings another row context and when a `details` binding `change` leaves its control destroyed. Effect: stored value unchanged, Error on the field, Save blocked with the error in the popover (F3) like B11, and the message survives `DraftMessages` reads (F6).
- B6 rejected variants: `selectedKey` two-way (B6 measurement); a message with the V4 model as processor (F6); `sap.m.Select` (the user requires a ComboBox); `value` bound through a custom type that maps names to codes (re-implements the item match, unmeasured); firing `validationError` from the module (protected API).
- B7, MULTI_LIST: the row's `selections` become an own-request binding, the measured one, held in the multi combo box's `dependents` aggregation with the parameters of F9; `selectionFinish` creates (`create({ value_code }, true)`) and deletes (`context.delete()`) its contexts (`POST` 201, `DELETE` 204 measured). `selections` leaves the section's `$expand`; the selected keys, the display join and the counter's "filled" of a MULTI_LIST row read this binding (recomputed on its `change` and after each create or delete). Cost: one own `GET .../details(...)/selections` per MULTI_LIST row, in display mode too.
- B7 rejected variants: the dependent binding (no own cache, B7); `selectionChange` per click (the create itself fails); a list with remove buttons plus an Add combo box (needs the same create); a module-created `model.bindList` (same binding as F9, but the module would have to rebind and destroy it by hand).
- B2, Edit of a product without rows (D13): when the fragment root's binding context becomes a draft product context (`IsActiveEntity` false) whose `subcategory_code` is set, once per context path, the module calls `requestSideEffects([{ $NavigationPropertyPath: 'details' }])` on it (measured working; `refresh()` on the dependent binding throws). F7 makes the root context the trigger; when those properties are not loaded yet (deep link to an existing draft), no request is needed: the rows were filled at that draft's Edit and come with the page's `GET`. Cost: one `GET Products(..,false)?$select=details&$expand=details(...)` per Edit.
- B4 trigger (D-2): after each write of a field (an input's `change`, the LIST write) the module calls `requestSideEffects([{ $PropertyPath: 'DraftMessages' }])` on the draft product context, in the same `$auto` batch as the `PATCH`; the `patchCompleted` of the dependent `details` binding is never raised (B4) and is dropped. D-3 (duplicate message with the target `/Productsundefined/numberValue`) is re-checked by `ui-verifier` at step 10 after this change and goes to the reviewer if it stays.
- D-6: proposed to `ux-designer`: the multi combo box sets no `valueStateText`, so the flash of SCREENS row 6 shows the framework text (F8) and the popup no longer announces an error sentence without an error. Needs the row 6 sentence changed in SCREENS before step 8.
- B9: proven; the static hint is not built, `req.warn` stays (D16).
