## Decisions that require an ADR

`docs/decisions/ADR-0015-list-report-draft-marker.md` (proposed): the draft/lock marker of a draft-enabled List Report is produced by `@Common.SemanticKey` on the UI annotation layer, naming the element that is both `UI.HeaderInfo.Title` and the first `UI.LineItem` `DataField`; for `Products` that element is `name`; and `name` deliberately stays without a uniqueness constraint. `PATTERNS.md` has no row for this (its "UI Fiori Elements" rows cover `@UI.*` layout and the code-list value help only), so per CLAUDE.md invariant 4 the way is decided once, in an ADR, and turned into a PATTERNS row by `docs-keeper` in step 9. Consequences for `PATTERNS.md`, `docs/STATE.md` and `docs/LESSONS.md` are listed in the acceptance criteria; the status sentence is replaced (not appended to) by the orchestrator when the user approves.

## Decisions for the user

Only the first item can change the plan; the rest are recorded so the autonomous run needs no further input.

1. **`Products.name` uniqueness.** **A (recommended, and what this plan implements): UI-only.** Set the semantic key, add no constraint. Consequence: one file changes, no domain rule and no error text is invented, duplicate names remain legal and merely look alike in the list; the OPA5 row assertions pin an expected count of 1, so a future duplicate in the seed data fails loudly. **B: also add `@assert.unique: { name: [ name ] }` in `db/schema.cds`.** Consequence: the feature grows a phase 2 (`cap-backend-dev` + `test-backend`: a `db/` change, at least two new backend tests for the rejection on Create and on `draftActivate`, a check whether the constraint appears in the EDMX, and a decision on the error text), and the catalog can no longer hold two products with the same name — a real domain restriction that nothing in the request asked for. **C: introduce a proper business key (`productNumber`/SKU) and make that the semantic key.** Consequence: a separate, larger feature (new element, CSV data, LineItem column, filter, i18n, tests); this feature should then be postponed rather than done twice.
2. **Which element is the semantic key** (only relevant if A or B is chosen): `name` (recommended — it is the header title, the first column and `@mandatory`) versus `ID` (technically unique but a UUID, which would put a UUID in the key column and defeat the purpose).
3. **Table type.** Keep the FE default responsive table, which puts the marker into the `Product Name` cell (recommended; no manifest change), versus switching the List Report to a grid table so the marker gets its own unlabelled second column (a `manifest.json` change through Fiori MCP, a different look for the whole table, and a rewrite of the OPA5 column assertions — out of scope).
4. **The old `products-draft-edit` documentation.** Let `docs-keeper` correct the two inaccurate sentences in `docs/features/products-draft-edit/CONTEXT.md` in step 9 (recommended: the verification asked for it and it is one line each) versus leaving that file as a historical record.
5. **Registry generator.** Leave `scripts/gen-registry.mjs` as it is, so `@Common.SemanticKey` does not show up in `docs/registry/SERVICES.md` (recommended: a generator change is a user request, not a feature side effect) versus teaching it to render entity-level `@Common.*` annotations.
