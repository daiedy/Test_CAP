# products-rating-filter: screens

Written by `ux-designer` from the SAP Fiori guidelines; read by `fiori-app-dev`, `ui5-freestyle-dev`, `test-ui` and `ui-verifier`. Backend agents do not read this file. One screen, one user task.

Date: 2026-09-25. Follows the plan-gate answers approved by the user on 2026-09-25 (CONTEXT "User decisions"): Q1 RangeSlider (ADR-0020), Q2 0..5 step 1, Q3 slider only, Q4 `liveMode: true` together with this feature (no Go button; every filter change reloads the table). Marks used below: **(MCP)** read from `fiori-mcp` `search_docs` or `ui5-mcp-server` `get_api_reference`; **(research)** read from `research/custom-filter-mechanism.md` (UI5 1.152.0 CDN sources); **(inferred)** expected behaviour of the framework that nobody has read or measured yet, to be confirmed by `ui-verifier`.

## Floorplan and duplication check
- Floorplan: unchanged List Report + Object Page (`sap.fe.templates.ListReport`, `variantManagement: Page`, `initialLoad: true`). This feature adds one filter field to the existing List Report filter bar and switches the page to `liveMode: true` (PLAN step 4c, page setting read by the List Report view as `liveMode="{viewData>/liveMode}"`, research section 5): the filter bar has **no Go button**, a filter change reloads the table at once. It is not a new screen and needs no new floorplan. User task: "narrow the product list to a band of ratings".
- Why a custom filter field and not a condition field: the Fiori Elements document "Custom Filter" (MCP, FPM explorer `https://ui5.sap.com/test-resources/sap/fe/core/fpmExplorer/index.html#/buildingBlocks/filterBar/filterBarCustom`) says the filter bar picks the most suitable control per data type and allows "a different selection control if it better suits your use case"; its own sample is a custom *range* filter. The integration rules (key = property name, bind to `{filterValues>}` or call `setFilterValues`) come from "Adding Custom Fields to the Filter Bar (V2 & V4)" steps 4-7 and 14 (MCP). The binding direction is fixed by ADR-0020 (accepted, one-way plus `change` handler), not by this file.
- Why `liveMode` is acceptable here: user decision Q4. The `fiori-mcp` snapshot has no `liveMode` document (query "List Report liveMode filter bar Go button" returns only filter bar building block pages); the facts come from research section 5 (CDN). With 15 rows and a small filter bar, one request per change is cheap; the request-per-change behaviour of each field is specified below and measured in scenario M.
- Control guideline: `sap.m.RangeSlider` API reference (MCP) links the SAP Fiori design guideline "Range Slider" `https://experience.sap.com/fiori-design-web/range-slider/`; `sap.m.Slider` links `https://experience.sap.com/fiori-design-web/slider/`. The guideline text itself is not in the MCP snapshot; see "UX risks" for the one guideline concern.
- Duplication: `docs/registry/UI-ARTIFACTS.md` lists "Extensions and fragments: _none_" for `app/products`; pages `ProductsList` and `ProductsObjectPage` only. No existing filter fragment, handler or formatter to reuse. The rating *display* (stars column, Object Page field) from #5 stays untouched; this feature does not add a second rating visualization to the table.

## Screen: Products List Report, filter bar
- Title and subtitle: unchanged (app title from `webapp/i18n` `appTitle`; variant management title "Standard" plus the modified marker `*` when the filter bar differs from the saved variant).
- Filters (no more than 5 by default): **Name, Category, Price, Rating**, in this order; Rating is new, placed directly after Price (`position: { placement: After, anchor: price }`, `availability: Default`, i.e. visible in the bar without opening Adapt Filters). If Fiori Elements also shows its draft "Editing Status" field for the draft-enabled entity, the visible total is 5, still within the limit (inferred).
  - Control: `sap.m.RangeSlider`, `min 0`, `max 5`, `step 1`, `width 100%` of the filter item (the `sap.m.Slider` default, MCP), `progress` on (default, the selected band is highlighted).
  - Recommended display properties, all standard (MCP, `sap.m.Slider`): `enableTickmarks="true"` so the six integer positions 0..5 are visible (a 6-value scale is discrete; without ticks the user cannot tell that 2.5 is not selectable); `showAdvancedTooltip="true"` and `inputsAsTooltips="true"`, because the API says verbatim "To comply with the accessibility standard, it is recommended to set the `inputsAsTooltips` property to true" (the handle tooltip then contains an input field where a number can be typed). These three are a design decision of this file for `fiori-app-dev`; they do not affect the condition mapping of ADR-0020. Whether a typed value in the tooltip input fires the same `change` event as a drag is **inferred** (verifier scenario E).
  - Event: the fragment handles `change` only, never `liveChange`. `change` "is triggered after the end user finishes interacting, if there is any change"; `liveChange` "is triggered during the dragging period, each time the slider value changes" (MCP, `sap.m.Slider` events, inherited by `sap.m.RangeSlider`). With `liveMode` this means one table reload per handle release, not per drag step.
  - Label: "Rating", taken from `Common.Label` `{i18n>Products.rating}` of the service bundle through the Fiori Elements label fallback (research section 2, predicted); no manifest `label`.
  - Value to condition: both handles at 0 and 5 = **no condition** (products with `rating` null stay visible); any narrower band `[lo, hi]` = condition `rating BT lo..hi`, sent as `rating ge lo and rating le hi` as soon as the handle is released (`liveMode`). `lo = hi` is allowed (both handles on the same value, API "The right and left handle can select the same value", MCP) and means "exactly that rating".
- When each filter field reloads the table (`liveMode`, one `Products` request per change):

| Field | Control (FE default unless stated) | A change is | Requests |
|---|---|---|---|
| Name | condition input | Enter or leaving the field with a changed text (`sap.m.InputBase` `change`: "fired when the text in the input field has changed and the focus leaves the input field or the enter key is pressed", MCP) | one per committed text, none per keystroke (inferred for the FE field wrapper) |
| Category | fixed-values dropdown from #3 | selecting a value | one per selection (inferred) |
| Price | condition input | Enter or leaving the field, as Name | one per committed value (inferred) |
| Editing Status | draft status select (FE) | selecting a value | one per selection (inferred) |
| Rating | `sap.m.RangeSlider` (this feature) | handle release after a drag, one keyboard step, or a committed tooltip input | one per release or step; a drag across several ticks is one request (MCP `change` vs `liveChange`) |

- Table columns in order of importance (no more than 7): unchanged (5 columns from #5, Rating stars last with `UI.Importance #Low`). The filter does not add, move or hide a column.
- Actions and their placement (toolbar, row, header): no new action. **No Go button** (`liveMode`). The other filter bar buttons keep their meaning: **Adapt Filters** lists Rating once (Q3); **Clear**, if the page shows it, resets Rating to 0..5 and the table reloads at once (inferred, scenario F). No reset icon next to the slider (the FPM sample in "Adding Custom Fields" step 6 has one; here the full range *is* the reset, and the filter bar's own Clear / variant reset cover the rest).
- Object Page sections: unchanged.
- States of the Rating filter (every change reloads the table at once):

| State | Slider shows | Filter bar condition for `rating` | Table | "Filtered by" (collapsed header) and Adapt Filters count |
|---|---|---|---|---|
| First load, Standard variant | handles at 0 and 5, whole bar highlighted | none (research section 4, M2) | 15 rows, variant not marked modified | Rating not listed; count excludes Rating (inferred) |
| Narrowed | e.g. 4..5 | `BT 4...5` set on `change` (release of the handle or keyboard step) | reloads at once: 8 rows, all 4 or 5 stars; table title count updates | variant marked `*`; Rating listed, e.g. "Filtered By (1): Rating" (inferred wording, FE text) |
| Single value | 5..5 | `BT 5...5` | 4 rows | as above |
| Back to full range | 0..5 | removed (`setFilterValues('rating')`) | reloads at once: 15 rows | Rating no longer listed (inferred) |
| Cleared by filter bar Clear or by selecting the Standard variant | 0..5 (formatter clamps an empty value into 0..5, PLAN criterion "formatRange") | none | reloads at once as the variant defines (inferred) | Rating not listed |
| Restored from a saved variant | the saved band, e.g. 2..4 | `BT 2...4` from the variant | 9 rows | Rating listed |
| Combined with Category KITCHEN and 5..5 | 5..5 | `BT 5...5` plus the category condition | 2 rows | "Filtered By (2): Category, Rating" (inferred) |
| Empty result, e.g. Category KITCHEN and 0..0 | 0..0 | `BT 0...0` | no rows: the table's standard no-data text for a filtered list (FE default, inferred), no custom message | Category, Rating listed |

- Empty state and errors: the empty result uses the Fiori Elements table no-data text, no custom illustration or text. Filtering is read-only and cannot fail on validation: the slider cannot produce a value outside 0..5 or a non-integer (step 1, clamp). A failed `$batch` shows the standard Fiori Elements message handling; nothing feature-specific. A `setFilterValues` promise rejection is a developer error (console), not a user message.
- Roles: `viewer` (CatalogViewer) and `alice`/`bob` (CatalogEditor) see and use the same slider with the same result; filtering does not depend on the role. Draft rows of an editor are filtered by their saved `rating` like active rows (inferred; the draft marker behaviour of `DraftMarkerInListReportJourney` is untouched).
- Locale: the label follows the service bundle (`ru` value exists since #5); the numbers 0..5 in ticks and tooltips are locale-neutral; the handle ARIA texts come from the UI5 `sap.m` message bundle in the session language (inferred).
- Criticality and statuses: none. The slider has no value state; the band highlight (`progress`) is the only visual emphasis and uses the theme default.
- What is shown instead of a UUID (`TextArrangement`): not applicable; `rating` is an integer shown as numbers on the slider and as stars in the table.

## Accessibility
Checklist of the `ui5-best-practices-accessibility` skill (read from the plugin `ui5` 0.1.8, `SKILL.md`, `references/labeling.md`, `references/keyboard.md`); the `fiori-mcp` snapshot has no accessibility document for the filter bar (agent memory), so control facts come from the UI5 API reference (MCP) and are otherwise marked inferred.
- Landmarks and headings: unchanged; the fragment adds no `Title`, `Panel` or page container.
- Labeling (skill topic 2): the fragment has no own `Label`; the filter bar renders the field label "Rating". Requirement: **both handles and the range bar must have an accessible name that contains "Rating"**. Whether the Fiori Elements custom filter wrapper connects its label to the slider (`labelFor` / `aria-labelledby`) is **inferred, not verified**; verifier scenario G checks the accessibility tree. If the name is missing, the fix is the skill's pattern "static ARIA reference": `ariaLabelledBy` of the RangeSlider (a public association, MCP) pointing to a `core:InvisibleText` bound to the same label source (`Common.Label` via metaModel, no new key), placed before the slider in the fragment.
- Values for assistive technology: the RangeSlider renders hidden `InvisibleText` elements for "handles and progress announcement" (hidden aggregation `_handlesLabels`, MCP); expected per handle: `role="slider"`, `aria-valuemin 0`, `aria-valuemax 5`, `aria-valuenow` the handle value (inferred from the control's standard rendering; scenario G).
- Keyboard (skill topic 4): the API lists "Keyboard (Arrow keys, "+" and "-")" as a way to move a handle (MCP, `sap.m.Slider` overview). Expected in addition, from the UI5 slider keyboard handling (inferred, not in MCP): Tab reaches the start handle, then the end handle, then (with `inputsAsTooltips`) the tooltip inputs, in visual left-to-right order; Home/End jump to 0/5; Page Up/Page Down move by a larger step (with a 0..5 scale, effectively to the ends). Each keyboard step fires `change`, which sets the condition, and with `liveMode` **the table reloads after each step** (at most 5 steps across the whole scale; focus stays on the handle during the reload, inferred, scenario E). There is nothing to confirm with Enter: the `FE_FilterSearch` command (Ctrl+Enter) is registered only when `liveMode` is false (research section 5), so it is not available on this page. No `tabindex` > 0, no custom F6 group: the filter bar is already one group.
- Keyboard shortcuts (topic 5): none added; Ctrl+Enter (search) is not registered with `liveMode` and is not replaced.
- Invisible messaging (topic 6): the filter result is announced by the framework table (title count "Products (8)"); the app adds no `InvisibleMessage` call because the app code does not run the search (inferred; scenario G listens for it).
- Reading order (topic 7): DOM order = visual order Name, Category, Price, Rating; the tooltips are rendered in a popup container (`_tooltipContainer`, MCP) and must not steal focus from the handle, also not while the table reloads.
- Target size (topic 8): standard slider handles of `sap_horizon`; no `Link`/`Object*` controls in the fragment, nothing to adjust.

## Theme and tokens
Standard controls only (`sap.m.RangeSlider` with standard properties) in `sap_horizon`; no CSS, no custom colours, no `class` on the slider beyond what Fiori Elements puts on the filter item (UI5 MCP `get_guidelines`: data binding and `core:require` for types and handlers, no globals). ## Verifier scenarios
Design-level scenarios for `ui-verifier`, in addition to the acceptance criteria of `PLAN.md`; run on `npx cds serve --in-memory --port 4004` unless stated. No scenario presses Go: the page has none.
- A. First load: no Go button in the filter bar; Rating after Price, visible without Adapt Filters, handles at 0 and 5, tick marks at 0..5, variant name without `*`, 15 rows, first `Products` `$batch` GET without `rating`, console without "not in the range" warning.
- B. Mouse: drag the start handle from 0 to 4 in one drag and release: the table reloads at once with 8 rows, `$filter` contains `rating ge 4 and rating le 5`, the variant shows `*`, and the network log has exactly one new `Products` request for the drag (none during the drag). Drag the whole band (click on the highlighted range and drag, API "The entire range can be moved along the interval", MCP) from 4..5 to 3..4 and release: 7 rows (3 x3 + 4 x4, research section 6), again one request.
- C. Collapsed header: with 4..5 set, collapse the page header; the collapsed filter summary names Rating and the count includes it. Move back to 0..5: the table shows 15 rows and Rating is no longer named. Record the exact rendered text (inferred wording).
- D. Variant: set 2..4 (table reloads to 9 rows), save as a new variant "Mid ratings"; switch to Standard (slider 0..5, 15 rows without any further action); switch back (slider 2..4, 9 rows). Reload the page with the saved variant selected: the slider shows 2..4, not 0..5 (the one-way display binding risk of PLAN).
- E. Keyboard: Tab to the start handle, Arrow Right x2 (0 -> 2): two reloads, one request each, table at the end shows the rows of 2..5; Tab to the end handle, Arrow Left (5 -> 4): one reload, 9 rows. Focus stays on the handle through each reload. Home/End on a handle jump to 0/5 (one request each). Ctrl+Enter does nothing. If the tooltip input is shown, type 3 into it and leave the field: the handle moves to 3, the condition updates and the table reloads once (typed-input path of `inputsAsTooltips`).
- F. Clear and reset: with 4..5 set, press the filter bar Clear (if present) or select Standard again: slider back to 0..5, `getConditions().rating` empty, Rating not in "Filtered by", table reloads to 15 rows without a further action.
- G. Screen reader / accessibility tree (chrome-devtools snapshot at least): each handle has role `slider`, a name containing "Rating" (en) and the `ru` label in `ru`, `aria-valuemin 0`, `aria-valuemax 5`, `aria-valuenow` matching. Record whether the table count change after a reload is announced. Name gaps go to "UX risks" follow-up, not silently fixed.
- H. Adapt Filters: the dialog lists Rating once; toggling it off hides the slider from the bar and keeps an applied condition counted (inferred); in the dialog's filter view the slider is the same control. Record whether a change in the dialog reloads the table at once or on OK (inferred, framework behaviour, not a defect either way).
- I. Roles and locale: `viewer` gets the same slider and counts and no Go button; `?sap-language=ru` shows the `ru` label, numbers unchanged, no Go button.
- J. Empty result: select Category KITCHEN, then set 0..0: no rows, standard no-data text, no error message.
- K. Narrow width (browser at phone width, informational): the slider stays usable in the collapsed/expanded filter bar and the handles do not overlap the label.
- L. Mock mode (`cd app/products && npm run start-mock`): setting 4..5 gives 8 rows at once as on the real backend, no Go button.
- M. `liveMode` on every field (en and ru, `alice` and `viewer`; network tab filtered on `$batch`): no Go button anywhere in the filter bar (also not in the expanded/collapsed header states). Change each field once and count `Products` requests: measured (research section 8, `VERIFICATION.md`), the first filter change after page load sends **two** `Products` requests for any field (framework, mdc `FilterBarBase._checkAndNotify`; reproduced for Rating and for the standard Name field), every later change sends **one**, and the final rows always match the final conditions. Category, Price and Editing Status request counts are **not measured**. Each request's `$filter` reflects the change and the table rows match it. More than the framework's own doubling on the first change (per keystroke or per drag pixel) is a defect of PLAN step 4/4c, reported, not tuned.

## UX risks
- **Guideline concern, slider for exact values.** The Fiori "Range Slider" and "Slider" guidelines (URLs above, from the MCP API references; the guideline texts are not in the MCP snapshot, so the following is from general design knowledge and **not verified**) recommend a slider when an approximate value is enough and an input when the exact value matters. Here the scale has only six integer values, the user thinks in "stars", and exact typing is still possible through `inputsAsTooltips`; the concern is therefore acceptable, but it is the reason why the tooltip inputs and tick marks are required above rather than optional.
- **Filter bar width.** A filter item in the V4 filter bar is narrow (about the width of an input); a RangeSlider with ticks and two advanced tooltips needs vertical space above the handles. The tooltip may overlap the filter label or the bar above (inferred). Detection: scenarios A and K screenshots. Mitigation within the standard: drop `showAdvancedTooltip`/`inputsAsTooltips` and keep `showHandleTooltip` (default), accepting the API's accessibility note; this is a user decision (Open question 1), not a silent change.
- **Full range excludes nothing, a lower bound of 0 excludes nulls.** 0..5 means "no filter" and keeps products without a rating; 0..4 means "rating between 0 and 4" and drops them. No seeded product has a null rating today, so this is invisible in tests but can surprise a user later. Documented behaviour, no UI hint planned (Open question 2).
- **Display after variant switch or back navigation** depends on the one-way `{filterValues>}` binding plus formatter (PLAN risk 2, predicted from source). Symptom: the slider shows 0..5 while "Filtered by" names Rating. Detection: scenarios D and F.
- **Label and ARIA name** depend on the Fiori Elements wrapper (PLAN risk 3). Symptom: no visible label, or handles announced as "slider" without "Rating". Detection: scenarios A, G, I.
- **Request per change.** With `liveMode` every committed change is a round trip: a keyboard user who walks a handle across the scale sends up to 5 requests, and a Name edit sends one on Enter or leave. With 15 rows this is acceptable. Risk: a quick sequence of keyboard steps leaves an older response on screen (inferred; the framework is expected to show the result of the last change). Detection: scenarios E and M, the final rows must match the final range. A request per keystroke or per drag step is a defect (PLAN risk "liveMode reloads on every filter change").
- **Modified marker with no net change.** Moving a handle and back to 0..5 reloads the table twice and may leave the variant marked `*` although no condition exists (inferred). Cosmetic; record in scenario B/C, not a defect.
- **Variant switch applies at once.** With `liveMode` a variant switch or Clear reloads the table immediately, whether or not the variant is "Apply Automatically" (inferred, framework behaviour); stated so the verifier does not report it as an inconsistency.

## Open questions for the user
1. Handle tooltips: tick marks plus input tooltips (recommended here, accessibility note of the API) or the plain default handle tooltip (more compact in the narrow filter item)? Decide after `ui-verifier` scenario A/K screenshots if the space is tight.
2. Products without a rating: is it acceptable that any narrowed range (including 0..4) hides them, with no "include unrated" option? Recommended: yes, no seeded product is unrated.
