## 4. Row generation: what the handler needs (measured R4-R10)

- The rows are inserted with `INSERT.into(ProductDetails.drafts)` (service entity, run on the database) with `ID`, `product_ID`, `attribute_code`, `position`, `IsActiveEntity: false`, `HasActiveEntity: false`, `HasDraftEntity: false` and the parent's `DraftAdministrativeData_DraftUUID`; without the UUID the insert fails (R10). The parent's UUID comes from `SELECT.one.from(req.subject).columns('ID', 'subcategory_code', 'DraftAdministrativeData_DraftUUID')` in `before('PATCH', Products.drafts)` and from `Products.drafts` by `ID` in `after('EDIT', Products)`.
- Stale rows are removed with `DELETE.from(ProductDetails.drafts).where({ ID: { in: ids } })`; their draft selections go with them (R8).
- Kept rows get the new subcategory's `position` with `UPDATE(ProductDetails.drafts, ID)`.
- The warning is `req.warn({ code: 'PRODUCTS_DETAILS_VALUES_REMOVED', args: [n] })`, `n` = removed rows that had a value or at least one selection; it travels in the `sap-messages` header of the `PATCH` response only (R7). How Fiori Elements shows a warning of a field `PATCH` is not measured (no browser); PLAN step 7a proves it.
- The handler runs after `resetStaleSubcategory` in the same `before('PATCH')` registration: a `PATCH` that carries a non-null `subcategory_code` reconciles; a `null` (also the one set by the reset) keeps the rows (D10 (a)); active writes are never reconciled (R16 guard).

## 5. Scratch handler (sketch, not the implementation)

`before('PATCH', Products.drafts)`: `resetStaleSubcategory`, then `if ('subcategory_code' in req.data && req.data.subcategory_code)` reconcile. `after('EDIT', Products)`: read the new draft, reconcile with its own subcategory. Reconcile: `SELECT attribute_code, position FROM SubcategoryAttributes WHERE subcategory_code = :s`; `SELECT` the draft rows of the product; delete rows whose attribute is not assigned (count the filled ones, warn); insert the missing ones; update `position` of the kept ones. One `SELECT` of assignments, one of rows, one of selections for the filled count, one `DELETE`, one `INSERT`, at most three `UPDATE`s per subcategory change.

## 9. Rejected mechanisms (this revision)

| Mechanism | Why not |
|---|---|
| One `value : String` column with a per-type regex | user decision U7: typed columns and UI5 types, no regex |
| `Integer` column next to `Decimal` | one `Decimal(15, 3)` column; INTEGER is `floor(x) = x` (portable, R14) and the UI5 Decimal type with scale 0 |
| Server scale check per DECIMAL attribute | `round(x, n)` is non-portable (cds-mcp); the column scale 3 is enforced (`ASSERT_DATA_TYPE`, R14), the attribute scale on the client |
| Delimited string for MULTI_LIST | user addition: normalized child entity, each value validated and filterable |
| `@assert.unique` on `ProductDetailSelections` | the ADR-0026 measurement (500 `ERR_SQLITE_ERROR` with `@cap-js/sqlite`) applies; the constraint branch gives 400 and draft messages (R17, R21) |
| Rows created by `srv.new` | creates whole drafts, not children of an existing draft (cds-mcp) |
| Rows created only at display time (virtual rows) | no row to bind and `PATCH`; the user decided rows exist (U2) |
| Reconcile on the active path | the ADR-0024 rule: active writes are not reset; the root branch rejects (R16) |
| Delete all rows when the category change empties the subcategory | D10 (b): loses `COLOUR`/`MATERIAL` values that the next subcategory may share; one more side-effect target |
| Copy-free order (sort by attribute name) | the user asked for an order per subcategory; a calculated element cannot reach the assignment row (a to-many path, ADR-0026 compile fact) |
