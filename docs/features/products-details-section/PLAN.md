## Decisions that require an ADR
- ADR-0027 amendment "Browser proof of the fragment" (2026-10-12, phase 3): the LIST write through a one-way key and a control validation message, the own-request `selections` binding, the Edit refresh of `details`; mechanisms inside decision 5, no user decision changed.
- ADR-0027 "Typed product details as a generated form" (accepted 2026-10-12, `docs/decisions/ADR-0027-typed-product-details-form.md`, D18): value types on the attribute with a `DetailValueTypes` code list; typed columns and the second composition level `ProductDetailSelections` for MULTI_LIST; the allowed values `DetailListValues` as a code list per attribute; declarative typed and membership rules; rows generated and reconciled by the existing draft handler (U2, U3) and filled at Edit; the generic custom section fragment with a factory and UI5 types; it supersedes ADR-0026 decisions 3, 4, 6 and 7 and keeps 1, 2 and 5. No `PATTERNS.md` row covers handler-created composition children, typed EAV values or a second composition level today.
- No new runtime or dev dependency, no change to authentication: no further ADR.

## Risks
- B1, proven (step 7): the `formElements` factory resolves through `core:require`; FE merges the `details` binding with its parameters into the page's product `GET` (no own `GET`). Measured costs: in edit mode one `attribute/values` `GET` per list control; after ruling B7 one own `selections` `GET` per MULTI_LIST row. Skeleton defect D-1 (`visible` expressions on a string code) fixed in step 8. The static-template fallback is not used.
- B2, refuted for a product without rows (the `draftEdit` response carries `details: []`, the `after('EDIT')` fill comes later); chosen (ruling B2, measured): the module calls `requestSideEffects([{ $NavigationPropertyPath: 'details' }])` on the root context once per draft context path with a `subcategory_code` (FE binds the draft context before it sets the edit mode); `refresh()` on the dependent binding throws. Cost: one `GET` per Edit. Verified in the browser at step 10 (criterion "a product created through the API showing its fields right after Edit").
- B3, proven: a row `PATCH` goes to `Products(...,false)/details(...,false)` with 204, no 422.
- B4, mapping proven (value state with the project text on the input); the skeleton trigger (the dependent binding's `patchCompleted`) never fires (D-2); chosen: `requestSideEffects([{ $PropertyPath: 'DraftMessages' }])` on the product context after each field write, in the `PATCH`'s batch. D-3 (a duplicate message with the target `/Productsundefined/numberValue`) re-checked at step 10, then the reviewer.
- B5, proven: the per-row Decimal type parses `ru` "1,2", rejects non-numbers, extra decimals, fractions of INTEGER and out-of-range values before any request, with framework texts naming the bound.
- B6, refuted in detail: a two-way `selectedKey` `PATCH`es `listValue_code: null` while the user types a non-item text, and the module's `setValueState` is no message, so it does not block Save. Chosen (ruling B6, ComboBox kept, SCREENS row 5 stays true): `selectedKey` `OneWay`; the module writes only in `change` through the row context `setProperty`; a non-item text adds a client validation message on `<comboBoxId>/selectedKey` (`ControlMessageProcessor`, `validation: true`, the shape of the framework's own type errors), which sets the Error state and blocks Save like B11 and survives `DraftMessages` reads. Residual: after the clear icon on a non-item text the empty field is committed at the next focus leave (OPA5 criterion "A list field accepts only its values", step 10). `sap.m.Select` is not used (the user requires a ComboBox).
- B7, refuted: the dependent `selections` binding has no own cache, `create()` sends nothing and fails. Chosen (ruling B7, measured `POST` 201 and `DELETE` 204): the `dependents` binding of the multi combo box with `parameters: { $$ownRequest: true, $select: 'ID,IsActiveEntity,value_code' }`; `selections` leaves the section's `$expand`; keys, display join and the row's "filled" read that binding. The named fallbacks (`selectionChange`, remove buttons with an Add box) need the same create and are not used.
- B8, proven: `#SubcategoryChanged` re-reads `details` with the page's `DraftMessages` read; the fields follow at once; no module refresh.
- B9, proven: the warning shows as the Warning value state with its text on the Subcategory field right after the change and is listed in the message popover; it clears at the next `DraftMessages` read after another field change. The static hint is not built, the handler's `req.warn` stays (D16). OPA5 asserts the Subcategory value state Warning with the text.
- B10, proven for inputs and LIST fields (the counter follows each `PATCH` and clearing); MULTI_LIST token removal is proven by the OPA5 criterion "A multi-value field adds and removes values" once ruling B7 is built.
- The handler inserts into the draft table with the parent's `DraftAdministrativeData_DraftUUID` (R10: 500 without it); a future cds draft change can break this; the phase 2 tests detect it.
- `@readonly` on `ProductDetails.position` drops client input but keeps the handler's value through activation (R5); a row created through the API (deep `POST` of the product, `POST Products(...,true)/details`) has a `null` position, which SQLite sorts first under `$orderby=position` (R23, other databases not measured); the next Edit gives it the assignment's position; the fragment adds no nulls rule (step 8).
- Products created by `importProducts` or the API show an empty section until their first Edit (D13); this includes a draft created by a `POST` that already carries `subcategory_code`: only a `PATCH` of the subcategory reconciles, FE Create posts an empty draft, so U2 holds in the UI (R24, accepted under D13; the rejected `after('NEW')` alternative is in research section 10).
- A top-level `DELETE` of a detail row or a selection is accepted for an editor like the same `DELETE` through the product (R22): an API client can leave a product without a row of an assigned attribute, the next Edit refills it empty (D13); no guard (declarative `Capabilities` restrictions and a handler rejected in research section 10), pinned by step 6b.
- `ASSERT_DATA_TYPE` rejects a non-number even on a draft `PATCH` (R11): the client type must catch it first (B5), otherwise the user sees a 400 instead of a field message.
- Mock mode (`npm run start-mock`) needs the new JSON files and does not run the handler (no row generation on subcategory change); not a gate.
- Test counts are expected values; each gate re-derives them and quotes its own; the contract figure 1591 was measured on the scratch (research section 7).
- B11, proven: a client type error of a fragment input blocks Save (no `draftActivate`) with the error and the field label in the message popover; FE stops Save on a message with `validation: true` whose control lies in the page (research F3), which ruling B6 reuses for the LIST field.
- No change to what any endpoint answers to an unauthenticated caller: the new sets sit under `@requires: 'authenticated-user'`; the CI readiness probe, the `run-app`/`test-all` smoke curls, the `ui-verifier` server check and the README need no update.
