## Deviations from the plan
- **"One `Products` request per change" (PLAN criterion, `SCREENS.md` scenario M).** Not literally true: the first filter change after page load sends **two** `Products` requests for any field, a framework behaviour of `liveMode` (mdc `FilterBarBase._checkAndNotify`), reproduced for both the Rating slider and the standard Name field, not specific to the custom filter field. Every later change sends one request, and the final table rows always match the final conditions (no stale data observed). The acceptance criterion and the `SCREENS.md` scenario were reworded to this measured fact rather than the plan's prediction. Category, Price and Editing Status request counts were **not measured** within the verifier's turn budget (only Rating and Name were); reviewer judgement (`REVIEW.md`): a wording defect against measured framework behaviour, not a defect of the feature, no separate user decision needed.
- **Saved variant restore (`SCREENS.md` scenario D).** Not verifiable in the FLP sandbox: `flpSandbox.html` sets no `data-sap-ui-flexibility-services`, so "Save As" goes to the default `LrepConnector` (404s), the change stays `NEW`, and switching variants erases it via `eraseDirtyChangesOnVariant`. `fiori-app-dev` reproduced the identical failure on `main` with a standard field (`Category=KITCHEN`, no custom filter field involved) and confirmed the fix works with a `SessionStorageConnector`. **User decision (2026-09-25): separate backlog issue, not part of this feature.** The PLAN criterion is marked accordingly; `ui-verifier`'s "F. Clear / reset" scenario exercises the same variant-select code path (Standard variant resets the slider), so the custom filter field's own reset behaviour is still covered.
- A new console warning, `Invalid empty segment - /Products//Products/rating` (`ODataMetaModel`), appears once per page load; most likely the label-fallback mechanism for a manifest filter field without `label`/`property` (as ADR-0020 requires). No visible or functional effect measured in any scenario. Recorded in `docs/LESSONS.md` ("Pending" section) instead of fixed, since adding `property`/`label` would be outside the two-entry ADR-0020 exception.

## Lessons
Four entries added to `docs/LESSONS.md`:
- `sap.fe.test` field identifiers (`{ property: <key> }`) never match a custom filter field's rendered id (`::CustomFilterField::<key>` vs `::FilterField::<key>`); the mdc FilterBar still reports `showGoButton: true` under `liveMode`, so "no Go button" needs a rendered-control check; a manifest filter field without `label`/`property` triggers the `Invalid empty segment` console warning (`Pending`, candidate: TESTING.md, PATTERNS "Custom filter field").
- The FLP sandbox has no flexibility connector, so variant "Save As" silently fails and a later variant switch erases the change; `ControlVariantApplyAPI.activateVariant`/`StateUtil.applyExternalState` bypass the failing code path, so a variant-restore test must fire a real `VariantManagement` select event (`Pending`, tracked as `STATE.md` open debt and a separate backlog issue).
- UI5's CDN bootstrap logs at ERROR level by default; a "no warning" claim needs `sap-ui-log-level=WARNING` and a positive control (`Pending`).
- `fiori-mcp` 1.12.2 `list_functionality` has no id for `filterFields` or `liveMode` (`Pending upstream`, tracked as `STATE.md` open debt, `upstream-watcher` re-checks on each bump).
