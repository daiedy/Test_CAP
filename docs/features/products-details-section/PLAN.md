Date: 2026-10-12 (revision 2). Status: approved (user, 2026-10-12: revision 2, D10-D23 as recommended, D18 ADR-0027 accepted; the user rejected the table section on 2026-10-12 after phase 4 round 1 and decided U1-U7 plus the MULTI_LIST addition, `CONTEXT.md` "User decisions"; revision 1 was approved on 2026-10-11 and its phases 2-3 are committed at `59b51fc` and `001f961`). Shape (ADR-0018): one criterion per line under "Acceptance criteria", table rows only under "Steps"; explanations belong in `CONTEXT.md` or `research/`. `node scripts/check-feature-docs.mjs products-details-section` verifies the shape at the phase 1 gate.

Contract rule: a step that changes the OData model (`db/*.cds`, `srv/**/*.cds`, `app/*/annotations/*.cds`) schedules `npx vitest -u` and `cds compile '*' --to edmx-v4 -s CatalogService -l en > app/products/webapp/localService/metadata.xml` in the same phase, never in a later one; the sync test in `test/metadata.test.js` turns red at that phase's gate otherwise (PATTERNS "OData contract"). In this revision only phase 2 changes the model: the removal of the table annotations sits in phase 2 because the old `UI.LineItem` and `Common.Text` paths point at the removed `value` and `attributeName` (measured, `research/typed-form-facts.md` section 7); phase 3 changes `manifest.json`, the fragment and tests only, so its contract figure equals phase 2's.

Baseline at `cc23ef0` (re-count at each gate): `npm test` 196 in 11 files (`test/catalog-service.test.js` 96 with 21 in `describe('CatalogService.ProductDetails')`, `test/metadata.test.js` 14, `test/products-import.test.js` 20); `npm run test:ui` 58 (56 `opaTest` + 2 QUnit, 5 of them in `ProductDetailsSectionJourney.js`); `metadata.xml` 1287 lines. Expected: phase 2 `metadata.xml` 1591 (measured on the scratch model of research section 6 with the D17 seed shape, including both `position` elements and their titles), phase 3 the same; `npm test` 208 (`catalog-service` 108, `metadata` 14); `npm run test:ui` 60 (58 opaTest + 2 QUnit). Every status, code and target below was measured on the scratch (research section 3), none is assumed; the UI behaviour of phase 3 is proven in the browser by step 7 first.

## Risks
- B1 (not verified by MCP, BindingParser source): the custom section fragment binds `formElements` with a `factory` resolved through `core:require`, relative to the Object Page context, with `parameters` `$expand=attribute($expand=values),selections` and `$orderby=position`. Detection: no form elements or a binding error in the console. Fallback: a static `FormElement` template with four type-specific controls and `visible` expressions on `attribute/valueType_code`, no factory; client constraints then lose the per-attribute bounds (the server messages still show them).
- B2: Edit rebinds the fragment to the draft context and shows the rows the server created at Edit (D13). Detection: active rows or no rows in edit mode. Fallback: refresh the `details` binding in the module on the `ui>/isEditable` change.
- B3: two-way binding `PATCH`es `Products(...,false)/details(...,false)` (the relative path; the FE table did so in revision 1), never the top-level set (422). Detection: a 422 in the `$batch`. Fallback: none expected; stop and return to `architect`.
- B4: server draft messages (targets `details(ID=...,IsActiveEntity=false)/<column>`, R12) show as value states on the inputs. Detection: message only in the popover. Fallback: accept the popover (FE standard), record it in VERIFICATION.
- B5: `sap.ui.model.odata.type.Decimal` with `scale` (0 for INTEGER) and `minimum`/`maximum` from `attribute` parses `ru` "1,2" and shows the bound in its error. Detection: a `PATCH` with a wrong value or none. Fallback: constraints without bounds (format only), the server range message remains.
- B6: `sap.m.ComboBox` items bound to `attribute/values` of the row, `selectedKey` two-way on `listValue_code`; non-item text gets the error state from the module's `change` check. Fallback: `sap.m.Select` (no free text, no check needed).
- B7: `sap.m.MultiComboBox` keys from the row's `selections`; `selectionFinish` creates and deletes contexts of that list binding (`POST`/`DELETE` through `Products(...)/details(...)/selections`); display joins `value/name` with a comma. Detection: no `POST`/`DELETE` in the `$batch`, or a 422. Fallback: `selectionChange` (one create or delete per click) instead of `selectionFinish`; if contexts cannot be created on that binding, a list of selections with a remove button and a combo box with an Add button.
- B8: `#SubcategoryChanged` (`TargetEntities: [ details ]`) re-reads the fragment's own-cache `details` binding (Context source: side effects are delegated to dependent bindings with own caches). Detection: old fields after a subcategory change. Fallback: the module refreshes the binding on the Object Page context's `patchCompleted`.
- B9: the `PRODUCTS_DETAILS_VALUES_REMOVED` warning arrives only in the `sap-messages` header of the `PATCH` (R7); how FE shows it is unmeasured. Detection: no visible warning. Fallback: the `ux-designer`'s static hint (D16 alternative), the handler's `req.warn` removed.
- B10: the counter "Filled N of M" follows value edits in the draft (computed in the module from the list binding's contexts: a value, or at least one selection for MULTI_LIST). Fallback: recompute on the list binding's `change` and the contexts' `patchCompleted`.
- The handler inserts into the draft table with the parent's `DraftAdministrativeData_DraftUUID` (R10: 500 without it); a future cds draft change can break this; the phase 2 tests detect it.
- `@readonly` on `ProductDetails.position` drops client input but keeps the handler's value through activation (R5); a deep `POST` through the API creates rows without a position (sorted last).
- Products created by `importProducts` or the API show an empty section until their first Edit (D13).
- `ASSERT_DATA_TYPE` rejects a non-number even on a draft `PATCH` (R11): the client type must catch it first (B5), otherwise the user sees a 400 instead of a field message.
- Mock mode (`npm run start-mock`) needs the new JSON files and does not run the handler (no row generation on subcategory change); not a gate.
- Test counts are expected values; each gate re-derives them and quotes its own; the contract figure 1591 was measured on the scratch (research section 7).
- B11: client type errors of the fragment's inputs (non-number, too many decimals, out of range) reach the FE message model and block Save like the FE fields (SCREENS UX risk 5). Detection: Save succeeds with the last valid value. Fallback: the server range and whole-number checks still reject at activation; a non-number is never written (`ASSERT_DATA_TYPE` would answer 400, R11), so the risk is a silently kept old value; then `handleValidation` through Fiori MCP if the app lacks it, else a reviewer-accepted known behaviour.
- No change to what any endpoint answers to an unauthenticated caller: the new sets sit under `@requires: 'authenticated-user'`; the CI readiness probe, the `run-app`/`test-all` smoke curls, the `ui-verifier` server check and the README need no update.
