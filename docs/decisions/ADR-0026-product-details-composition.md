# ADR-0026: Product details as a composition of reusable attribute values

Date: 2026-10-11. Status: accepted (user, 2026-10-11, feature `products-details-section`).
<!-- On acceptance replace the whole Status sentence with the accepted form; never append to the proposed one. -->

## Context
Issue #9 asks for an Object Page section "Details" whose content depends on the product's subcategory. The user chose dynamic attributes (reading (a)) over fixed typed fields, free-text values with a unit on the attribute, attributes reusable across subcategories through an assignment entity, and editing inside the product draft by a `CatalogEditor` with read-only access for a `CatalogViewer` (`CONTEXT.md` "User decisions"). This is the first composition of the model and the first entity-attribute-value shape. `PATTERNS.md` has the row "Parent-child relationship (document)" without an example and nothing on: a value help whose In parameter lives on the parent of a composition child, a set-membership rule ("the attribute is assigned to the product's subcategory") between a child row and a code list, uniqueness inside a draft tree, the authorization of a directly addressed composition child, or what happens to child rows when the parent's subcategory changes.

Evidence: `docs/features/products-details-section/research/framework-facts.md` (cds-mcp, fiori-mcp until its outage, UI5 1.153.0 CDN sources, cds 10.1.1 scratch compile and runtime matrix).

## Decision
1. **Shape.** `db/schema.cds`: `Products.details : Composition of many ProductDetails on details.product = $self`; `DetailAttributes : CodeList { key code : String(30); unit : String(10); subcategories : Association to many SubcategoryAttributes on subcategories.attribute = $self; }`; `SubcategoryAttributes : cuid { subcategory : Association to Subcategories; attribute : Association to DetailAttributes; }` with `@assert.unique.pair: [ subcategory, attribute ]`; `ProductDetails : cuid { product : Association to Products; attribute : Association to DetailAttributes; value : String(100); }`. The assignment entity is keyed by `cuid` like every non-code entity (CONVENTIONS section 3); the pair is unique by the persistence constraint, which lives in `db/` because it is DDL, not semantics. A global attribute is assigned to many subcategories in the CSV, no special branch.
2. **Service.** One projection per entity in `srv/catalog-service.cds`: `ProductDetails` with the same `@restrict` as `Products` (capire: only the target entity of a request is authorized, and the target of `Products(...)/details` is the child, so the child's own grants guard reads and, on the active path, writes through the product; corrected 2026-10-12 by the phase 2 mutation measurement: without them a `CatalogViewer` creates a row through `POST Products(<id>,IsActiveEntity=true)/details` with 201 and a user without a catalog role reads `ProductDetails`; top-level writes are refused by lean draft with 422 `DRAFT_MODIFICATION_ONLY_VIA_ROOT`, a viewer's top-level `POST` without `IsActiveEntity` by the grant first with 403, measured); `@readonly DetailAttributes`; `@readonly SubcategoryAttributes { *, attribute.name as attributeName }`, the value-help collection with the localized attribute name flattened. `@odata.draft.enabled` stays on `Products` only (ADR-0012); the child is draft-enabled by the composition.
3. **Value.** `value : String(100)` free text, `@mandatory` together with `attribute`; the unit is an element of the attribute and is displayed next to the value from `attribute.unit`.
4. **Value help of the child row.** The ADR-0024 decision 1 shape on `ProductDetails.attribute` in `app/products/annotations/ProductDetails.cds`: `Common.Text: attribute.name`, `#TextOnly`, `ValueListWithFixedValues: true`, one hand-written `Common.ValueList` with `CollectionPath 'SubcategoryAttributes'`, `ValueListParameterInOut` `attribute_code`/`attribute_code`, `ValueListParameterIn` **`product.subcategory_code`**/`subcategory_code` (a navigation path to the parent, compiled to `PropertyPath="product/subcategory_code"`), `ValueListParameterDisplayOnly` `attributeName`. FE 1.153 reads In-parameter sources with `bindingContext.requestProperty(...)`, so a navigation path is fetched late from the row context, and a draft row's `product` is the draft parent (measured). No calculated element, no copied foreign key.
5. **Guards, declarative.** In `srv/annotations/ProductDetails.cds`: `attribute @mandatory @assert.target @assert: (case when attribute.code is not null and product.subcategory.code is not null and not exists attribute.subcategories[subcategory.code = $self.product.subcategory.code] then 'PRODUCTS_DETAIL_ATTRIBUTE_NOT_ASSIGNED' when attribute.code is not null and exists product.details[attribute.code = $self.attribute.code and ID != $self.ID] then 'PRODUCTS_DETAIL_ATTRIBUTE_DUPLICATE' end)`; `value @mandatory`. In `srv/annotations/Products.cds` the existing `subcategory` constraint gets a second branch `when subcategory.code is not null and exists details[attribute.code is not null and not exists attribute.subcategories[subcategory.code = $self.subcategory.code]] then 'PRODUCTS_SUBCATEGORY_HAS_FOREIGN_DETAILS'`. `$self` is the annotated entity inside an infix filter (CDL name resolution; measured). Measured coverage: active writes through the root, deep writes, `draftActivate` (every child row re-checked, targets `in/details(ID=...,IsActiveEntity=false)/attribute_code`), draft messages on a child `PATCH` (shown on the child and on the root). **No `@assert.unique` on `ProductDetails`**: cds 10.1.1 with `@cap-js/sqlite` answers a violation with 500 `ERR_SQLITE_ERROR` on the active path and writes nothing on a draft; the constraint branch gives 400 with the key and the rows named. No handler.
6. **Subcategory change with existing rows (PLAN D1, accepted as (i) by the user on 2026-10-11).** Nothing is deleted; the root branch writes the message on the Subcategory field as soon as the draft subcategory changes, Save is rejected naming each row that does not fit, the user deletes or changes those rows. Option (ii), deleting foreign rows in `resetStaleSubcategory`, was rejected (see Alternatives); decision 5's root branch covers the active API path either way.
7. **UI.** `app/products/annotations/Products.cds`: `UI.ReferenceFacet` `Details` with `Target: 'details/@UI.LineItem'`; `Common.SideEffects #SubcategoryChanged { SourceProperties: [ subcategory_code ], TargetEntities: [ details ] }` and `details` added to `#CategoryChanged`, because the rows cache the parent's `subcategory_code` for their value help. `ProductDetails.cds`: `UI.HeaderInfo` (the table title needs `TypeNamePlural`; the facet `Label` is the same i18n word in both locales), `UI.LineItem` `attribute_code` with `![@UI.Importance]: #High` (the row's identity stays out of the pop-in), `value`, `attribute.unit`, `Common.SideEffects #AttributeChanged { SourceProperties: [ attribute_code ], TargetProperties: [ 'attribute/name', 'attribute/unit' ] }`. Inline creation is the FE V4 default of an Object Page table, Create and Delete exist only in edit mode, so no `manifest.json` change and no `UI.*Hidden` on the child: a viewer never enters edit mode (ADR-0013).

First application: feature `products-details-section` (#9).

## Alternatives
| Option | Why rejected |
|---|---|
| Reading (b): fixed typed detail elements on `Products`, shown per subcategory with `UI.Hidden` paths | user decision 1; every new attribute is a model and contract change, 20 attributes are 20 columns on every product |
| Attributes bound to one subcategory (`DetailAttributes.subcategory`) | user decision 3; `Colour` would exist 15 times with 15 text rows |
| Composite key `(subcategory, attribute)` on `SubcategoryAttributes` | CONVENTIONS allow composite keys only for text and code tables; nothing references the assignment row, so the natural key buys nothing; `@assert.unique.pair` costs one line and 0 EDMX lines; the value help maps `attribute_code`, not the key |
| Child referencing the assignment row instead of the attribute | changes the agreed shape and the row's foreign key to an assignment UUID; a `Colour` row would not survive a subcategory change even where `Colour` is assigned to the new subcategory; the `exists` constraint reaches the same declarative guard |
| Unmanaged `assignment` association on the child (`on ... assignment.subcategory = product.subcategory`) | compile error: a managed association may be followed only to its target's keys in an ON condition |
| Calculated element `subcategory_code = product.subcategory_code` on the child as the In parameter | a contract property without business meaning; FE reads the navigation path directly |
| Foreign key copied into the child by a `before('NEW')` handler | duplicated data, stale after a subcategory change, imperative (invariant 6) |
| `before` handlers for the membership and duplicate rules | four registrations (`NEW`/`PATCH` drafts, `CREATE`/`UPDATE` active, deep root) and no draft-message path; the constraints cover all measured paths |
| `@assert.unique` on `ProductDetails` (user decision 6 as written) | 500 on every active duplicate, nothing on a draft (measured); the constraint branch replaces it |
| `@odata.contained` on `details` (no `ProductDetails` entity set) | not needed: the set is write-locked by lean draft and read-guarded by `@restrict`; the mock server and `sap.fe.test` work with plain entity sets |
| `UI.FieldGroup` section | one element per attribute, that is reading (b) |
| Hide the table's Create while the subcategory is empty (`InsertRestrictions.NonInsertableNavigationProperties` with an `If`) | the flow is category, subcategory, details (ADR-0025 makes the subcategory mandatory); the dropdown is unfiltered and the server rejects at Save; may be added later (PLAN D5) |
| Option (ii) delete foreign rows silently on the draft subcategory PATCH | destroys typed values without confirmation; a handler plus a test matrix; the root branch is needed anyway for the active API path; kept as the user's option in PLAN D1 |
| Option (iii) keep foreign rows and block only new ones | not expressible declaratively (needs old-versus-new row knowledge) and leaves inconsistent data |

## Consequences
- `PATTERNS.md`: "Parent-child relationship (document)" gets the example `Products.details` and the facts "the child inherits drafts from the root, top-level writes to it answer 422, the child projection carries its own `@restrict`, which guards reads and active-path writes through the root" (corrected 2026-10-12); "Cross-field consistency check" gets the set-membership form (`exists <to-many>[... $self.<path>]`, `$self` is the annotated entity) with the example `ProductDetails.attribute`; "Dependent value help" gets "on a composition child the In parameter may be a navigation path to the parent (`product.subcategory_code`), paired with a `Common.SideEffects` from the parent property to the composition"; "Authorization" gets the composition sentence; the row "New entity" or `.claude/rules/db-model.md` (protected) gets "persistence constraints `@assert.unique` live in `db/`".
- `templates/annotations-ui.cds`: a commented child-row value help block; `templates/entity.cds` already shows a composition.
- `docs/architecture/TESTING.md` "cds 10 specifics": `DRAFT_MODIFICATION_ONLY_VIA_ROOT` for top-level child writes; activation targets `in/details(ID=...,IsActiveEntity=false)/<element>`; `@assert.unique` violations are 500s with `@cap-js/sqlite`; a child `POST` writes no draft message, a `PATCH` does.
- `docs/architecture/ARCHITECTURE.md` "Current model" and the registry diagram gain the composition and the two code-list-like entities.
- EDMX cost on this model: phase 2 +293 lines (entity types, sets, draft elements of the child, texts, three generated value lists, labels), phase 3 +96 net (facet, line item, header info, three side-effect records rendered twice, the hand-written value list replacing the generated one, text annotations).
- The reviewer accepts: no handler for these rules, no `@assert.unique` on `ProductDetails`, exactly one `Common.ValueList` on `ProductDetails/attribute_code`, no `manifest.json` diff, the constraints only in `srv/annotations/`.
- Follow-ups enabled, each its own issue: typed values or per-attribute value lists, an Excel import column for details, hiding Create until a subcategory exists, a maintenance screen for attributes and assignments (today CSV only).
