## Pending

- 2026-09-29. `products-excel-upload` (#7): Fiori Elements V4 (UI5 1.152) does not refresh the List Report by itself after a collection-bound action that returns a scalar (`importProducts` returns `Integer`); it reloads only after Create, Delete, the draft actions and a bound action whose returned instance differs from the bound one. `@Common.SideEffects` with an absolute `TargetEntities` path closes the gap (PATTERNS "Refresh after an action", ADR-0021 amendment A). Status: transferred to PATTERNS in the same change; kept here as the source-attributed record for `/retro`.
- 2026-09-29. `products-excel-upload` (#7): a Fiori Elements V4 action parameter is marked required in the dialog, and an empty submit blocked, only through the parameter's own `Common.FieldControl` (`FieldControlHelper.isRequiredExpression`, UI5 1.152 `sap/fe/core/templating/FieldControlHelper-dbg.js`); `Nullable="false"` from `not null` is ignored, and so is any field control on the underlying stream element. `@mandatory` on the action parameter emits `Common.FieldControl: #Mandatory` and the required asterisk lands on the parameter's `Label`, not on the `sap.ui.unified.FileUploader` itself (PATTERNS "Mandatory field", ADR-0021 amendment B). Status: transferred to PATTERNS in the same change; kept here as the source-attributed record for `/retro`.
- 2026-09-29. `products-excel-upload` (#7), decompression guard (ADR-0021 amendment D, research section 8): a request body-size limit only bounds what travels over HTTP, not what an archive unzips to (a 207 KB upload can hold a 200 MB text value); `read-excel-file/node` 9.3.10 inflates every kept zip entry into memory before parsing. Guard by counting inflated bytes with `node:zlib` `inflateRawSync(..., { maxOutputLength })` before the parsing library runs. A `worker_threads` Worker with `resourceLimits.maxOldGenerationSizeMb` does **not** bound this: inflated entries are `Buffer`s, external memory outside the V8 heap the limit governs, so the worker only dies after the memory is already spent. `write-excel-file` 4.1.1 writes every entry with flag bit 3 and size 0 in the local header (the "data descriptor" path, size discovered by scanning to the descriptor signature), not a declared size, so fixtures built with it exercise a different path of a size-guard walk than a workbook with sizes in its headers. Status: pending triage by `/retro` (candidate: TESTING.md or a security note for file-upload actions; the guard itself is in PATTERNS "File upload through an action").
- 2026-09-29. `products-excel-upload` (#7): `test-backend` added a per-`it` `afterEach` (not only an end-of-`describe` cleanup) in `test/catalog-service.test.js` to delete rows an import test created, so that a red assertion in one `it` does not leave rows behind that shift the row counts asserted by later tests in the same file. Status: pending triage by `/retro` (candidate: `tests-backend.md` cleanup rule).
- 2026-09-29. The `Write`/`Edit` tools decode a single-backslash `\u` escape followed by four hex digits in their string parameters into the real character before writing to disk (a doubled backslash lands as two literal backslashes); there is no way to put a literal single-backslash escape on disk through these tools. Writing Russian text or a Unicode escape example into an English-only file (`docs/**`, `.claude/agent-memory/**`) this way silently produces real Cyrillic characters that the Cyrillic PostToolUse hook then flags. Grep the file for non-ASCII right after writing test or example data that is meant to hold `\u` escapes literally; give Russian values as `U+XXXX` code points in English-only prose instead. Status: pending triage by `/retro` (candidate: a tooling note in `tests-ui.md` or the `project-protocol` skill).

## Pending upstream

- 2026-09-29. `products-excel-upload` (#7): in cds 10.0.6, `req.error(status, 'KEY', args)` (the positional form) rewrites `code` to the key only for the top-level error of a response (`normalized()` in `@sap/cds/lib/srv/protocols/http.js` replaces `code` by the key only when `e.code == e.status`); a message collected as one of several `details[]` entries keeps the numeric `status` in its `code` instead, because it never goes through that top-level path. Workaround: the object form `req.error({ status, code: 'KEY', args })` per message (PATTERNS "Business logic error", ADR-0021 decision 4). Status: `Pending upstream @sap/cds`; not a project defect, no local patch planned.
- 2026-09-29. `products-excel-upload` (#7): cds 10.0.6's OData `sap-messages` header (`ODataAdapter.sap_messages4`) resolves a message key through `normalized()`, which looks it up only in `i18n.default_language`, never through `localized()`; a `req.info`/`req.error` key is therefore never translated into the caller's `Accept-Language` by the framework. Workaround: resolve the text by hand with `cds.i18n.messages.at(key, req.locale, args)` and pass it as `message` (PATTERNS "Success message of an action", ADR-0021 decision 4). Status: `Pending upstream @sap/cds`; not a project defect, no local patch planned.

- 2026-09-25. `products-rating-filter` (#6), two `liveMode`/custom-filter-field testing quirks: (1) `sap.fe.test` field identifiers (`{ property: <key> }`) resolve to `::FilterField::<key>` and never match a custom filter field's rendered id `::CustomFilterField::<key>`; probe the id on the running app instead of guessing. (2) under `liveMode: true` the mdc FilterBar still reports `showGoButton: true`, so "no Go button" must be asserted on the rendered control, not on that flag. Separately, a manifest `filterFields.<key>` entry with no `label`/`property` (ADR-0020) logs `Invalid empty segment - /Products//Products/rating` (`ODataMetaModel`) once per page load; no visible or functional effect measured. Status: pending triage by `/retro` (candidate: TESTING.md, PATTERNS "Custom filter field").
- 2026-09-25. `products-rating-filter` (#6): `app/products/webapp/test/flpSandbox.html` sets no `data-sap-ui-flexibility-services`, so a filter variant "Save As" fails (`HEAD .../sap/bc/lrep/actions/getcsrftoken/` and `GET .../sap/bc/lrep/flex/data/products` both 404) and switching variants erases the unsaved change via `VariantManagerApply.handleSelectVariant` → `eraseDirtyChangesOnVariant`; reproduces on `main` with any filter field, not specific to a custom one. `ControlVariantApplyAPI.activateVariant`/`StateUtil.applyExternalState` set state without going through the variant-select code path and so do not exercise this gap; a variant-restore test must fire a real `VariantManagement` select event. Status: pending a flexibility connector (Session/LocalStorageConnector), tracked as `docs/STATE.md` open debt, separate backlog issue (user decision 2026-09-25).
- 2026-09-25. The UI5 CDN bootstrap logs at ERROR level by default, so a "no warning" claim from the browser console is meaningless unless the page loaded with `sap-ui-log-level=WARNING` (or higher verbosity) and a positive control (an intentionally triggered warning) confirms warnings would actually surface. Status: pending triage by `/retro` (candidate: `templates/feature/VERIFICATION.md` console-check note).
- 2026-09-25. `products-rating-column` (#5): an edit-mode `sap.m.RatingIndicator` clamps a displayed value above `maxValue` and writes the clamped value back through its two-way binding on the very next render (`onBeforeRendering` calls `setValue`, UI5 1.152.0 `sap/m/RatingIndicator-dbg.js`). So a range violation left in a draft (for example a value injected directly through the OData API) self-corrects the instant the field is re-rendered or the page reloaded, even though the `ASSERT_RANGE` `DraftMessages` entry the server produced is still shown until the next refresh. A "Save is rejected by `@assert.range`" scenario is therefore only observable if the invalid value is written and Save is clicked before any reload or re-render of the field; reproducing it after a reload silently passes for the wrong reason. Status: pending triage by `/retro` (candidate: a PATTERNS or TESTING note for range checks on a clamping control).

(The retro of 2026-09-23 transferred the three entries of the `catalog-authorization` run — a mock fixture verified on a path the application never uses, a scratchpad figure read as a phase figure, a silent-hiding mechanism failing asymmetrically across pages — and the pipeline findings of that run: the registry gate deadlock, work lost at turn limits, the orchestrator fixing instead of verifying. Destinations are listed in `docs/CHANGELOG.md`, 2026-09-23, `pipeline`.)

Status: `Pending upstream @sap-ux/fiori-mcp-server` (pinned 1.12.2); `upstream-check` reports new versions.
- 2026-09-07. `DRAFT_ALREADY_EXISTS` and `DRAFT_ACTIVE_DELETE_FORBIDDEN_DRAFT_EXISTS` are untranslated (English) in `@sap/cds/_i18n/messages_ru.properties`, unlike `ASSERT_MANDATORY`/`ASSERT_RANGE`/`ASSERT_TARGET`, which are translated. Status: `Pending upstream @sap/cds`; not a project defect, no local patch planned.
- 2026-09-16. UI5 1.152.0 logs `Failed to read path /CatalogService.EntityContainer/Permissions/isEditor - TypeError: Cannot read properties of undefined (reading '$select')` once per page load for the container-qualified `$edmJson` `$Path` that CAP's role-based-visibility recipe prescribes (ADR-0013). Root cause (`reviewer`, static trace of the CDN debug sources): `_SingletonPropertyCache` takes the first path segment as the singleton, `_Helper.wrapChildQueryOptions` returns `undefined` for a `$kind: Singleton` segment and `aggregateExpandSelect` reads `$select` off it; the sibling call site in `ODataParentBinding` is guarded, this one is not. The actions still resolve correctly through the `MetaModelConverter` route (five measurements, both roles). Status: `Pending upstream sapui5` (1.152.0 from the unpinned CDN, ADR-0006); the unproven local fix is the short path `/Permissions/isEditor`, tracked in `docs/STATE.md` open debt; `upstream-check` reports the UI5 version change.
