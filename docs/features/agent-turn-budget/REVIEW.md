## Hand-off items

1. Registry rule: met. `agentMaxTurns()` is the only reader of the `maxTurns` frontmatter, and `agentRuns()` is the only rule that splits a file into runs (see "Checked and in order").
2. One-short count: not blocking. It is a documentation finding for the two code comments that say "exact". It is also a design point for the architect: when a lagged read hits the `M-3` batch, the sharper note reaches turn `M-1` instead of `M-2`. It never arrives later than `M-1`, because the batch of `M-2` reads at least `M-3`. So the last useful turn `M` is still reachable, but a denied handback loses its spare turn. The lag also delays the first note: in the live run the threshold batch 54 read 53, and no record of it exists. It also corrupts `turnNotes`. See the three Important findings. ADR-0032 and CONTEXT do not literally claim "exact"; the claim is only in the two code comments.
3. PATTERNS "Pipeline metric" (one transcript parser, hooks as the marker source), ADR-0032 decisions 1-6, ADR-0031 decision 6 (the probe commit 9f6c661 precedes the implementation d90c06b), and the PLAN phase 2 and phase 4 criteria are met in the code and tests. The open items are Minor or Important, below.
4. No finding is blocking. Every Important finding names the agent type that owns it.

## Important
- scripts/hooks/turn-budget.mjs:9 and scripts/lib/transcript-usage.mjs:400-401 state the count as "exact at hook time" / "Measured exact at PostToolBatch time (turn-budget probe P4: the current request's record is on disk)". VERIFICATION.md:38 and :85 measured 3 of 7 records one short on Claude Code 2.1.323 (the batch's own `assistant` record lands after the hook reads the file). A comment that states runtime behaviour must match the running behaviour (reviewer item 10). ADR-0032 and CONTEXT do not literally say "exact" (grep), so only these two comments are wrong. → `cap-backend-dev`: reword both to "the current request's record is usually on disk; on 2.1.323 the count can be one short (VERIFICATION check 1), the P4 fallback"; `docs-keeper` states "exact or one short" in D19/data-flow (PLAN step 9).
- scripts/lib/turn-budget.mjs:22 `TURN_LAST_CALL = 3` vs the one-short count: the sharper note can reach the agent one turn later than designed. With an exact count the hook after actual turn `M-3` reads `M-3`, so the sharper note reaches turn `M-2` and leaves 3 turns (`M-2`, `M-1`, `M`). With a one-short read it reaches turn `M-1` and leaves 2. That is the `K <= 2` design the P6 fallback replaced because a handback in turn `M` is unverified (hook-probe.md:55). A lint deny of the first handback needs a fix turn and a retry turn, so with 2 turns left the retry falls on `M`, the unverified case. This is non-blocking. CONTEXT:42 and hook-probe.md:14 decided in advance that one short means "no change". The regular note from `M - reserve` on already asks for the handback, and both check 1 agents handed back on the first note (VERIFICATION:22-23). The sharper text was never exercised (VERIFICATION:23), and the P6 fallback was chosen when P4 looked exact (hook-probe.md:75). The live repo run shows the lag at the threshold too. For `cap-backend-dev` `ab48cfd9654506e7f` (`maxTurns` 60, so the threshold is 54), turn 54 was a `Bash` batch (result 22:06:15.404Z) that grepped for `turn-note` records, so the hook was live. Yet that batch has no `turn-note` record and no `hook_additional_context` attachment: it read 53 and stayed silent, and the first note came after turn 55. A silent short read leaves no record, so "3 of 7 records" understates the rate: in that run 2 of the 4 batches from the threshold on read one short (54 and 56). Evidence: the reviewer's scratch read of `~/.claude/projects/-Users-anton-straltsou-github-Test-CAP/a7e1e6af-b74d-43f9-a399-133b59cd4391/subagents/agent-ab48cfd9654506e7f.jsonl`, turns 52-58. → `architect` decides, and the outcome is recorded in ADR-0032 decision 4. Option one: keep 3 and write that a lagged batch gives 2 turns. Option two: count the current batch when its `tool_calls[].tool_use_id` are missing from the file, the P4 row's own "count by `tool_calls` ids" remedy (ids only, never `tool_response`). Option three: `TURN_LAST_CALL = 4`.
- scripts/lib/pipeline-metrics.mjs:868 `notes: new Set(notesOf[i].map((e) => e.turn)).size`: notes are counted as distinct `turn` values. The same rule is in the test test/metrics.test.js:1811 ("the same turn logged twice counts once"). The JSDoc (:831-832) gives the reason as "a note the hook logged twice for one turn counts once", but PostToolBatch fires once per batch (VERIFICATION:38: "the hook did not fire twice; it counted one short"). So the dedupe merges two notes that the agent really received for two turns into one. In the repo run, turns 55 and 56 both logged `turn: 55` (VERIFICATION:34-35), and the card shows 1 note where the agent got 2. `turnNotes` is the figure #59 reads (ADR-0032 decision 5), so it undercounts whenever the lag hits. → `cap-backend-dev`: count `turn-note` records per run, which is one per batch under PostToolBatch, or dedupe on the record `ts`, not on `turn`, and fix the JSDoc. `test-backend`: add a case with two records of equal `turn` and different `ts` that expects 2. `docs-keeper`: put the counting rule into D19.
