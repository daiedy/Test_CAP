# ADR-0027: Typed product details as a generated form

Date: 2026-10-12. Status: accepted (user, 2026-10-12, feature `products-details-section`).
<!-- On acceptance replace the whole Status sentence with the accepted form; never append to the proposed one. -->

## Context
ADR-0026 (accepted 2026-10-11) modelled product details as a composition of free-text attribute values edited in an Object Page table. After phase 4 round 1 the user rejected the table as clumsy and decided on 2026-10-12 (`docs/features/products-details-section/CONTEXT.md` "User decisions" U1-U7 and the MULTI_LIST addition): the details become form fields generated from the subcategory; the server creates one row per assigned attribute; a subcategory change keeps common rows; empty values are allowed; values are typed by the attribute (TEXT, INTEGER, DECIMAL, LIST, MULTI_LIST) with declarative server checks and UI5 types on the client; list values are a localized entity per attribute; MULTI_LIST values are stored normalized in a child of the row. `PATTERNS.md` has no row for handler-created composition children, typed entity-attribute-value columns, a second composition level, or a generic custom section built by a factory.

Evidence: `docs/features/products-details-section/research/typed-form-facts.md` (cds-mcp, UI5 1.153.0 CDN sources, cds 10.1.1 scratch runtime matrix R1-R21, EDMX 1584 lines); `research/framework-facts.md` for the ADR-0026 facts that stay.

## Decision
1. **Shape** (`db/schema.cds`). `DetailValueTypes : CodeList { key code : String(20); }` with `TEXT`, `INTEGER`, `DECIMAL`, `LIST`, `MULTI_LIST`. `DetailAttributes` gains `valueType : Association to DetailValueTypes`, `minValue`, `maxValue : Decimal(15, 3)`, `scale : Integer` (DECIMAL only) and `values : Association to many DetailListValues on values.attribute = $self`. `DetailListValues : CodeList { key code : String(30); attribute : Association to DetailAttributes; position : Integer; }` (`position` = dropdown and display order): one list per attribute, shared by every subcategory, codes unique across lists, names localized through the `CodeList` texts (the ADR-0024 shape of `Subcategories`). `SubcategoryAttributes` gains `position : Integer`. `ProductDetails` loses `value` and gains `position : Integer`, `textValue : String(100)`, `numberValue : Decimal(15, 3)`, `listValue : Association to DetailListValues` and `selections : Composition of many ProductDetailSelections on selections.detail = $self`; `ProductDetailSelections : cuid { detail : Association to ProductDetails; value : Association to DetailListValues; }` is the second composition level. Draft-enabled through the root (ADR-0012); a top-level `POST` or `PATCH` answers 422 on both levels, a top-level `DELETE` is authorized like one through the product (corrected 2026-10-12, ADR-0026 decision 2).
2. **Service.** `ProductDetailSelections` is an explicit projection with the root's `@restrict` (the ADR-0026 decision 2 reasoning, measured again on the second level: viewer 403 on writes, `carol` 403 on reads); `@readonly DetailListValues`, `@readonly DetailValueTypes`; `SubcategoryAttributes` loses `attributeName` (its only consumer, the row's value help, is gone).
3. **Rows generated by the draft handler.** The existing `before('PATCH', Products.drafts)` registration runs `resetStaleSubcategory` and then reconciles the rows when the `PATCH` carries a non-null `subcategory_code`: rows whose attribute is assigned to the new subcategory are kept with their values and selections and get the new `position`; the other rows are deleted (their selections cascade); a row is inserted for each missing assigned attribute, empty, into `ProductDetails.drafts` with the parent's `DraftAdministrativeData_DraftUUID`. When removed rows held a value, the handler adds the warning `PRODUCTS_DETAILS_VALUES_REMOVED` on `subcategory_code` with their number and localized names (PLAN D16; it travels in the `PATCH` response header `sap-messages` and is not persisted as a draft message, measured). A `null` subcategory keeps the rows (PLAN D10 (a)). `after('EDIT', Products)` fills the missing rows of the new draft (PLAN D13). Active writes are never reconciled: the ADR-0026 root branch `PRODUCTS_SUBCATEGORY_HAS_FOREIGN_DETAILS` rejects an active subcategory change that leaves foreign rows. Rule in one line: after a subcategory change the draft holds exactly one row per attribute of the new subcategory, the common ones unchanged.
4. **Typed checks, declarative** (`srv/annotations/ProductDetails.cds`). Values are optional (U4). `textValue` only on TEXT, `numberValue` only on INTEGER or DECIMAL, `listValue` only on LIST, selections only on MULTI_LIST rows (`PRODUCTS_DETAIL_VALUE_TYPE_MISMATCH`); `numberValue` within `minValue`/`maxValue` (`PRODUCTS_DETAIL_VALUE_OUT_OF_RANGE`) and whole on INTEGER (`floor(numberValue) != numberValue`, `PRODUCTS_DETAIL_VALUE_NOT_INTEGER`, PLAN D12); `listValue` and a selection's `value` belong to the row's attribute (`PRODUCTS_DETAIL_VALUE_NOT_IN_LIST`, the ADR-0024 pair form `listValue.attribute.code != attribute.code` with null guards) and exist (`@assert.target`); a selection's value appears once per row (`exists detail.selections[value.code = $self.value.code and ID != $self.ID]`, `PRODUCTS_DETAIL_SELECTION_DUPLICATE`, no `@assert.unique`). Non-numbers and more than 3 decimals are the framework's `ASSERT_DATA_TYPE` (rejected even on a draft `PATCH`). The ADR-0026 `attribute` constraint (`NOT_ASSIGNED`, `DUPLICATE`) stays as an API guard (PLAN D15). Split (PLAN D19): the client UI5 type carries format, decimals and bounds with the framework texts; the server constraints are the API guard and the Save net, with placeholder-free texts (a constraint passes no arguments). No handler checks values.
5. **UI: one generic custom section.** `app/products/webapp/ext/fragment/DetailsForm.fragment.xml` + `DetailsForm.js`, added through Fiori MCP as the section `Details` after "Pricing & Stock" (PATTERNS "Custom section or column"). A `sap.ui.layout.form.Form` with `ColumnLayout` and one `FormContainer` whose rows are the `details` list binding (`$expand=attribute($expand=values)`, `$orderby=position`) held in the container's non-rendered `dependents` with `$$ownRequest: true`; the module keeps one form element per row context (amendment "Rows binding" below, which replaced the first wording "`formElements` bind `details` with a factory"). Per `attribute/valueType_code` a `sap.m.Input` (TEXT), a `sap.m.Input` with `sap.ui.model.odata.type.Decimal` (`scale` 0 for INTEGER, the attribute's `scale` for DECIMAL, `minimum`/`maximum` from the attribute; locale-aware), a `sap.m.ComboBox` on `attribute/values` with a non-item check in `change` (LIST), a `sap.m.MultiComboBox` whose `selectionFinish` creates and deletes contexts of the row's `selections` binding (MULTI_LIST, the only custom write code); display controls with the empty indicator, units, MULTI_LIST names joined by a comma; editability from `ui>/isEditable`; the counter "Filled N of M" computed from the bound rows. The fragment names no attribute. No regex, no controller extension. `Common.SideEffects #SubcategoryChanged` (`TargetEntities: [ details ]`) re-reads the section after the server reconciles.
6. **Removed from ADR-0026.** Decision 3 (free-text `value`, mandatory), decision 4 (the row's attribute value help with the navigation-path In parameter), decision 6 (reject at Save on a subcategory change) and decision 7 (table facet, `UI.LineItem`, `UI.HeaderInfo`, `#AttributeChanged`, `details` in `#CategoryChanged`) are superseded by this ADR. ADR-0026 decisions 1, 2 and 5 stay.

First application: feature `products-details-section` (#9), revision 2.

## Amendment: browser proof of the fragment (feature products-details-section, phase 3, 2026-10-12)
The browser proof (`docs/features/products-details-section/research/ui-proof.md`, section "Architect ruling on B2, B6, B7" with the framework facts F1-F9) refuted three mechanisms of decision 5; the decision otherwise stands and no user decision changes.
- **LIST.** A two-way `selectedKey` writes the model while the user types (a `PATCH` of `null`, or of a type-ahead item), and a value state set by the module is no message, so FE saves anyway. The `sap.m.ComboBox` stays (the user's choice): `selectedKey` is bound `OneWay`; the module writes `listValue_code` through the row context `setProperty` only in `change` (empty text: `null`; the selected item's text: its key); any other text writes nothing and adds a client validation message shaped like the framework's own type errors (`target` `<comboBoxId>/selectedKey`, `processor` `ControlMessageProcessor`, `validation: true`), which sets the Error state, blocks FE Save and is not removed by `DraftMessages` reads; the module removes it on a valid commit, on another row context and when its control is gone. The MULTI_LIST sync is therefore no longer the only custom write code. `sap.m.Select` is not the fallback any more (row in "Alternatives").
- **MULTI_LIST.** The row's `selections` binding read from the section's `$expand` has no cache of its own and cannot `create()`. `selections` leaves the section's `$expand`; the multi combo box holds the row's `selections` in its `dependents` aggregation with `parameters: { $$ownRequest: true, $select: 'ID,IsActiveEntity,value_code' }` (one `GET` per MULTI_LIST row); `selectionFinish` creates and deletes its contexts; the keys, the display join and the counter read it.
- **Edit of a product without rows** (PLAN D13). The `draftEdit` response does not carry the rows the `after('EDIT')` fill inserts (see "Rows binding": since `$$ownRequest` the dependent binding reads them itself, so this re-read is probably redundant). On entering a draft context with a subcategory the module calls `requestSideEffects([{ $NavigationPropertyPath: 'details' }])` on the product context once; after its own field writes it requests `DraftMessages` the same way, since FE's `#alwaysFetchMessages` runs only for FE fields.
- **Rows binding (2026-10-12, verification round 2 and review fixes).** The first end state (rows merged into the page's product `GET`, one form element per row from a `formElements` factory) was refuted in the browser (R2-D2 focus lost, R2-D5 list validation message lost, R2-D6 tokens recreated). Cause measured: a dependent list binding without a cache of its own is refreshed by V4 `refreshDependentListBindingsWithoutCache` on every `requestSideEffects` of the product, even a `DraftMessages` read, and the rows are rebuilt. The end state: (1) the `details` rows are bound in the FormContainer's non-rendered `dependents` with `$$ownRequest: true`, one own `GET` per page load and per Edit; `syncFormElements` keeps one form element per row context and `clearFormElements` destroys them on the binding's `refresh` event (else V4 re-requests the children of deleted rows: 404 and a modal error dialog). (2) The list items of a `ComboBox` and `MultiComboBox` are built once from the row's expanded `attribute.values` (`createValueItems`, `position` order from the `$expand`), not bound: a cache-less items binding was reset by every side effect and recreated the tokens (R2-D6); `setSelectedKeys` runs only when `diffSelections` finds a difference. (3) B6 as above: `selectedKey` `OneWay`, written in `change` only; a non-item text adds a `validation: true` message. (4) B7 as above: the own-request `selections` binding in the multi combo box's `dependents`. (5) The B2 Edit re-read `refreshRowsOfNewDraft` is kept as a safety net; it is probably redundant since `$$ownRequest` and goes only after a browser proof with a product created through the API (STATE open debt). (6) `labelFor` is set to the edit control in edit mode only (`applyLabelTarget`), because the display `Text` comes first. (7) The grid is the FE form default `ColumnLayout` 6/4/3 with `labelCellsLarge` 12. The "dependent binding cannot refresh itself" reason of the B2 bullet is true only without `$$ownRequest`.

## Alternatives
| Option | Why rejected |
|---|---|
| Keep the table section (ADR-0026 decision 7) | rejected by the user on 2026-10-12 (clumsy; the attribute dropdown repeated names, D-1) |
| One `value : String` with a regex per type | user decisions U5 and U7: typed columns, UI5 types, no hand-written regex |
| Separate `Integer` and `Decimal` columns | one `Decimal(15, 3)` column; INTEGER is a portable `floor` check plus scale 0 on the client |
| Server check of the DECIMAL attribute's scale | `round(x, n)` is non-portable (capire); the column scale 3 is enforced by `ASSERT_DATA_TYPE`, the attribute scale by the UI5 type |
| MULTI_LIST as a delimited string | not validatable per value, not filterable; the user asked for a normalized child |
| `@assert.unique` on `ProductDetailSelections` | 500 `ERR_SQLITE_ERROR` with `@cap-js/sqlite` (ADR-0026 measurement); the constraint branch gives 400 and draft messages |
| Allowed values per subcategory | the user decided one list per attribute shared by all subcategories |
| Rows created at display time or by the client | the user decided the server creates them (U2); the fragment would need create logic per attribute |
| Delete all rows when the subcategory becomes empty | PLAN D10 (b): loses values the next subcategory shares |
| Reconcile active writes too | ADR-0024 decision 3 keeps active writes unchanged; the root branch rejects instead |
| Order by attribute name | the user asked for an order per subcategory; a calculated element cannot reach the assignment row (ADR-0026 compile fact), so the position is copied once by the handler |
| Static template with four controls per element instead of a factory | the user decided a factory; kept as the named fallback of browser proof B1 |
| `sap.m.Select` for LIST | the user decided `ComboBox` with a non-item check; named as the fallback of B6 until the 2026-10-12 amendment kept the ComboBox with a one-way key and a client validation message |
| Amend ADR-0026 in place | four of its seven decisions change and five new mechanisms appear; a separate ADR keeps both readable; ADR-0026 keeps its status (the `superseded by` form would retire decisions 1, 2, 5) and gets an amendment pointer |

## Consequences
- `PATTERNS.md`: new row "Rows generated from an assignment on a draft" (the extended `before('PATCH', <Root>.drafts)` handler, insert into `<Child>.drafts` with the parent's `DraftAdministrativeData_DraftUUID`, keep common rows, warn with `req.warn`, fill at `after('EDIT')`, active writes rejected by the constraint); new row "Typed attribute values" (type on the attribute, typed columns, declarative type and range rules, UI5 Decimal type on the client); "Parent-child relationship (document)" gets the second-level fact (`@restrict` on each level, 422 on a top-level `POST` or `PATCH`, a top-level `DELETE` authorized like one through the root (corrected 2026-10-12), activation targets `in/details(...)/selections(...)/<fk>`); "Custom section or column" gets the example `DetailsForm` and the factory shape.
- `TESTING.md`: `ASSERT_DATA_TYPE` rejects a draft `PATCH`; `req.warn` of a `PATCH` handler lives only in `sap-messages`; the two-level activation targets; lean draft refuses a top-level child `POST`/`PATCH` with 422 but not a `DELETE` (403 `DRAFT_ACTIVE_DELETE_FORBIDDEN_DRAFT_EXISTS` while the root has a draft); a child row created through the API has a `null` `position`, which SQLite sorts first (added 2026-10-12, phase 2 findings).
- `ARCHITECTURE.md` "Current model": four detail entities plus the selections level.
- EDMX on this model: 1287 to 1584 lines measured (+386, -89); phase 3 adds none.
- The reviewer accepts: the reconciliation in the existing draft `PATCH` registration plus one `after('EDIT')`, no handler for value checks, no regex in the fragment, one generic fragment, the generated value lists on the new foreign keys (nothing in the UI reads them).
- Follow-ups enabled, each its own issue: filtering products by a detail value (the normalized selections allow it), an Excel import column for details, a maintenance screen for attributes and lists, per-subcategory narrowing of a list.
