# products-validations: plan

Date: 2026-10-13. Status: draft. Gate mode: semi-autonomous.

Shape (ADR-0018): one criterion per line under "Acceptance criteria", table rows only under "Steps"; explanations belong in `CONTEXT.md` or `research/`. `node scripts/check-feature-docs.mjs products-validations` verifies the shape at the phase 1 gate.

## Decisions that require an ADR
- ADR-0028 "Validation toolkit" (proposed, `docs/decisions/ADR-0028-validation-toolkit.md`): decision 1 custom texts through `@assert.format.message` / `@assert.range.message` with a message key (no PATTERNS row mentions them); decision 2 user-facing uniqueness through a self-association in `db/schema.cds` plus an `exists` constraint, never `@assert.unique` (no row covers uniqueness across the entity on a draft root); decision 3 the two-target `error('KEY', args, ('a', 'b'))` form in a constraint, a source-level API of `@cap-js/db-service` not in the capire docs, accepted only with a pinning test; decision 4 a conditionally required field as `@assert` + `error()` with both targets + `Common.FieldControl: (cond ? 7 : 3)` in the app annotations, never a conditional `@mandatory` (ADR-0025 variant without a row); decision 5 a required flag on the assignment entity read by the constraints and the form (D5 = A) instead of a copied column; decision 6 every new root constraint gets a per-row import pre-check as a pure function (generalises ADR-0021 amendment 4 E); decision 7 (only with R9) an imperative rule on a draft child through `before('SAVE', <Root>)`, `before('SAVE', <Child>)` and `before('PATCH', <Child>.drafts)` with one pure function, reserved for rules no portable expression can state.
- No ADR for R1, R3, R5 themselves (PATTERNS "Format or range check"), for the R8 branches (ADR-0026 decision 5 form) or for the `DetailsForm` label marker (ADR-0027 decision 5, a `setRequired` in the existing factory).

## Risks
- `error()` with targets is not in the capire docs (research section 2): a cds or db-service minor could change it; the R4 and R6 tests pin the `additionalTargets` shape, and the fallback is a single-target constraint (D8), a one-line change per rule.
- Fiori Elements may not render `additionalTargets` as a second error state (not measured): `ui-verifier` scenario in phase 3; fallback: accept one highlighted field, SCREENS and the OPA5 case adapt, the server rule is unchanged.
- An activation error on a custom form control (`in/details(...)/numberValue`) may stay in the message popover without a value state on the input: `ui-verifier` measures; fallback: `DetailsForm.js` adds a client `validation: true` message for an empty required field at commit (the ADR-0027 B6 shape), a `fiori-app-dev` round in phase 3.
- Input validation at activation hides the constraints until fixed (research section 1, P8d): a user can see a second set of messages on the second Save; SCREENS documents it, the OPA5 cases assert one kind per Save.
- R6 breaks every writer that omits a description (LESSONS 2026-10-10): `newProduct`, `generatedRow`, README are in steps 4 and 5; a forgotten writer shows as a red existing test at the phase 2 gate.
- The required assignments of D6 must match the seed and the journeys' target subcategories (research section 8): a wrong flag shows as a failed Save in `ProductDetailsFormJourney`, `EditCategoryOnObjectPageJourney` or `SubcategoryDependsOnCategoryJourney` at the phase 3 gate.
- `lower()` on SQLite folds ASCII only, so two Cyrillic names that differ in case are not duplicates on SQLite (they are on HANA): documented in the ADR, no test asserts Cyrillic case folding.
- Fiori Elements may apply `Validation.Pattern` or `Validation.Exclusive` on the client before the request (not measured): the message text would then be the framework's, not the project's; `ui-verifier` records which text appears and the plan gate decides whether the client type is acceptable.
- `importProducts` with `max-statements`: the pre-checks are lib functions; the handler adds one `SELECT` and three `push` lines; if ESLint still trips, the pre-check wiring moves into one `rowPreChecks(rows, order, locale)` helper next to `subcategoryMismatches`.
- Two users creating the same name concurrently both pass while typing and the second Save fails with the duplicate message: by design (the check runs at commit against active rows).
